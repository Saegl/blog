1. Why parser combinators?

Suppose you are building an issue tracker, and users ask for a search box that understands real queries:

status == "open" and (priority > 2 or owner == "saegl")

You need to turn that string into a structure your code can evaluate: an and node whose right child is an or node, whose children are comparisons. This is parsing: recovering the structure that a flat string of characters encodes. You have parsed things before, so let us go through the usual options and see where each one hurts.

  • Regular expressions. Fine for the leaves (a number, a quoted string, a field name) but not for the whole query. The parentheses can nest arbitrarily deep, and recognising balanced nesting needs unbounded memory, which a finite automaton does not have. (Python's re has extensions beyond regular languages, but nobody wants to maintain a nested query parser written in one regex.)
  • A hand-written recursive descent parser. This works, and production compilers such as GCC, Clang, Go and Rust are written this way. But it is a lot of code. Most of that code is bookkeeping (moving a position forward, skipping spaces, saving and restoring the position when an alternative fails), and the grammar ends up buried in control flow.
  • A parser generator (yacc, ANTLR, Lark). You write the grammar in a separate notation and a tool turns it into a parser. The grammar is readable, but it lives outside your language: you need a separate build step, a separate syntax, and a separate way to attach the code that builds your data structures.
  • Parser combinators. You write the grammar as ordinary code in your language. Each grammar rule becomes a value (a parser), and small functions called combinators glue parsers into bigger parsers: “this then that”, “this or that”, “this, many times”. The result reads almost like the grammar, but it is plain Python: you can unit test a single rule, put rules in a list, generate rules in a loop, or step into one with a debugger.

Here is a taste of where we are heading. This is the complete rule for a JSON array, from the parser we will build in section 13:

array = symbol("[") >> lazy(lambda: value).sep_by(symbol(",")).map(list) << symbol("]")

Read it aloud: a [ symbol, then values separated by commas, collected into a list, then a ]. The operators >> and << mean “sequence, and keep the side the arrow points to”. By the end of this page you will have written every piece of the library that makes this line work, and you will know exactly what happens, call by call, when it runs.

Concretely, we will build:

  1. a hand-written recursive descent parser, to have something to compare against;
  2. first_steps.py: parsers as bare functions, and the four basic combinators;
  3. combo.py: a typed library with operators, good error messages, a generator-based “do-notation”, precedence helpers, cut, packrat memoization and left-recursion support;
  4. a calculator in two styles (precedence levels and Pratt parsing);
  5. a JSON parser that agrees with Python's json module on 2000 random documents;
  6. a small imperative language with let, while, if and an interpreter.

Practice: motivation

easy Why can no single true regular expression (one built only from concatenation, alternation and star) decide whether a string of parentheses like (()(())) is balanced?

Hint

A regular expression is equivalent to a finite automaton. What would the automaton need to remember after reading ((((((?

Solution

Every regular expression can be compiled into a deterministic finite automaton with some fixed number of states, say \(k\). To check balance after reading a prefix, the automaton must know how many parentheses are currently open, because the strings (\(i\))\(i\) are balanced while (\(j\))\(i\) with \(j \ne i\) are not.

Feed it the prefixes (0, (1, …, (\(k\). That is \(k+1\) prefixes and only \(k\) states, so by the pigeonhole principle two different prefixes (\(i\) and (\(j\) with \(i \ne j\) end in the same state. From that state the automaton reads )\(i\) and has to reach the same verdict for both strings, yet only one of them is balanced. Contradiction. (This is the pumping-lemma argument in disguise.)

A common wrong answer is “because regexes can't count”. They can count up to any fixed bound: a regex can check balance up to depth 3. What they cannot do is count without a bound.

medium For each input format, decide whether a regex is enough or you need a parser that can recurse: (a) ISO dates like 2026-10-04; (b) arithmetic with parentheses; (c) CSV rows with quoted fields ("a,b",c); (d) JSON; (e) Python's f-strings, which can contain expressions that contain f-strings.

Solution

(a) Regex: fixed shape, no nesting. (b) Parser: parentheses nest without bound. (c) Regex is enough for a single row, since a quoted field is "([^"]|"")*" and quotes don't nest; a parser is still often nicer for good errors. (d) Parser: arrays and objects nest. (e) Parser: f-strings nest inside f-strings. Since Python 3.12 (PEP 701) the CPython grammar itself handles f-strings for exactly this reason.

The test is always the same: can the structure contain itself? If yes, you need recursion.

2. A short refresher: grammars and recursive descent

You know both topics already, so this section only fixes the notation the rest of the page uses and points out the two properties we will lean on later.

Grammar notation

We write grammars in a light EBNF. A rule gives a name to a pattern. Quoted text is literal, names refer to other rules, juxtaposition means sequence, | means alternative, * means zero or more, ? means optional, and parentheses group. Here is a grammar for nested lists of integers, which will be our running example for the next few sections:

list   = "[" items? "]"
items  = item ("," item)*
item   = number | list
number = /[0-9]+/              (a regular expression, for the leaves)

The grammar accepts [1,[2,3]], and the way it accepts it is a parse tree: each rule that was used becomes a node, and the characters are the leaves.

Recursive descent

Recursive descent turns each rule into a function. The function looks at the input at the current position, consumes what its rule describes by calling the functions of the rules it mentions, and either returns a result (advancing the position) or reports failure. Sequence becomes consecutive calls, * becomes a loop, | becomes an if (or a try-this-then-that), and a rule that mentions itself becomes a recursive call.

Two properties of recursive descent matter for everything that follows:

  1. Left recursion loops forever. A rule like expr = expr "-" number | number turns into a function whose first act is to call itself at the same position, without consuming anything. The recursion never ends. We will meet this head-on in sections 14 and 18.
  2. Alternatives are tried in order. When you write a recursive descent parser by hand, you try the alternatives one after another and commit to the first that works. That is a choice you make, and it makes the parser deterministic. Formally this puts us in the world of parsing expression grammars (PEGs) rather than context-free grammars; section 16 makes the difference precise.

Practice: grammars

easy Using the grammar above, which of these are accepted? [], [,], [[]], [1,], [01].

Solution

[]: yes, items? may be absent. [,]: no, items must start with an item. [[]]: yes, the single item is a list, which is empty. [1,]: no, every comma must be followed by an item. [01]: yes! /[0-9]+/ happily matches 01. If you wanted to forbid leading zeros you would write /0|[1-9][0-9]*/, which is exactly what JSON does.

medium Write a grammar for a comma-separated list of words in which a trailing comma is allowed (a,b, is fine, a,,b and , are not, and the empty string is fine).

Solution 
words = (word ("," word)* ","?)?
word  = /[a-z]+/

Check the cases: the empty string matches the outer ?. a,b, is word, then ("," word) once, then the optional trailing comma. a,,b fails because after a, (taken as the trailing comma) a b remains, and after a the pair ("," word) can't match ,,. A lone , fails because a non-empty list must start with a word.

The common wrong answer is (word ",")*. It accepts a,b, but rejects a,b, because it forces every word to be followed by a comma.

3. What exactly is a parser?

Before writing any parser it pays to say precisely what one is, because the precise answer is what makes combinators possible.

The textbook answer is “a function from a string to a tree”. That is right for a whole program, but it doesn't compose. Think about the rule number inside items. It isn't asked to parse the whole input; it is asked to parse a number starting at some position, and whoever called it then needs to know where the number ended, so it can continue from there. So a parser for one rule needs a slightly richer interface:

Definition: parser

A parser for values of type T is a function that takes the input text and a start position index, and returns one of two things:

  • success: a value of type T built from some prefix of text[index:], together with the position right after that prefix (where the next parser should continue);
  • failure: the position where it gave up, and a description of what it expected there.

In symbols, with \(\Sigma^*\) the set of strings, \(\mathbb{N}\) the natural numbers and \(E\) the set of error descriptions, \[\text{Parser}[T] \;=\; \Sigma^* \times \mathbb{N} \;\to\; (T \times \mathbb{N}) \;\cup\; (\mathbb{N} \times E).\]

A small example makes this concrete. Take a parser number that reads decimal digits and returns them as an int, run on the text "42 apples":

Three details of this interface do a lot of work later on:

  • We pass an index instead of slicing the string. Slicing text[index:] copies the rest of the input on every call, which makes parsing quadratic. Section 20 measures exactly how much this costs.
  • A parser consumes a prefix, not everything. number succeeding on "42 apples" says nothing about " apples"; that part is somebody else's job. If you want “the whole input”, you must ask for it by requiring the end of input afterwards.
  • Failure is a value, not an exception. The caller decides what a failure means: try another alternative, stop a loop, or give up. That decision is the heart of every combinator.
Detour: the list-of-successes rhyme

Functional programmers sum this up with a rhyme by Fritz Ruehr, popularised by Graham Hutton's textbook: “A parser for things is a function from strings to lists of pairs of things and strings.” The list lets a parser return several ways to parse a prefix (empty list = failure). That is Wadler's 1985 “list of successes” technique, and it handles ambiguous grammars by exploring every alternative. Our parsers return at most one result, committing to the first alternative that works. That is simpler and faster, and it is what nearly every practical library (Parsec, parsy, pyparsing) does. The cost is that our parsers recognise PEG languages rather than arbitrary context-free ones, which section 16 discusses.

Practice: the parser interface

easy The parser number is run on the text "7 dwarfs, 12 apostles". What does it return from index 0, from index 1, and from index 10?

Solution

Index 0: success with value 7, next index 1 (only one digit). Index 1: failure at 1, because a space is not a digit. Index 10: success with value 12, next index 12. Count it out: 7=0, space=1, dwarfs=2..7, comma=8, space=9, 1=10, 2=11, so the number ends before index 12.

medium Why does the failure case carry a position at all? The caller knows where it called the parser from.

Solution

Because a parser can fail after making progress internally. A parser for "[" items "]" called at index 0 on "[1, 2 x" gets through [1, 2 and fails at the x, index 6. For an error message, index 6 is far more useful than index 0. In section 15 we push this idea further: even successful results carry the position of the deepest failure seen along the way.

4. The hand-written way

Let's write the nested-list parser by hand, in the most direct style: a class that holds the text and a current position, with one method per grammar rule. We also allow spaces between tokens, the way a real format would.

naive_rd.py
"""Hand-written recursive descent for nested integer lists like "[1, [2, 3], []]"."""

type Nested = int | list[Nested]


class ListParser:
    def __init__(self, text: str) -> None:
        self.text = text
        self.position = 0

    def skip_spaces(self) -> None:
        while self.position < len(self.text) and self.text[self.position] == " ":
            self.position += 1

    def expect(self, char: str) -> None:
        self.skip_spaces()
        if self.position >= len(self.text) or self.text[self.position] != char:
            raise SyntaxError(f"expected {char!r} at position {self.position}")
        self.position += 1

    def peek(self) -> str:
        self.skip_spaces()
        return self.text[self.position] if self.position < len(self.text) else ""

    def number(self) -> int:
        self.skip_spaces()
        start = self.position
        while self.position < len(self.text) and self.text[self.position].isdigit():
            self.position += 1
        if start == self.position:
            raise SyntaxError(f"expected a digit at position {start}")
        return int(self.text[start : self.position])

    def item(self) -> Nested:
        return self.nested_list() if self.peek() == "[" else self.number()

    def nested_list(self) -> list[Nested]:
        self.expect("[")
        items: list[Nested] = []
        if self.peek() != "]":
            items.append(self.item())
            while self.peek() == ",":
                self.expect(",")
                items.append(self.item())
        self.expect("]")
        return items

    def parse(self) -> list[Nested]:
        result = self.nested_list()
        if self.peek() != "":
            raise SyntaxError(f"unexpected {self.peek()!r} at position {self.position}")
        return result


print(ListParser("[1, [2, 3], []]").parse())
print(ListParser("[[10], [[20, 30]], 40]").parse())
try:
    ListParser("[1, [2 3]]").parse()
except SyntaxError as error:
    print("SyntaxError:", error)
output
[1, [2, 3], []]
[[10], [[20, 30]], 40]
SyntaxError: expected ']' at position 7

It works, and for a grammar this small it is not even long. But look at what each method actually does.

5. What keeps repeating

Go through ListParser again and sort each line into one of two piles: lines that express the grammar, and lines that are plumbing.

Grammar constructHow it shows up in the code
a literal like "["skip spaces, bounds check, compare, raise, advance (expect)
a regex leaf like /[0-9]+/skip spaces, remember start, loop while digit, check non-empty, slice, convert
sequence a bcall a(), then b(); the shared self.position carries the hand-off
alternative a | bpeek() at one character and branch; works only because the alternatives start differently
repetition ("," item)*a while peek() == "," loop, written out by hand
optional items?if self.peek() != "]": you have to know what can come after items

Four problems stand out.

  1. The same patterns are written again and again. Every literal repeats the skip-compare-advance dance; every comma-separated list repeats the same loop. In a grammar with fifty rules you write these patterns fifty times, and each copy is a chance for an off-by-one.
  2. Alternatives are hard. item decides between number and list by peeking at one character. That's fine here, but what if two alternatives start the same way, like x = 1 versus x == 1? Then you need to try one, and if it fails, rewind self.position and try the other. Forgetting to rewind is a classic bug (see the practice problem).
  3. The grammar is invisible. To recover items = item ("," item)* from the code you have to reverse-engineer a loop. The grammar and the parser are two documents that drift apart.
  4. The pieces can't be reused or tested alone. number is a method bound to one object with mutable state. You can't easily say “give me a parser for a comma-separated list of whatever this other parser parses”.

That last point contains the cure. “A comma-separated list of whatever” is a function whose argument is a parser. If parsers were values (things you can pass to a function and return from it) then every repeated pattern in the table could be written once, as a function from parsers to parsers. That function is a combinator. Everything in the rest of this page follows from that one observation.

Practice: find the bug

medium A colleague extends ListParser with booleans and writes this method. [true] parses fine, but [false] is rejected. What is wrong, and what is the general lesson?

def boolean(self) -> bool:
    self.skip_spaces()
    for word, value in [("true", True), ("false", False)]:
        start = self.position
        for char in word:
            self.expect(char)  # raises SyntaxError on mismatch
        return value
    raise SyntaxError("expected a boolean")
Hint

Trace false. Which alternative does it try first, and how far does that attempt get before it fails?

Solution

There are two bugs, and both are about alternatives. First, the first failing expect raises an exception that escapes the method, so the second alternative is never tried. Feeding false fails while trying t, which is the error you saw. Second, start is computed but never used to rewind: even if the exception were caught, the position would stay wherever the failed attempt left it, and the next alternative would start in the wrong place.

The correct shape is: save the position, try the alternative, and on failure restore the position before trying the next one. Every hand-written backtracking parser has to get this right in every rule. A combinator for alternatives gets it right once, for everyone. In our design it is even simpler: positions are passed around as values rather than stored in a mutable field, so there is nothing to restore. The second alternative is simply called with the same index as the first.

6. Warm-up: a parser is a function

We take the definition from section 3 literally and write it as Python types. A success is an Ok holding a value and the next index; a failure is an Err holding the index and what we expected; a parser is any callable from (text, index) to one of those. The type aliases use the Python 3.12 type statement, so Parser[int] reads as “a parser that produces ints”.

first_steps.py — part 1: the types
"""First steps: parsers as plain functions."""

import re
from collections.abc import Callable
from dataclasses import dataclass


@dataclass(frozen=True)
class Ok[T]:
    value: T  # what we built from the text
    index: int  # where the next parser should continue


@dataclass(frozen=True)
class Err:
    index: int  # where we failed
    expected: str  # what we wanted to see there


type Result[T] = Ok[T] | Err
type Parser[T] = Callable[[str, int], Result[T]]

Now the simplest possible parsers, the leaves of every grammar. literal("[") matches exactly the text [; pattern(r"[0-9]+") matches a regular expression at the current position. Notice that both are functions that return parsers. literal is not itself a parser; you give it the text to look for, and it builds and returns a parser (the inner function parse_literal, a closure that remembers expected_text).

first_steps.py — part 2: literal and pattern
def literal(expected_text: str) -> Parser[str]:
    def parse_literal(text: str, index: int) -> Result[str]:
        if text.startswith(expected_text, index):
            return Ok(expected_text, index + len(expected_text))
        return Err(index, repr(expected_text))

    return parse_literal


def pattern(regular_expression: str) -> Parser[str]:
    compiled = re.compile(regular_expression)

    def parse_pattern(text: str, index: int) -> Result[str]:
        found = compiled.match(text, index)
        if found:
            return Ok(found.group(), found.end())
        return Err(index, f"/{regular_expression}/")

    return parse_pattern

Two details are worth slowing down for. text.startswith(expected_text, index) checks for the prefix at position index without copying anything. And compiled.match(text, index) is the regex equivalent: it anchors the match at index, unlike search, which would happily skip ahead to find a match later in the text. Getting either of these wrong is a pitfall we come back to in section 20.

Two levels: builders and parsers

Keep two kinds of function apart in your head. A parser has the signature (text, index) -> Result[T] and does the actual work when called. A parser builder (like literal or pattern) takes some configuration and returns a parser. Calling a builder parses nothing; it only constructs. All the interesting functions in this page are builders, and most of them take parsers as their configuration.

Solution

sol_first.py
"""Solutions: three more building blocks in the first_steps style."""

from first_steps import Err, Ok, Parser, Result, alt, fmap, literal, many, pattern, seq


def end_of_input(text: str, index: int) -> Result[None]:
    if index == len(text):
        return Ok(None, index)
    return Err(index, "end of input")


def optional[A, D](parser: Parser[A], default: D) -> Parser[A | D]:
    def succeed_with_default(text: str, index: int) -> Result[D]:
        return Ok(default, index)  # consume nothing

    return alt(parser, succeed_with_default)


def sep_by[A](item: Parser[A], separator: Parser[object]) -> Parser[list[A]]:
    def keep_right(pair: tuple[object, A]) -> A:
        return pair[1]

    def first_and_rest(parts: tuple[A, list[A]]) -> list[A]:
        return [parts[0], *parts[1]]

    one_or_more = fmap(first_and_rest, seq(item, many(fmap(keep_right, seq(separator, item)))))
    return optional(one_or_more, [])


number = fmap(int, pattern(r"[0-9]+"))
whole_number = fmap(lambda pair: pair[0], seq(number, end_of_input))
print(whole_number("42", 0), whole_number("42x", 0))
print(optional(literal("-"), "+")("-5", 0), optional(literal("-"), "+")("5", 0))
print(sep_by(number, literal(","))("1,22,333", 0))
print(sep_by(number, literal(","))("", 0))
print(sep_by(number, literal(","))("1,2,", 0))
output
Ok(value=42, index=2) Err(index=2, expected='end of input')
Ok(value='-', index=1) Ok(value='+', index=0)
Ok(value=[1, 22, 333], index=8)

Ok(value=[1, 2], index=3)

The output's first line shows why we need it: number alone would accept "42x" by consuming 42 and leaving x for nobody. Requiring end_of_input afterwards turns “a prefix is a number” into “the whole text is a number”.

7. The key insight: functions that combine parsers

Section 5 ended with a wish: write each repeated pattern once, as a function of the parsers involved. Now that parsers are ordinary Python values, the wish is easy to grant. Take sequence. “Run parser first; if it succeeds, run parser second where first stopped; succeed with both values.” That sentence mentions two parsers and nothing about what they parse, so it is a function of two parsers. It returns a new parser, which is again a function of (text, index).

The key insight

A combinator is a function that takes parsers and returns a parser. Because its output has the same type as its inputs, combinators nest without limit: the output of one is a valid input to another. A grammar rule like items = item ("," item)* is a nested expression of sequence, repetition and leaves. Translate each operator into its combinator and you get a nested expression of function calls that is the parser. The grammar's structure and the code's structure become the same tree.

This closure property (parsers in, parser out) is the same reason arithmetic works. Since + takes two numbers and returns a number, you can write (a + b) + c without ever thinking about it. Here is what it buys us in practice. The parser total, which adds up 1+20+300, is the expression

8. The core four: seq, alt, fmap, many

Four combinators are enough to express any grammar without recursion: sequence, ordered choice, transforming a result, and repetition. (Recursion is the fifth ingredient, and gets its own section next.)

Sequence

first_steps.py — part 3: seq and alt
def seq[A, B](first: Parser[A], second: Parser[B]) -> Parser[tuple[A, B]]:
    def parse_seq(text: str, index: int) -> Result[tuple[A, B]]:
        first_result = first(text, index)
        if isinstance(first_result, Err):
            return first_result
        second_result = second(text, first_result.index)  # continue where first stopped
        if isinstance(second_result, Err):
            return second_result
        return Ok((first_result.value, second_result.value), second_result.index)

    return parse_seq


def alt[A, B](first: Parser[A], second: Parser[B]) -> Parser[A | B]:
    def parse_alt(text: str, index: int) -> Result[A | B]:
        result = first(text, index)
        if isinstance(result, Ok):
            return result
        return second(text, index)  # backtrack: same index as before

    return parse_alt

seq(first, second) builds a parser that threads the position through: first runs at index, and second runs at first_result.index, wherever first stopped. If either fails, the whole sequence fails with that failure. The value is the pair of both values.

Ordered choice

alt(first, second) tries first; if it succeeds, that is the answer and second is never run. Only if first fails is second tried, at the same index. That is the backtracking from section 5, and notice that there is nothing to restore: the index is a local variable that the failed attempt could not change.

Ordered means ordered

alt commits to the first alternative that succeeds, even if a later one would consume more. alt(literal("a"), literal("ab")) on "ab" returns "a" and leaves b unconsumed. If the enclosing parser then needs the end of input, the whole parse fails, even though the grammar "a" | "ab" “obviously” accepts ab. Put longer alternatives first. Sections 16 and 20 return to this.

Transforming results: fmap

Leaf parsers produce strings and seq produces nested tuples. Neither is what you want in the end. fmap(transform, parser) runs the parser and, on success, applies a plain function to its value. This is how parsing produces data instead of strings: fmap(int, pattern(r"[0-9]+")) is a parser for ints.

Repetition: many

many(parser) runs parser again and again, each time from where the previous run stopped, and collects the values into a list. It stops at the first failure, and the failure is not an error for many: zero or more means stopping is normal. It returns the list and the index where the last successful run ended, so the failed attempt consumes nothing.

first_steps.py — part 4: fmap and many
def fmap[A, B](transform: Callable[[A], B], parser: Parser[A]) -> Parser[B]:
    def parse_fmap(text: str, index: int) -> Result[B]:
        match parser(text, index):
            case Ok(value, end):
                return Ok(transform(value), end)
            case Err() as error:
                return error

    return parse_fmap


def many[A](parser: Parser[A]) -> Parser[list[A]]:
    def parse_many(text: str, index: int) -> Result[list[A]]:
        values: list[A] = []
        while isinstance(result := parser(text, index), Ok):
            values.append(result.value)
            index = result.index
        return Ok(values, index)

    return parse_many

Solution

9. Recursion, and the first real grammar

The nested-list grammar contains itself: item = number | list and list contains items. With combinators that means the parser for item needs the parser for list, which needs item. In Python we can't just write

item = alt(number, nested_list)   # NameError: nested_list is not defined yet
nested_list = ...  # uses item

because alt(number, nested_list) is evaluated immediately, and at that moment nested_list does not exist yet. The fix is to delay the lookup until the parser actually runs, by the time all module-level names are defined. A def does exactly that: the body of a function is evaluated when the function is called, not when it is defined. So we write item as a function with the parser signature that builds the alternative on the spot:

first_lists.py
"""Nested integer lists, rebuilt from the first_steps building blocks."""

from first_steps import Ok, Parser, Result, alt, fmap, literal, many, pattern, seq

type Nested = int | list[Nested]


def keep_left[T](pair: tuple[T, object]) -> T:
    return pair[0]


def keep_right[T](pair: tuple[object, T]) -> T:
    return pair[1]


def token[T](parser: Parser[T]) -> Parser[T]:
    return fmap(keep_left, seq(parser, pattern(r" *")))  # skip spaces after the token


number = token(fmap(int, pattern(r"[0-9]+")))
comma, open_bracket, close_bracket = token(literal(",")), token(literal("[")), token(literal("]"))


def item(text: str, index: int) -> Result[Nested]:
    # A def can mention nested_list before it exists; that is how the grammar recurses.
    return alt(number, nested_list)(text, index)


def first_and_rest(parts: tuple[Nested, list[Nested]]) -> list[Nested]:
    return [parts[0], *parts[1]]


def nothing(text: str, index: int) -> Result[list[Nested]]:
    return Ok([], index)


items: Parser[list[Nested]] = alt(
    fmap(first_and_rest, seq(item, many(fmap(keep_right, seq(comma, item))))),
    nothing,
)


def nested_list(text: str, index: int) -> Result[list[Nested]]:
    return fmap(keep_left, seq(fmap(keep_right, seq(open_bracket, items)), close_bracket))(text, index)


print(nested_list("[1, [2, 3], []]", 0))
print(nested_list("[[10], [[20, 30]], 40]", 0))
print(nested_list("[1, [2 3]]", 0))
output
Ok(value=[1, [2, 3], []], index=15)
Ok(value=[[10], [[20, 30]], 40], index=22)
Err(index=2, expected="']'")

The first two lines of output are right. Two things are wrong, and both shape the library we build next.

  1. The code is unreadable. fmap(keep_left, seq(fmap(keep_right, seq(open_bracket, items)), close_bracket)) says “bracket, items, bracket” in the least readable way possible. Prefix function calls nest inside-out, and every “keep this part, drop that part” needs a helper function. The grammar is visible in the code, but only to a patient reader.
  2. The error message is useless. On [1, [2 3]] the real mistake is the missing comma between 2 and 3, at index 7. The parser says Err(index=2, expected="']'"): it complains about the comma at index 2, which is perfectly fine. Why? The inner list fails at index 7, so the second item fails, so the many in items stops quietly after 1 and succeeds. Then close_bracket runs at index 2, finds a comma, and that failure is the one reported. The information about index 7 was thrown away by many.

The first problem is ergonomics, and Python's operator overloading solves it. The second is a real design question, and the solution (track the furthest failure) is simple but subtle enough to deserve all of section 15. Both go into combo.

easy In first_lists.py, items is a module-level value but item and nested_list are defs. Could items have been the def and item the value instead?

Solution

What matters is that every cycle of references goes through at least one delayed lookup. The cycle is item → nested_list → items → item. Here two of its links are delayed (item's and nested_list's bodies run late). Solution

For this grammar, yes, it accepts the same inputs. A list starts with [ and a number with a digit, so for any input at most one alternative can get past its first character. Order only matters when alternatives can both succeed at the same position, as with "a" | "ab". If lists could start with a digit (say a syntax like 3[a,b,c] for a repeated list), then a successful number tried first would grab the 3 and the list alternative would never be tried. The order would then decide which language you accept.

10.1 Results that remember the furthest failure

We keep Ok and Err, with one addition, which fixes the bad error message from section 9: every result also records the furthest position at which anything failed while producing it, and what was expected there. In [1, [2 3]], the many inside the outer list succeeds, but its Ok now carries the note “by the way, at index 7 somebody expected , or ]”. When ] later fails at index 2, we compare the two failures and report the one that got further. Section 15 explains why this heuristic works so well. For now, one function does all the bookkeeping: merge(result, earlier) returns result with its failure information replaced by earlier's if earlier got further, or combined with it if both stopped at the same position.

combo.py — imports
"""combo: a small parser combinator library, built step by step."""

from __future__ import annotations

import re

combo.py — results and merge
@dataclass(frozen=True, slots=True)
class Ok[T]:
    value: T
    index: int  # where the next parser should continue
    # The furthest position where some attempt failed along the way,
    # and what was expected there. Used only for error messages.
    furthest: int = -1
    expected: frozenset[str] = frozenset()


@dataclass(frozen=True, slots=True)
class Err:
    furthest: int
    expected: frozenset[str]
    committed: bool = False  # True means "do not try alternatives"


type Result[T] = Ok[T] | Err


def merge[R: Ok[Any] | Err](result: R, earlier: Ok[Any] | Err) -> R:
    """Keep whichever failure information got further into the input."""
    if earlier.furthest > result.furthest:
        return replace(result, furthest=earlier.furthest, expected=earlier.expected)
    if earlier.furthest == result.furthest and not earlier.expected <= result.expected:
        return replace(result, expected=result.expected | earlier.expected)
    return result

The committed flag on Err is for the cut combinator in section 15. You can ignore it until then: it is always False unless cut sets it.

10.2 The Parser class

In first_steps a parser was a bare function. Now we wrap that function in a small frozen dataclass. The wrapper adds no behaviour of its own; calling a Parser just calls the function inside. What it buys is methods and operators: we can write number.map(int) instead of fmap(int, number), and a | b instead of alt(a, b), and the combinator expressions read left to right like the grammar.

combo.py — the Parser class
@dataclass(frozen=True, slots=True)
class Parser[T]:
    run: Callable[[str, int], Result[T]]

    def __call__(self, text: str, index: int) -> Result[T]:
        return self.run(text, index)

    def parse(self, text: str) -> T:
        """Parse all of `text`, or raise ParseError."""
        memo_token = _memo_table.set({})
        try:
            result = (self << eof)(text, 0)
        finally:
            _memo_table.reset(memo_token)
        match result:
            case Ok(value):
                return value
            case Err(furthest, expected):
                raise ParseError(text, furthest, expected)

    def map[U](self, transform: Callable[[T], U]) -> Parser[U]:
        def run(text: str, index: int) -> Result[U]:
            match self(text, index):
                case Ok(value, end, furthest, expected):
                    return Ok(transform(value), end, furthest, expected)
                case Err() as error:
                    return error

        return Parser(run)

    def bind[U](self, choose_next: Callable[[T], Parser[U]]) -> Parser[U]:
        def run(text: str, index: int) -> Result[U]:
            match self(text, index):
                case Ok(value, end) as first:
                    return merge(choose_next(value)(text, end), first)
                case Err() as error:
                    return error

        return Parser(run)

Three methods so far:

  • parse(text) is the entry point for users. It runs the parser at index 0, insists on reaching the end of input (via eof, defined below), and either returns the value or raises a ParseError. It also sets up a fresh memo table for each parse; the table stays empty until section 17.
  • map is fmap as a method.
  • bind runs this parser, hands its value to a function that chooses the next parser, and runs that parser where this one stopped. It is strictly more powerful than &, because the second parser can depend on what the first one found. Section 12 is about why that matters.

10.3 Operators

Python lets a class define what |, &, >> and << mean through the methods __or__, __and__, __rshift__ and __lshift__. We use them for ordered choice and three kinds of sequence:

ExpressionMeaningValue
a | btry a; if it fails, try b at the same indexa's or b's
a & ba then b(a_value, b_value)
a >> ba then bb_value (the arrow points at the kept side)
a << ba then ba_value
combo.py — operators (inside class Parser)
    def __or__[U](self, other: Parser[U]) -> Parser[T | U]:
        """Ordered choice: try self; only if it fails, try other at the same index."""

        def run(text: str, index: int) -> Result[T | U]:
            first = self(text, index)
            if isinstance(first, Ok) or first.committed:
                return first
            return merge(other(text, index), first)

        return Parser(run)

    def __and__[U](self, other: Parser[U]) -> Parser[tuple[T, U]]:
        """Sequence: run self, then other where self stopped; keep both values."""

        def run(text: str, index: int) -> Result[tuple[T, U]]:
            first = self(text, index)
            if isinstance(first, Err):
                return first
            second = merge(other(text, first.index), first)
            if isinstance(second, Err):
                return second
            return Ok((first.value, second.value), second.index, second.furthest, second.expected)

        return Parser(run)

    def __rshift__[U](self, other: Parser[U]) -> Parser[U]:
        """Sequence, keep only the right value."""
        return (self & other).map(lambda pair: pair[1])

    def __lshift__(self, other: Parser[Any]) -> Parser[T]:
        """Sequence, keep only the left value."""
        return (self & other).map(lambda pair: pair[0])

Look at how __or__ merges: when the first alternative fails and the second is tried, the second's result is merged with the first's failure. If the second succeeds, its Ok still remembers what the first alternative expected. If both fail at the same position, their expectations are united, which is how we get messages like “expected , or ]”.

Detour: Python's operator precedence applies to our operators

Overloading an operator changes what it does, not how tightly it binds. Python's precedence, from tightest to loosest, is *, then + -, then << >>, then &, then ^, then |. For us that ordering is mostly lucky:

  • a >> b | c means (a >> b) | c: sequences bind tighter than choice, as in grammars.
  • key & symbol(":") >> value means key & (symbol(":") >> value), which gives (key, value) with the colon dropped. Convenient.
  • >> and << have equal precedence and group left to right: a << b >> c is (a << b) >> c, which keeps c! The idiom open >> content << close works because it groups as (open >> content) << close.

When in doubt, add parentheses. Libraries such as parsy and pyparsing make the same choice of operators and live with the same table.

10.4 Repetition, and a guard against infinite loops

combo.py — repetition (inside class Parser)
    def many(self) -> Parser[Sequence[T]]:
        """Zero or more repetitions, as many as possible (greedy, no backtracking)."""

        def run(text: str, index: int) -> Result[Sequence[T]]:
            values: list[T] = []
            info: Ok[Any] | Err = Ok(None, index)
            while True:
                result = merge(self(text, index), info)
                match result:
                    case Err(committed=True):
                        return result
                    case Err():
                        return Ok(values, index, result.furthest, result.expected)
                    case Ok(value, end):
                        if end == index:
                            raise ValueError("many(): the parser succeeded without consuming input")
                        values.append(value)
                        index, info = end, result

        return Parser(run)

    def many1(self) -> Parser[Sequence[T]]:
        return (self & self.many()).map(lambda pair: [pair[0], *pair[1]])

    def optional[D](self, default: D) -> Parser[T | D]:
        return self | pure(default)

    def sep_by(self, separator: Parser[Any]) -> Parser[Sequence[T]]:
        return self.sep_by1(separator) | pure([])

    def sep_by1(self, separator: Parser[Any]) -> Parser[Sequence[T]]:
        return (self & (separator >> self).many()).map(lambda pair: [pair[0], *pair[1]])

many is the loop from first_steps with two additions. It merges failure information from every iteration, so that the failed last attempt (the one that ended the loop) is remembered for error messages. And it refuses to loop on a parser that succeeds without consuming input. Such a parser would succeed forever at the same index, so many would never terminate; raising an exception turns a hang into a bug report. many1, optional, sep_by and sep_by1 are then one-liners built from the others, which is the combinator style at its best.

Detour: why Sequence[T] and not list[T]

The repetition methods return Parser[Sequence[T]] even though the value is a list. The reason is variance. We want a Parser[int] to be usable wherever a Parser[int | str] is expected (a parser of ints is a parser of ints-or-strings), which requires Parser to be covariant in T. Mypy infers the variance of a PEP 695 generic class from how T is used, and list is invariant (a list[int] is not a list[int | str], because someone could append a string to it). So a method returning Parser[list[T]] makes Parser invariant, and then array: Parser[Json] = ...sep_by(...) no longer type-checks. Sequence is read-only and therefore covariant, which keeps Parser covariant. This was a real error mypy reported while this page was being written.

(Pyright infers variance for frozen dataclasses more strictly than mypy and treats Ok as invariant, so it reports two errors in __or__. The page's code is checked with mypy --strict.)

10.5 Labels

10.6 Leaves, recursion and tokens

combo.py — primitive parsers
def string(expected_text: str) -> Parser[str]:
    def run(text: str, index: int) -> Result[str]:

            return Ok(expected_text, index + len(expected_text))
        return Err(index, frozenset({repr(expected_text)}))

    return Parser(run)


def regex(pattern: str, flags: int = 0) -> Parser[str]:
    compiled = re.compile(pattern, flags)

    def run(text: str, index: int) -> Result[str]:
        found = compiled.match(text, index)  # anchored at index, no slicing
        if found:
            return Ok(found.group(), found.end())
        return Err(index, frozenset({f"/{pattern}/"}))

    return Parser(run)


def pure[T](value: T) -> Parser[T]:
    """Succeed with `value` without consuming anything."""
    return Parser(lambda text, index: Ok(value, index))


def fail(expected: str) -> Parser[Any]:
    """Fail without consuming anything."""
    return Parser(lambda text, index: Err(index, frozenset({expected})))


def _eof(text: str, index: int) -> Result[None]:

        return Ok(None, index)
    return Err(index, frozenset({"end of input"}))

def lazy[T](make_parser: Callable[[], Parser[T]]) -> Parser[T]:
    """Defer building a parser until first use; this is how grammars recurse."""
    built: list[Parser[T]] = []

    def run(text: str, index: int) -> Result[T]:
        if not built:
            built.append(make_parser())
        return built[0](text, index)

    return Parser(run)

lazy packages the trick from section 9: it takes a zero-argument function that returns a parser, and calls it only the first time the parser runs, caching the result. Writing lazy(lambda: value) inside a grammar defers the lookup of the name value until parse time, so rules can refer to rules defined further down the module.

combo.py — whitespace and tokens
whitespace: Parser[str] = regex(r"\s*")


def token[T](parser: Parser[T]) -> Parser[T]:
    """A lexeme: the parser followed by any trailing whitespace."""
    return parser << whitespace


def symbol(expected_text: str) -> Parser[str]:
    return token(string(expected_text))

The last piece is a convention for whitespace. Every token parser consumes the whitespace after itself. Then whitespace is skipped exactly once between any two tokens, and only the very start of the input needs an explicit whitespace >> …. The alternative (skipping whitespace before each token) works too. Mixing the two conventions in one grammar is a classic source of bugs.

10.7 Error reports

combo.py — ParseError
class ParseError(Exception):
    def __init__(self, text: str, index: int, expected: frozenset[str]) -> None:
        self.text, self.index, self.expected = text, index, expected
        self.line = text.count("\n", 0, index) + 1
        line_start = text.rfind("\n", 0, index) + 1
        self.column = index - line_start + 1
        line_end = text.find("\n", index)
        self.source_line = text[line_start : line_end if line_end != -1 else len(text)]
        super().__init__(str(self))

    def __str__(self) -> str:
        found = repr(self.text[self.index]) if self.index < len(self.text) else "end of input"
        wanted = " or ".join(sorted(self.expected)) or "nothing (internal error)"
        return (
            f"line {self.line}, column {self.column}: expected {wanted}, found {found}\n"
            f"    {self.source_line}\n"
            f"    {' ' * (self.column - 1)}^"
        )

The exception turns an index into a line and column, shows the offending line with a caret under the position, and lists what was expected and what was found.

11. Watching a parser run

Everything so far has been about how parsers are built. Let us now watch one run. The demo below contains a tiny JavaScript port of the same ideas (the same Ok/Err results, the same combinators) and a classic arithmetic grammar without spaces:

expr   = term   (("+" | "-") term)*
term   = factor (("*" | "/") factor)*
factor = number | "(" expr ")"

Each box in the tree is one call of a rule (expr, term, factor) or of a leaf parser (number or a literal). A box is orange while the call is running, green when it succeeds (with the span it consumed), and red when it fails (with the position where it failed). Step through 1+2*3 and watch the index: the tree grows depth-first, left to right, exactly like a hand-written recursive descent parser would call its functions.

Step through a parse

Some things to notice while you step:

  • Failures are everywhere and they are normal. After 1, term's loop tries "*" and "/" at index 1; both fail, which simply ends the loop. Most red boxes are “this repetition is over” or “not this alternative”, not errors.
  • The index only moves forward on success. A failed call leaves its caller's index unchanged. That is the whole backtracking story.
  • Precedence comes from nesting. In 1+2*3, the * is consumed by a term call that is a child of the expr loop that consumed +. So 2*3 is grouped first. Nobody wrote a precedence table; the grammar's layering produced it.
  • Try 2*(3 and 7-: the final step reports where the parse failed and what was expected.

Practice: tracing

medium Without running anything, explain why parsing 1+2*3 calls the literal "*" exactly 3 times and "/" exactly 2 times.

Solution

Every term runs factor and then a loop of (("*" | "/") factor)*. Each loop iteration tries "*" first, and tries "/" only when "*" fails.

  • The first term parses 1; its loop tries "*" at index 1 (fails, it's a +), then "/" (fails). Loop over: 1 star, 1 slash.
  • The second term parses 2; its loop tries "*" at index 3 and succeeds (no slash tried), parses factor 3, then tries "*" at index 5, the end (fails), and "/" (fails). That is 2 stars and 1 slash.

Total: 3 stars, 2 slashes, matching the counter output. The general rule is that a loop with \(k\) successful iterations makes \(k+1\) attempts, and every alternative in front of the successful one is also attempted.

medium In the demo, try 8/4/2. Does the tree group it as (8/4)/2 or 8/(4/2)? Where in the grammar does that come from, and what value does the demo compute?

Solution

Structurally the tree is flat: one term call with three factor children, and the *// attempts between them. The grouping is decided by the code that turns the loop's list of (operator, factor) pairs into a value. The demo folds the list from the left (JavaScript's reduce), giving \((8/4)/2 = 1\). Repetition loses the grouping, so the fold must put it back. That is precisely what chainl1 will package up in section 14. (Folding from the right would give \(8/(4/2) = 4\), which is wrong for division.)

12. When the next step depends on a value: bind, and a little about monads

Every grammar so far had a fixed shape: which parser runs next never depended on what an earlier parser found, only on whether it succeeded. Plenty of real formats are not like that. A classic example is the netstring, a length-prefixed string: 5:hello, means “5 characters follow, then a comma”. The payload can contain anything, including colons and commas, because the reader never looks for a delimiter; it counts.

With &, | and map alone this is impossible. Those combinators fix the structure of the parser before parsing starts, and here the structure (how many characters to take) is only known halfway through. We need a combinator that runs a parser, looks at its value, and then decides which parser to run next. That is bind, which we already defined in section 10.2:

def bind[U](self, choose_next: Callable[[T], Parser[U]]) -> Parser[U]:
    def run(text: str, index: int) -> Result[U]:
        match self(text, index):
            case Ok(value, end) as first:
                return merge(choose_next(value)(text, end), first)
            case Err() as error:
                return error
    return Parser(run)

The argument choose_next is an ordinary function from a value to a parser, and it is called during parsing, each time self succeeds. For netstrings, the function is take: given a count, it builds a parser for exactly that many characters.

netstring.py
"""Length-prefixed strings ("netstrings"): the next parser depends on a parsed value."""

This reads like straight-line code, and it scales to long sequences without the nested tuples that & produces. Here is the machinery:

combo.py — generate
type ParserBody[T] = Generator[Parser[Any], Any, T]


def generate[T](body: Callable[[], ParserBody[T]]) -> Parser[T]:
    """Write a parser as a generator: `value = yield some_parser`."""

    def run(text: str, index: int) -> Result[T]:
        steps = body()
        info: Ok[Any] | Err = Ok(None, index)
        try:
            next_parser = next(steps)
            while True:
                result = merge(next_parser(text, index), info)
                if isinstance(result, Err):
                    return result
                index, info = result.index, result
                next_parser = steps.send(result.value)
        except StopIteration as finished:
            return Ok(finished.value, index, info.furthest, info.expected)

    return Parser(run)
Detour: how a generator becomes a parser

A Python generator is a function that can pause. yield something pauses it and hands something to whoever is driving it. The driver can resume it with gen.send(value), and then the paused yield expression evaluates to value. When the generator executes return result, the driver's send raises StopIteration with result attached as .value.

generate is a driver. next(steps) runs the body up to the first yield and receives a parser. The driver runs that parser at the current index. On failure it returns the failure and abandons the generator; on success it advances the index and sends the value back into the body, which continues to its next yield. When the body returns, StopIteration.value becomes the final result. Each yield is exactly one bind: “run this parser, and call the rest of the function with its value”.

One subtlety: a generator can only be run once, so run calls body() afresh on every parse attempt. Because of backtracking, the same @generate parser can be attempted many times in one parse.

Why this is a monad (lightly)

You have now met the two operations that make parsers a monad:

  • pure(x): the parser that succeeds with x and consumes nothing;
  • p.bind(f): run p, feed its value to f, run the parser that f returns.

That's really all “monad” means here: a type with those two operations that obey three laws. Writing \(p \gg\!= f\) for p.bind(f), the laws are

\[ \begin{aligned} \text{left identity:}\quad & \text{pure}(x) \gg\!= f \;\equiv\; f(x)\\ \text{right identity:}\quad & p \gg\!= \text{pure} \;\equiv\; p\\ \text{associativity:}\quad & (p \gg\!= f) \gg\!= g \;\equiv\; p \gg\!= (\lambda x.\; f(x) \gg\!= g) \end{aligned} \]

where \(\equiv\) means “behaves identically on every input text and start index”. In plain words: wrapping a value in pure and immediately binding it does nothing; binding to pure does nothing; and it doesn't matter how you group a chain of binds. The last law is what lets generate flatten any chain of steps into straight-line code without changing its meaning.

The proofs come straight from the code. For left identity: pure(x) called at index \(i\) returns Ok(x, i) with no failure info (furthest = -1). bind then calls f(x) at index \(i\) and merges the result with that Ok. Merging with “nothing failed anywhere” changes nothing, so the result is exactly f(x)(text, i). For right identity: if p fails, bind returns its error unchanged. If it succeeds with Ok(v, j, F, E), then pure(v) at \(j\) gives Ok(v, j) with no failure info, and merging copies \(F, E\) back in. The result is Ok(v, j, F, E), identical to p's. For associativity, both sides run p, then f's parser where p stopped, then g's parser where that stopped, and stop at the first failure. So values and indices agree. The failure bookkeeping agrees too, because merge is the operation “keep the larger furthest, unite expectations on a tie”. That operation is associative and commutative (it is the least upper bound in the order “further is bigger; on a tie, compare expectation sets by inclusion”), so the grouping cannot matter.

Applicative versus monadic parsers

The combinators &, map and pure (Haskell calls this interface Applicative) build parsers whose structure is fixed in advance: it is a data structure you could walk before parsing anything, to print the grammar, compute which characters each rule can start with, or generate a railroad diagram. bind gives up that transparency. Its second half is a Python function, and nobody can see inside a function without calling it. That is the trade-off. Monadic parsers can parse context-sensitive formats such as netstrings, matching XML tags or here-documents; applicative parsers can be analysed and optimised. Libraries designed for speed (and parser generators) lean applicative; Parsec-style libraries offer both.

hard Prove the associativity law for the values and indices by unfolding both sides on an input where all three parsers succeed, and identify what happens when f's parser fails.

Solution

Let p at index \(i\) give value \(a\) and end \(j\); let f(a) at \(j\) give \(b\), end \(k\); let g(b) at \(k\) give \(c\), end \(l\).

Left side, (p.bind(f)).bind(g). The inner bind runs p (to \(j\)), then f(a) (to \(k\)), and succeeds with \((b, k)\). The outer bind passes \(b\) to g and runs g(b) at \(k\), giving \((c, l)\).

Right side, p.bind(lambda x: f(x).bind(g)). It runs p (to \(j\)), then calls the lambda with \(a\), giving the parser f(a).bind(g), and runs it at \(j\). That runs f(a) (to \(k\)), then g(b) at \(k\), giving \((c, l)\).

Both give \((c, l)\). If f(a) fails at some position \(e\): on the left, the inner bind returns that error and the outer bind returns it unchanged. On the right, f(a).bind(g) returns it, and the outer bind returns it. Same error either way, so the two sides agree in all cases (the cases where p or g fails are analogous).

13. Capstone I: a complete JSON parser

We now have everything needed for a real format. JSON's grammar, per RFC 8259, with whitespace allowed around every token, is:

document = ws value
value    = "null" | "true" | "false" | number | string | array | object
array    = "[" (value ("," value)*)? "]"
object   = "{" (member ("," member)*)? "}"
member   = string ":" value
number   = /-?(0|[1-9][0-9]*)(\.[0-9]+)?([eE][+-]?[0-9]+)?/
string   = '"' (plain-chars | "\" escape | "\u" 4 hex digits)* '"'

The translation is nearly mechanical. Each rule becomes a module-level parser, and lazy(lambda: value) breaks the recursion cycle:

json_parser.py
"""A complete JSON parser (RFC 8259) built with combo."""

from collections.abc import Sequence

from combo import Parser, generate, lazy, regex, string, symbol, token, whitespace, ParserBody

type Json = None | bool | int | float | str | list[Json] | dict[str, Json]

ESCAPES = {'"': '"', "\\": "\\", "/": "/", "b": "\b", "f": "\f", "n": "\n", "r": "\r", "t": "\t"}

null: Parser[Json] = symbol("null").map(lambda _: None)
true: Parser[Json] = symbol("true").map(lambda _: True)
false: Parser[Json] = symbol("false").map(lambda _: False)


def to_number(digits: str) -> int | float:
    return float(digits) if any(c in digits for c in ".eE") else int(digits)


number: Parser[Json] = token(
    regex(r"-?(0|[1-9][0-9]*)(\.[0-9]+)?([eE][+-]?[0-9]+)?").label("number")
).map(to_number)

plain_chars = regex(r'[^"\\\x00-\x1f]+')
simple_escape = string("\\") >> regex(r'["\\/bfnrt]').map(lambda letter: ESCAPES[letter])
unicode_escape = (string("\\u") >> regex(r"[0-9a-fA-F]{4}")).map(lambda hex4: chr(int(hex4, 16)))


def join_chunks(chunks: Sequence[str]) -> str:
    # 😀 arrives as two surrogate halves; this glues them into one code point
    return "".join(chunks).encode("utf-16", "surrogatepass").decode("utf-16")


string_literal: Parser[str] = token(
    string('"') >> (plain_chars | simple_escape | unicode_escape).many().map(join_chunks) << string('"')
).label("string")

array: Parser[Json] = (
    symbol("[") >> lazy(lambda: value).sep_by(symbol(",")).map(list) << symbol("]")
).label("array")


@generate
def member() -> ParserBody[tuple[str, Json]]:
    key = yield string_literal
    yield symbol(":")
    item = yield value
    return key, item


obj: Parser[Json] = (
    symbol("{") >> member.sep_by(symbol(",")).map(dict) << symbol("}")
).label("object")

value: Parser[Json] = null | true | false | number | string_literal | array | obj

A few details deserve comment:

  • number keeps ints as ints. to_number looks for ., e or E, matching what json.loads does, so that 1815 becomes an int and 1.5e3 a float.
  • Strings are built from chunks. Runs of ordinary characters come out of one regex match, so a long string costs one regex call, not one call per character. Escapes are separate alternatives. The control characters U+0000–U+001F are excluded from plain chunks because the RFC forbids them unescaped.
  • Surrogate pairs. Characters outside the Basic Multilingual Plane, such as 😀, are written in JSON as two \u escapes (a UTF-16 surrogate pair). join_chunks glues the pair back into one code point by round-tripping through UTF-16.
  • member uses generate, because three steps with two values worth keeping read better as straight-line code than as (string_literal << symbol(":")) & value.

14. Precedence and associativity

Arithmetic is the classic stress test for any parsing technique, because a correct parser has to get two separate things right. Precedence: 2 + 3 * 4 is 2 + (3 * 4). Associativity: 10 - 3 - 2 is (10 - 3) - 2 = 5, not 10 - (3 - 2) = 9, while 2 ^ 3 ^ 2 conventionally means 2 ^ (3 ^ 2) = 512. The two groupings of subtraction are different trees:

Two tempting mistakes

The textbook grammar for left-associative subtraction is expr = expr "-" number | number. It is left recursive: the first thing expr does is call expr. Flipping it around to expr = number "-" expr | number removes the left recursion, but it builds the wrong tree:

The first attempt calls itself at index 0, which calls itself at index 0, and so on until Python gives up. The second terminates, but it parses 10 - (3 - 2), because the recursion is on the right, so the right side groups first. Neither is acceptable.

The fix: repetition plus a left fold

The standard way out has two steps. First, write the rule with repetition instead of recursion: expr = number ("-" number)*. This accepts the same strings and is not left recursive. The repetition produces a flat list, 10 followed by the pairs [("-", 3), ("-", 2)], which has lost the grouping. Second, rebuild the grouping with a left fold: start with 10, combine with 3 to get 7, combine that with 2 to get 5. That pattern is common enough to deserve a combinator, traditionally called chainl1 (“chain, left-associative, at least one operand”). Its operator parser returns the function that combines two operands, so the fold doesn't need to know what the operators mean:

combo.py — chainl1 and chainr1
def chainl1[T](operand: Parser[T], operator: Parser[Callable[[T, T], T]]) -> Parser[T]:
    """operand (operator operand)*, folded to the LEFT: ((a - b) - c)."""

    def fold(parts: tuple[T, Sequence[tuple[Callable[[T, T], T], T]]]) -> T:
        accumulated, rest = parts
        for combine, right in rest:
            accumulated = combine(accumulated, right)
        return accumulated

    return (operand & (operator & operand).many()).map(fold)


def chainr1[T](operand: Parser[T], operator: Parser[Callable[[T, T], T]]) -> Parser[T]:
    """operand (operator operand)*, folded to the RIGHT: a ^ (b ^ c)."""

    def fold(parts: tuple[T, Sequence[tuple[Callable[[T, T], T], T]]]) -> T:
        first, rest = parts
        if not rest:
            return first
        operands = [first, *(right for _, right in rest)]
        combines = [combine for combine, _ in rest]
        accumulated = operands[-1]
        for combine, left in zip(reversed(combines), reversed(operands[:-1])):
            accumulated = combine(left, accumulated)
        return accumulated

    return (operand & (operator & operand).many()).map(fold)

Precedence then comes from layering, one rule per precedence level, each built from the next tighter one: an expression is a chain of terms joined by +/-; a term is a chain of powers joined by *//; and so on down to atoms. A looser operator can only appear between the units that the tighter levels have already grouped.

Claim: chainl1 builds the left-associated tree

For operands \(a_0, a_1, \dots, a_n\) and operators \(\circ_1, \dots, \circ_n\), chainl1 returns \[ ((\cdots((a_0 \circ_1 a_1) \circ_2 a_2) \cdots) \circ_n a_n). \] Proof by induction on \(n\), the number of operators. Write \(\text{acc}_k\) for the value of accumulated after \(k\) iterations of fold's loop. Base case: \(\text{acc}_0 = a_0\), the claim for \(n = 0\). Step: the loop body sets \(\text{acc}_{k} = \circ_k(\text{acc}_{k-1}, a_k)\). By the induction hypothesis \(\text{acc}_{k-1}\) is the left-nested expression of the first \(k\) operands, so \(\text{acc}_k\) is that expression combined with \(a_k\) on the right, which is the left-nested expression of the first \(k+1\) operands. \(\blacksquare\)

chainr1 is the mirror image: it walks the operand list backwards and builds \(a_0 \circ_1 (a_1 \circ_2 (\cdots \circ_n a_n))\).

An alternative: Pratt parsing

One rule per precedence level works, but a language with fifteen levels (C has about that many) gets fifteen nearly identical rules. Each atom is then parsed through fifteen nested calls, which costs time and recursion depth. Pratt parsing, also called top-down operator precedence (Vaughan Pratt, 1973), handles all levels in one loop. Each operator gets two numbers, its binding powers: how strongly it pulls on the operand to its left and on the operand to its right.

The Pratt loop

expression(min_power) parses an expression in which every operator binds at least as strongly as min_power:

  1. Parse a start: an atom, or a prefix operator followed by expression(its right power).
  2. Loop: look at the next operator. If its left power is less than min_power, stop and return. The operator belongs to some enclosing call, which will see it next. Otherwise consume it, parse expression(its right power) as the right operand, combine, and repeat.

Associativity is encoded in the asymmetry. For a left-associative operator choose right power = left power + 1, so the recursive call refuses another copy of the same operator and hands it back to the loop. For a right-associative operator choose right power < left power, so the recursive call accepts it and the right side groups first.

It is easy to write a Pratt parser as a combinator. It is just a Parser whose run function we write by hand, using other parsers for atoms and operators. That is worth remembering: a combinator library is open, and when a pattern is awkward to express with the existing combinators, you drop down to a hand-written run and the result composes with everything else.

pratt.py
"""Pratt parsing (top-down operator precedence) as a hand-written combo Parser."""

import math
import operator
from collections.abc import Callable, Iterable
from dataclasses import dataclass

from combo import Err, Ok, Parser, Result, lazy, merge, regex, string, symbol, whitespace


@dataclass(frozen=True)
class Operators[T]:
    prefix: dict[str, tuple[int, Callable[[T], T]]]  # name -> (right power, action)
    infix: dict[str, tuple[int, int, Callable[[T, T], T]]]  # name -> (left power, right power, action)
    postfix: dict[str, tuple[int, Callable[[T], T]]]  # name -> (left power, action)


def one_of(names: Iterable[str]) -> Parser[str]:
    """Any of the operator names. Longest first, so "**" is tried before "*"."""
    ordered = sorted(names, key=len, reverse=True)
    # Start from a parser that always fails and expects nothing, then add one alternative per name.
    parser: Parser[str] = Parser(lambda text, index: Err(index, frozenset()))
    for name in ordered:
        parser = parser | (string(name) << whitespace)
    return parser


def pratt[T](atom: Parser[T], operators: Operators[T]) -> Parser[T]:
    prefix_token = one_of(operators.prefix)
    after_operand_token = one_of({*operators.infix, *operators.postfix})

    def expression(min_power: int) -> Parser[T]:
        def run(text: str, index: int) -> Result[T]:
            # 1. The start of an expression: a prefix operator, or an atom.
            prefix = prefix_token(text, index)
            if isinstance(prefix, Ok):
                right_power, action = operators.prefix[prefix.value]
                operand = merge(expression(right_power)(text, prefix.index), prefix)
                if isinstance(operand, Err):
                    return operand
                left: Ok[T] = Ok(action(operand.value), operand.index, operand.furthest, operand.expected)
            else:
                start = merge(atom(text, index), prefix)
                if isinstance(start, Err):
                    return start
                left = start
            # 2. Keep extending `left` while the next operator binds tightly enough.
            while True:
                found = merge(after_operand_token(text, left.index), left)
                if isinstance(found, Err):
                    return merge(left, found)
                name = found.value
                if name in operators.postfix:
                    left_power, unary_action = operators.postfix[name]
                    if left_power < min_power:
                        break
                    left = Ok(unary_action(left.value), found.index, found.furthest, found.expected)
                else:
                    left_power, right_power, binary_action = operators.infix[name]
                    if left_power < min_power:
                        break  # leave this operator to an enclosing call
                    right = merge(expression(right_power)(text, found.index), found)
                    if isinstance(right, Err):
                        return right
                    left = Ok(binary_action(left.value, right.value), right.index, right.furthest, right.expected)
            return left

        return Parser(run)

    return expression(0)

expression(0): atom 2; sees ** (left 8 ≥ 0), consumes it, calls expression(7). That call: atom 3; sees **, left 8 ≥ 7, so it keeps it, consumes it, calls expression(7) which returns 2. The prefix operator parses its operand with expression(right power), so the right power decides which infix operators the operand may absorb: those with left power ≥ it. 15. Error messages that point at the problem

A parser for real users spends most of its life rejecting input, so the quality of its error messages matters as much as its speed. We have used combo's messages for a while; now let us look at why they work, and at the one tool (cut) they still need.

The problem: failures get swallowed

Recall the bad message from section 9. On [1, [2 3]], first_steps complained about index 2, while the real problem is at index 7:

The general pattern: combinators that are allowed to fail (many, optional, sep_by, every |) turn failures into successes, and the information about what was wrong disappears with them. The failure that finally surfaces is often a consequence of the real error, far away from it.

The furthest-failure heuristic

Furthest failure

Report the failure at the largest index reached during the whole parse, together with everything that was expected at that index.

Why this is usually right: a parser can only fail at index \(k\) after everything before \(k\) was accepted by some path through the grammar. The path that got furthest is the reading of the input that explains the most characters, and so the most plausible thing the author meant. The unexpected character is where that reading breaks down.

Implementing it is the reason Ok carries furthest and expected. Every combinator merges the information from all the results it saw, including the successful ones, so a failure swallowed by many still travels upward inside the Ok, and parse() reports the furthest one at the end. The expected set at that index explains the “or”s in our messages: every alternative that failed exactly there contributes. That is Parsec's design, described in Leijen and Meijer's 2001 report, and nearly every combinator library since uses it.

When backtracking hides a real error: cut



Furthest failure fixes the message when the parse fails. Sometimes, though, backtracking makes a broken

closing parenthesis of a link, the link alternative fails, the plain-text alternative happily accepts the

16. Why it works: semantics and proofs



We have tested a lot. This section steps back and asks what a combinator parser means, which inputs it
accepts, and why it always terminates. The answers explain several surprises that are otherwise confusing,
starting with this one: our parsers do not accept everything their EBNF grammar does.



16.1 What a parser denotes



Fix an input text \(x\) of length \(n\), and write \(x_i\) for its character at index \(i\). Each parser \(P\)
denotes a function from start indices to outcomes:
\[ [\![P]\!] : \{0, \dots, n\} \to \{0, \dots, n\} \cup \{\bot\}, \]
where \(j\) means “succeeds and stops at \(j\)” and \(\bot\) means “fails”. (We drop the values and the error
bookkeeping here; neither affects whether or where a parse succeeds.) Reading the code of each
combinator gives its meaning:





ParserMeaning at index \(i\)


string(s)\(i + |s|\) if \(x_i \dots x_{i+|s|-1} = s\), else \(\bot\)


p & q\(\bot\) if \([\![p]\!](i) = \bot\); otherwise \([\![q]\!]([\![p]\!](i))\)


p | q\([\![p]\!](i)\) if it is not \(\bot\); otherwise \([\![q]\!](i)\)


p.many()the index after the longest run \(i = j_0 < j_1 < \dots < j_k\) with \([\![p]\!](j_{t}) = j_{t+1}\), stopping at the first \(\bot\)


pure(v)\(i\)


eof\(i\) if \(i = n\), else \(\bot\)





These are exactly the rules of a parsing expression grammar (PEG), the formalism Bryan Ford
introduced in 2004. A PEG and an EBNF grammar can look identical on paper. The difference is in the two rows for
| and many: choice is ordered and committed (once p succeeds,
q is never considered, even if the rest of the parse then fails), and repetition is greedy and
never gives anything back. A context-free grammar, by contrast, accepts a string if any combination
of choices derives it.

shift/reduce conflicts to resolve.




Claim: | is associative, and fail is its unit (on outcomes)

\([\![(p \mid q) \mid r]\!] = [\![p \mid (q \mid r)]\!]\), and \([\![\text{fail} \mid p]\!] = [\![p]\!] = [\![p \mid \text{fail}]\!]\).


Proof. Both sides of the first equation return the first non-\(\bot\) value among
\([\![p]\!](i), [\![q]\!](i), [\![r]\!](i)\), in that order, or \(\bot\) if all three fail. For the second:
\([\![\text{fail}]\!](i) = \bot\), so the choice falls through to \(p\); and if \(p\) fails, adding a final \(\bot\)
changes nothing. \(\blacksquare\)


Note the qualifier “on outcomes”: fail("x") | p can produce a different error message than
p, because "x" joins the expected set when p fails at the same index. Laws about
parsers usually hold up to error bookkeeping, which is why laws_check.py compares values and indices only.





16.2 Termination



When does a combinator parser always halt? We've seen two ways to loop: left recursion (section 14) and
many over a parser that consumes nothing (section 10, which we turned into an exception). It turns out
these are the only two ways.




Theorem: termination

Suppose (1) every primitive parser terminates, (2) every parser used inside many consumes at least one
character whenever it succeeds, and (3) the grammar has no left recursion: there is no cycle of rules in which a rule
can reach itself at the same index without consuming input. Then parsing any input terminates.





Proof. Consider the tree of all parser calls made while parsing: each node is a call “parser \(P\) at
index \(i\)”, and its children are the calls it makes directly. We show this tree is finite.



Step 1: no infinite path. Build a directed graph on rules with an edge \(P \to Q\) whenever \(P\)
can call \(Q\) at its own start index, i.e. before consuming anything. Condition (3) says this graph has no
cycles, so we can define \(h(P)\), the length of the longest path starting at \(P\), which is a finite number. Give each
call “\(P\) at \(i\)” the measure \(\mu = (n - i,\; h(P))\), compared lexicographically (first component first). Take
any call and one of its children “\(Q\) at \(j\)”. Since parsers never move backwards, \(j \ge i\). If \(j > i\),
the first component strictly decreases. If \(j = i\), then \(P \to Q\) is an edge of the graph, so
\(h(Q) < h(P)\): the first component stays equal and the second strictly decreases. Either way the measure strictly
decreases from parent to child. The lexicographic order on pairs of natural numbers is well-founded (it has no infinite
decreasing chain), so every path in the call tree is finite.



Step 2: finitely many children. A combinator makes a bounded number of direct calls, except
many, which loops. By condition (2), each successful iteration strictly increases the index, and the
index can't exceed \(n\), so many makes at most \(n + 1\) calls. Every node therefore has finitely many
children.



Step 3. A tree in which every node has finitely many children and every path is finite is itself
finite. (This is König's lemma, read contrapositively: an infinite finitely-branching tree has an infinite path.)
Each call does a finite amount of work besides its children, so the whole parse terminates. \(\blacksquare\)



The proof also says what to check when a grammar hangs: look for a path from a rule back to itself that consumes
nothing, and for loops whose body may succeed empty. combo catches the second kind at runtime; the first
shows up as RecursionError, or is handled properly by left_recursive in section 18.

17. Complexity: backtracking and packrat parsing



How fast is a combinator parser? For most practical grammars, linear in the input size. In the worst case,
exponential. This section shows both and the classic cure, packrat memoization.



17.1 A grammar that explodes



Here is an innocent-looking grammar for sums and differences of parenthesised terms, written the way the grammar
reads, with three alternatives that all start with term:



expr = term "+" expr | term "-" expr | term
term = "(" expr ")" | number



On the input (1) the trouble is already visible. expr tries its first alternative:
term parses all of (1), but no + follows, so the alternative fails and everything it
did is thrown away. The second alternative parses term again, from the same index, for the same result.
The third does it a third time. And each of those term calls contains an expr call on the
inside, which does the same thing three times over:





Let's count. Write \(E(d)\) for the number of term calls made by expr on the input with
\(d\) nested parentheses, \((^d\,1\,)^d\). At depth 0, expr calls term three times, once per
alternative, and each term just parses the number: \(E(0) = 3\). At depth \(d \ge 1\), expr
calls term three times; each of those calls parses the ( and then runs expr on the
inside, which has depth \(d - 1\) and makes \(E(d-1)\) term calls of its own. So


\[ E(d) = 3\,\bigl(1 + E(d-1)\bigr), \qquad E(0) = 3. \]


To solve it, add \(\tfrac{3}{2}\) to both sides. The right side becomes
\(3 + 3E(d-1) + \tfrac{3}{2} = 3\bigl(E(d-1) + \tfrac{3}{2}\bigr)\), so the shifted sequence
\(F(d) = E(d) + \tfrac{3}{2}\) satisfies \(F(d) = 3F(d-1)\) with \(F(0) = \tfrac{9}{2}\). That is a geometric
sequence: \(F(d) = \tfrac{9}{2} \cdot 3^d = \tfrac{3^{d+2}}{2}\). Subtracting back,


\[ E(d) = \frac{3^{d+2} - 3}{2}. \]


Check: \(E(0) = (9 - 3)/2 = 3\), \(E(1) = (27 - 3)/2 = 12\), \(E(2) = (81-3)/2 = 39\). The work grows by a factor of
3 per level of nesting, so twelve levels already mean over two million calls. Here are measurements of three versions of the grammar:



backtracking.py
"""Exponential backtracking, and two cures: packrat memoization and left factoring."""

from combo import Parser, Result, lazy, regex, string

calls = 0


def counted[T](parser: Parser[T]) -> Parser[T]:
    def run(text: str, index: int) -> Result[T]:
        global calls
        calls += 1
        return parser(text, index)

    return Parser(run)


def build(memoize: bool, left_factored: bool) -> Parser[object]:
    number = regex(r"[0-9]+")

    else:  # expr = term "+" expr | term "-" expr | term
        expr = (term & string("+") & lazy(lambda: expr)) | (term & string("-") & lazy(lambda: expr)) | term
    return expr

17.2 Packrat parsing: memoize (rule, index)



A parser's outcome at a given index depends on nothing but the text and the index: no hidden state, no
side effects. So the second and third term call at the same index will certainly return the same
result as the first. Caching results by (parser, index) is therefore always safe, and it turns the
exponential tree into a small DAG. This is packrat parsing, from Bryan Ford's 2002 master's thesis
and ICFP paper:



combo.py — memo (inside class Parser)
    def memo(self) -> Parser[T]:
        """Packrat memoization: compute each (parser, index) at most once per parse()."""
        slot = object()  # a unique, hashable identity for this memoized parser

        def run(text: str, index: int) -> Result[T]:
            table = _memo_table.get(None)
            if table is None:  # called outside parse(): no table, no caching
                return self(text, index)
            key = (slot, index)
            if key not in table:
                table[key] = self(text, index)
            return table[key]

        return Parser(run)




The table lives in the ContextVar that parse() creates fresh for every parse, so results
from one input never leak into another. The memo column above shows the effect: \(3d + 3\) lookups,
of which only \(d + 1\) are real computations (one per nesting level). The rest are table hits.




Claim: packrat parsing is linear time

Let \(R\) be the number of memoized rules and \(n\) the input length. If every rule is memoized and each rule's
body, apart from its calls to other memoized rules, does a constant amount of work, then a parse takes
\(O(R \cdot n)\) time and \(O(R \cdot n)\) memory.


Proof. There are at most \(R(n+1)\) distinct pairs (rule, index). Each pair is computed at most once;
every later request for it is a dictionary lookup, \(O(1)\) expected. A computation does constant work of its own plus
some constant number \(c\) of requests to other pairs. Total work is at most
\(R(n+1) \cdot (\text{const} + c \cdot O(1)) = O(R\,n)\). The table holds at most \(R(n+1)\) entries. \(\blacksquare\)


The fine print: “constant work per body” excludes unbounded loops like many inside a rule. Ford's
formulation rewrites repetition as recursion through a memoized helper rule, which restores the bound. Primitive
regexes must also run in time proportional to what they consume.





Linear time sounds like an unconditional win, but the memory is the catch. A table entry per rule per character
means hundreds of bytes per input byte for a big grammar. Memoizing a rule whose result is never re-requested is
pure overhead (a dictionary insert per call). So practical packrat parsers memoize selectively. CPython's PEG
parser, for example, memoizes only rules marked (memo) in the grammar, plus all left-recursive rules.



17.3 The other cure: don't ask twice



The third column, left-factored, is the grammar rewritten so that the common prefix is parsed once:
expr = term (("+" | "-") expr)?. It does \(d + 1\) calls with no table at all. Most hand-tuned grammars
look like this: alternatives start with distinct tokens (an LL(1)-like shape), so | never retries an
expensive prefix. For such grammars a combinator parser is linear without any memoization. Our JSON parser is
an example: every alternative of value starts with a different character, and its run time grows in
proportion to the input:

medium In the memo column, why are there exactly \(3d + 3\) calls of the counted
term parser, and why are \(d+1\) of them real computations?


Solution

The counter wraps the memoized parser, so it counts requests. expr is not memoized, so every
expr call still makes 3 requests for term, one per alternative. With memoization only the first request
at each index actually runs term's body, and that body calls expr once on the inner text. So
there is exactly one expr call per nesting level, \(d+1\) of them (depths \(d, d-1, \dots, 0\)), each
making 3 requests: \(3(d+1) = 3d+3\) requests. The distinct indices requested are \(0, 1, \dots, d\) (the
term at depth \(k\) starts after \(d-k\) open parentheses), so \(d+1\) real computations and \(2d+2\)
lookups, matching the demo.








medium Memoization is “always safe” only because parsers have no side effects. Give an
example of a map callback that breaks under memoization, and one that breaks without it.


Solution

A callback that increments a counter of “numbers seen” runs once per computed parse. Without memo it runs
again on every backtracking retry, overcounting (section 20 shows a real run where a number is seen twice). With memo it
runs once per (rule, index), so a lookup does not re-run it, but now the count depends on which rules
are memoized. A callback that appends to a list breaks the same way. Worst of all is a callback with a
non-idempotent external effect, such as an INSERT into a database: it may run for a branch that is
later abandoned. The rule: map callbacks should be pure functions that build values. Do the effects
afterwards, on the finished result.









18. Left recursion, for real



chainl1 sidesteps left recursion by rewriting the grammar. But sometimes you want to keep the grammar
as written, either because it is easier to read, or because you are transcribing a specification that uses left
recursion, or because the left-recursive structure is more complex than a binary operator chain (think
call = call "(" args ")" | call "." name | atom). In 2008, Warth, Douglass and Millstein showed that a
packrat parser can support left recursion with a small twist on the memo table.



The idea: grow a seed



Look at expr = expr "-" number | number at index 0. Any successful parse of expr at index
0 must, at the bottom of its left spine, use the second alternative, number. Bigger parses wrap a smaller
parse of expr as the left operand. So build it from the bottom:



    
  
  1. Plant a seed in the memo table: “expr at 0 fails”.
    2. 
  
  2. Evaluate the body. Its left-recursive call to expr at 0 hits the table and gets the seed, failure,
  so the first alternative fails and the second gives 10, ending at index 3. That beats the seed, so
  it becomes the new seed.
    3. 
  
  3. Evaluate the body again. Now the recursive call returns 10 (ending at 3), so the first
  alternative extends it: 10 - 3, ending at 7. Better, so it is the new seed.
    4. 
  
  4. Again: (10 - 3) - 2, ending at 10. New seed.
    5. 
  
  5. Again: the recursive call returns the parse ending at 10, the first alternative needs a - at index
  10, the end of input, and fails. The second alternative gives 10 ending at 3, which is not better.
  Stop, and return the seed.
    6. 




combo.py — left_recursive
def left_recursive[T](make_parser: Callable[[], Parser[T]]) -> Parser[T]:
    """A rule that may call itself at the same index (Warth-style seed growing).

    Only for direct left recursion; must be used inside parse().
    """
    slot = object()
    built: list[Parser[T]] = []

    def run(text: str, index: int) -> Result[T]:
        if not built:
            built.append(make_parser())
        table = _memo_table.get(None)
        if table is None:
            raise RuntimeError("left_recursive() parsers need parse()")
        key = (slot, index)
        if key in table:  # a recursive call at the same index: answer from the table
            return table[key]
        table[key] = Err(index, frozenset())  # the seed: "the rule fails here"
        while True:
            attempt = built[0](text, index)
            best = table[key]
            if isinstance(attempt, Err) or (isinstance(best, Ok) and attempt.index <= best.index):
                return merge(best, attempt)  # stopped growing
            table[key] = attempt  # grew further: plant the bigger seed and retry

    return Parser(run)

Claim: seed growing terminates

Each round either stops or replaces the seed with a result whose end index is strictly larger. End indices
are at most \(n\), so there are at most \(n + 1\) rounds. Each round is an ordinary parse of the body, in which the
left-recursive call returns immediately from the table, so by the termination theorem of section 16 (the
left-recursive edge is now broken) each round terminates. \(\blacksquare\)





Two limitations of this simple version are worth knowing. First, it handles direct left recursion. With
indirect left recursion (a = b "x" | "y", b = a "z"), the other rules in the cycle
compute results from the current seed. If those results get memoized, they go stale when the seed grows.
Warth et al. track the set of rules “involved” in each growing cycle and refuse to memoize them during growth;
CPython's PEG parser generator uses a variant of the same idea. Second, it must run inside parse(),
because it needs the memo table.

easy How many rounds does left_recursive run for expr on the
input 9, and what is returned?


Solution

Two rounds. Round 1: the recursive call returns the seed (failure), the first alternative fails, and
number gives 9 ending at 1. That beats a failure, so it becomes the seed. Round 2: the recursive

medium What does e = left_recursive(lambda: e | number) do on
9? Plain recursive descent would recurse forever; does seed growing?


Solution

It returns 9 after two rounds (this was run while writing the page). Round 1: e at 0 gives the
seed failure, and number gives 9 at 1, so the seed becomes 9. Round 2: e at 0 returns 9 at 1
from the table and succeeds immediately with the same end index, not larger, so it stops. The rule
e = e | number is pointless but harmless. The “strictly larger” condition is what turns a potential
infinite loop into a fixpoint computation.

def binary_operator(*names: str) -> Parser[Callable[[Expr, Expr], Expr]]:
    choice = symbol(names[0])
    for name in names[1:]:
        choice = choice | symbol(name)
    return choice.map(lambda name: lambda left, right: Binary(name, left, right)).label("operator")


atom: Parser[Expr] = number | identifier.map(Variable) | (symbol("(") >> lazy(lambda: expression) << symbol(")"))
unary: Parser[Expr] = (symbol("-") >> lazy(lambda: unary)).map(Negate) | atom
product = chainl1(unary, binary_operator("*", "/", "%"))
total = chainl1(product, binary_operator("+", "-"))
comparison: Parser[Expr] = (total & (binary_operator("==", "!=", "<=", ">=", "<", ">") & total).optional(None)).map(
    lambda parts: parts[0] if parts[1] is None else parts[1][0](parts[0], parts[1][1])
)
expression: Parser[Expr] = comparison.label("expression")




The precedence levels are chainl1 chains, as in section 14. binary_operator lists
longer operators first ("<=" before "<") because of ordered choice. It also labels the
choice "operator", so an error says “expected ; or operator” instead of listing all eleven
operators. Comparisons are deliberately non-associative: at most one per level, so 1 < 2 < 3 is
a syntax error rather than a confusing (1 < 2) < 3.



tiny.py — part 4: statements
block: Parser[Sequence[Statement]] = symbol("{") >> lazy(lambda: statement).many() << symbol("}")

let_statement: Parser[Statement] = keyword("let") >> cut(
    (identifier << symbol("=")) & (expression << symbol(";"))
).map(lambda pair: Let(*pair))

assign_statement: Parser[Statement] = ((identifier << symbol("=")) & cut(expression << symbol(";"))).map(
    lambda pair: Assign(*pair)
)

print_statement: Parser[Statement] = keyword("print") >> cut(expression << symbol(";")).map(Print)

while_statement: Parser[Statement] = keyword("while") >> cut(expression & block).map(lambda pair: While(*pair))


@generate
def if_statement() -> ParserBody[Statement]:
    yield keyword("if")
    condition: Expr = yield cut(expression)
    then_body: Sequence[Statement] = yield cut(block)
    else_body: Sequence[Statement] = yield (keyword("else") >> cut(block)).optional([])
    return If(condition, then_body, else_body)


statement: Parser[Statement] = let_statement | print_statement | while_statement | if_statement | assign_statement
program: Parser[Sequence[Statement]] = whitespace >> statement.many() << eof




Every statement that starts with a keyword wraps the rest of its body in cut. Once we have
seen while, the input is certainly a while-loop, and a broken condition should be reported as such
rather than trying the assignment alternative and producing a confusing message about the word while.
The assignment statement cuts after name = for the same reason. if_statement uses
generate because it has four steps with three values to keep, and the optional else branch
reads naturally as a yield.



The interpreter



tiny.py — part 5: the interpreter
OPERATIONS: dict[str, Callable[[int, int], int]] = {
    "+": lambda a, b: a + b,
    "-": lambda a, b: a - b,
    "*": lambda a, b: a * b,
    "/": lambda a, b: a // b,
    "%": lambda a, b: a % b,
    "==": lambda a, b: int(a == b),
    "!=": lambda a, b: int(a != b),
    "<": lambda a, b: int(a < b),
    "<=": lambda a, b: int(a <= b),
    ">": lambda a, b: int(a > b),
    ">=": lambda a, b: int(a >= b),
}


def evaluate(expr: Expr, variables: dict[str, int]) -> int:
    match expr:
        case Number(value):
            return value
        case Variable(name):
            return variables[name]
        case Negate(operand):
            return -evaluate(operand, variables)
        case Binary(operator, left, right):
            return OPERATIONS[operator](evaluate(left, variables), evaluate(right, variables))


def execute(statements: Sequence[Statement], variables: dict[str, int], output: list[str]) -> None:
    for current in statements:
        match current:
            case Let(name, value):
                variables[name] = evaluate(value, variables)
            case Assign(name, value):
                if name not in variables:
                    raise NameError(f"assignment to undeclared variable {name!r}")
                variables[name] = evaluate(value, variables)
            case Print(value):
                output.append(str(evaluate(value, variables)))
            case While(condition, body):
                while evaluate(condition, variables):
                    execute(body, variables, output)
            case If(condition, then_body, else_body):
                execute(then_body if evaluate(condition, variables) else else_body, variables, output)


def run(source: str) -> str:
    output: list[str] = []
    execute(program.parse(source), {}, output)
    return " ".join(output)

whose final value is "times". Generating parsers in a loop (operator tables, keyword lists) is exactly
where this bites. Fix: create the closure in a helper function (always), so each call has its
own scope. The default-argument trick lambda _, word=word: word also works but doesn't type-check
cleanly under mypy.

6. Side effects in map

The first alternative parsed 7, then failed on the missing comma, and was thrown away; the second

7. Slicing the input


pit_slicing.py
import time

from combo import Err, Ok, Parser, Result, string


def slicing_string(expected_text: str) -> Parser[str]:
    """The tempting version: cut the rest of the input off, then check its start."""

    def run(text: str, index: int) -> Result[str]:
        rest = text[index:]  # copies len(text) - index characters, every call!
        if rest.startswith(expected_text):
            return Ok(expected_text, index + len(expected_text))
        return Err(index, frozenset({repr(expected_text)}))

    return Parser(run)


for size in [25_000, 50_000, 100_000, 200_000]:
    text = "a" * size
    for name, make in [("startswith(s, index)", string), ("text[index:]", slicing_string)]:
        started = time.perf_counter()
        make("a").many().parse(text)
        print(f"{size:>6} chars, {name:>21}: {(time.perf_counter() - started) * 1000:7.1f} ms")

output

The slicing version copies the remaining text on every call. Each copy is fast C code, so at small sizes you barely

8. Recursion depth


pit_depth.py
import sys

from json_parser import document


def survives(depth: int) -> bool:
    try:
        document.parse("[" * depth + "]" * depth)
        return True
    except RecursionError:
        return False


low, high = 1, 1000  # survives(low) is True, survives(high) is False
while high - low > 1:
    middle = (low + high) // 2
    low, high = (middle, high) if survives(middle) else (low, middle)
print(f"recursion limit {sys.getrecursionlimit()}: deepest array that parses = {low}")
print(f"about {sys.getrecursionlimit() / low:.0f} Python frames per level of nesting")

output
recursion limit 1000: deepest array that parses = 40
about 25 Python frames per level of nesting


This one is surprising: our JSON parser gives up at 40 levels of nesting. Each level of JSON nesting passes through
about 25 Python frames: value's six nested |s, each going through Parser.__call__
and the inner run, plus the label, <<, >>,
&, map and sep_by layers. json.loads handles nesting in the
thousands. Fixes: raise the limit with sys.setrecursionlimit (cheap, but the C stack
is finite); flatten choices with a choice(*parsers) combinator that loops instead of nesting; or make
hot paths call .run directly. Treat the depth limit as part of your format's spec: an attacker can send
[[[[[[….



9. Mixing whitespace conventions


If some tokens skip whitespace before themselves and others after, then either whitespace gets
skipped twice (harmless) or nowhere (a parse error on perfectly good input, only at some boundaries). Pick one
convention (this page uses “after, plus once at the start”) and build every token through one helper.



10. Operator precedence of the combinator operators


Python's precedence, not your grammar's, decides how a >> b | c & d groups (section 10.3).
When a rule mixes | with &, >> or <<, add
parentheses even if you believe they are unnecessary.



11. Errors after skipped whitespace


With trailing-whitespace tokens, an error that “belongs” at the end of a line is reported at the start of the next
non-blank line (section 19). That's not wrong, but it surprises users. Keep the end index of the last real token
around if you want compiler-style “expected ; after this” messages.





Practice: pitfalls




medium Explain the output of pit_side_effects.py line by line, and predict
what seen would contain for the input 7,8.


Solution

On 7: the first alternative number & "," & number calls remember("7"),
then fails on the missing comma. | then runs the second alternative, which calls
remember("7") again and succeeds. So seen == ['7', '7']. On 7,8: the first
alternative succeeds outright, calling remember for 7 and for 8, and the second
alternative is never tried. So seen == ['7', '8']. The same parser has different side effects on different
inputs, which is why effects in actions are so treacherous.








hard Derive the slicing cost more precisely: if string("a").many() runs on
\(n\) characters a with the slicing implementation, how many characters are copied in total? Check it
against the timings.


Solution

The loop calls the parser at indices \(0, 1, \dots, n\) (the last call fails at the end). The call at index \(i\)
copies \(n - i\) characters. The total is \(\sum_{i=0}^{n}(n-i) = \sum_{k=0}^{n} k = \frac{n(n+1)}{2}\). For
\(n = 200{,}000\) that's about \(2 \times 10^{10}\) characters, roughly 20 GB of memory traffic for a 200 KB
input. Modern memory bandwidth is tens of GB/s, so this predicts on the order of a second of extra time. The measured
difference is about 0.7 s. Doubling \(n\) quadruples the copying, consistent with the slicing column growing from 322 ms to
980 ms while the index column only doubles.









21. Summary and cheat sheet



If you remember five things from this page, make them these:



    
  
  1. A parser is a function from (text, index) to (value, next index) or failure. Passing the
  index explicitly, instead of mutating a position, is what makes backtracking free and composition possible.
    2. 
  
  2. A combinator takes parsers and returns a parser. Closure under composition means grammar rules
  translate one-to-one into nested expressions, and every repeated pattern (lists, separators, brackets, operator
  chains) is written once.
    3. 
  
  3. Our parsers are PEGs. Choice is ordered and committed, and repetition is greedy. Order alternatives
  longest-first, make loop bodies consume, and never write left recursion unless the library handles it.
    4. 
  
  4. bind lets the next parser depend on a value (netstrings, matching tags,
  indentation), at the cost of making the parser opaque to analysis. generate turns chains of
  bind into straight-line code.
    5. 
  
  5. Good errors come from tracking the furthest failure, merging expectations at that index,
  labelling for humans, and cutting where the meaning becomes certain. Good performance comes from not asking
  the same question twice: left-factor, and memoize where you can't.
    6.

22. Quiz



A mixed review of the whole page. The answers that can be computed were checked by running
combo (file quiz_check.py, output at the end).







Q1. easy What does (string("a") | string("ab")).many()
return on "abab" from index 0?


Solution

['a'], stopping at index 1. The first iteration takes "a" (ordered choice; "ab"
is never tried). The second iteration at index 1 sees b: both alternatives fail, so the loop stops. If you
expected ['ab', 'ab'], you were reading the alternatives as a context-free choice.







Q2. easy Does (string("ab") | string("a")) >> string("b")
accept "ab"?


Solution

No. The choice commits to "ab", then "b" fails at the end: “column 3: expected 'b', found end
of input”. The choice is never revisited, even though taking "a" would have let the whole parse succeed.
That is PEG semantics (section 16).







Q3. easy How does Python group a & b | c >> d?


Solution

(a & b) | (c >> d): >> binds tightest, then &, then |.







Q4. easy What does chainr1 with integer division compute for
8 / 4 / 2? And chainl1?


Solution

chainr1: \(8 / (4 / 2) = 4\). chainl1: \((8/4)/2 = 1\).







Q5. easy What is combo's error message for
(string("x") | string("y")).parse("z")?


Solution

line 1, column 1: expected 'x' or 'y', found 'z'. Both alternatives failed at index 0, so
merge united their expectations.







Q6. medium Why must lazy cache the parser it builds, instead
of calling make_parser() on every run?


Solution

Correctness doesn't depend on it, but identity and speed do. make_parser() might construct a fresh parser
tree on each call (if the lambda builds rather than looks up), which is slow, and each fresh tree would have a fresh
memo() slot, so memoization would never hit. Caching gives each lazy exactly one underlying
parser.







Q7. medium True or false: adding .memo() to a rule can
change which inputs are accepted.


Solution

False for memo(). A parser's result depends only on the text and the index, so a cached result is
identical to a recomputed one. (Callbacks with side effects may run fewer times, but the outcome is the same.) It is
true for left_recursive, which uses the memo table to accept left-recursive inputs that plain
recursion could never finish.







Q8. medium What happens with string("a").optional(None).many()
on "aa"?


Solution

ValueError: many(): the parser succeeded without consuming input. Two iterations consume the
as; the third, at the end, has optional succeed with None without consuming. Without the guard
this would loop forever.







Q9. medium How many term calls does the plain backtracking
grammar of section 17 make at nesting depth 5?


Solution

\(E(5) = (3^7 - 3)/2 = (2187 - 3)/2 = 1092\). By recurrence: 120 at depth 3, \(3 \cdot 121 = 363\), then
\(3 \cdot 364 = 1092\).







Q10. medium In a Pratt table, a new left-associative operator
<> should bind tighter than + (1, 2) but looser than * (3, 4). Find binding
powers for it, or explain why you have to renumber.


Solution

Write its powers as \((l, r)\), with \(r = l + 1\) for left-associativity, and turn each requirement into an
inequality using the rule “an operator is absorbed by expression(m) iff its left power ≥ m”:


    
  
  • a + b <> c must be a + (b <> c): +'s right operand
  expression(2) must absorb it, so \(l \ge 2\).
    • 
  
  • a * b <> c must be (a * b) <> c: expression(4) must not absorb
  it, so \(l < 4\).
    • 
  
  • a <> b * c must be a <> (b * c): expression(r) must absorb
  *, so \(3 \ge r\).
    • 
  
  • a <> b + c must be (a <> b) + c: \(1 < r\).
    • 



With \(r = l + 1\): \(l \ge 2\) and \(l + 1 \le 3\), so \(l = 2, r = 3\). It fits exactly, with no renumbering. Running
the Pratt parser with "<>": (2, 3, ...) confirms
1 + 2 <> 3 => (1 + (2 <> 3)), 1 <> 2 * 3 => (1 <> (2 * 3)) and
1 <> 2 <> 3 => ((1 <> 2) <> 3). The common wrong answer is that no integer pair fits
“strictly between” (1, 2) and (3, 4). But the powers of neighbouring levels may touch: what matters is only the
inequalities above. A second new level between + and <>, however, would not fit, which
is why real Pratt tables use spaced-out numbers like 10, 20, 30.







Q11. hard The termination theorem requires “no left recursion”. Is
a = b "x" | "y", b = "z" a | a "w" left recursive?


Solution

Yes, indirectly. Edges at the same index: a → b (first alternative), b → a (second alternative of
b, since a is called before anything is consumed). The first alternative of b
consumes z first, so it is fine. The cycle a → b → a without consumption makes plain recursive descent
loop on every input: a calls b, whose first alternative either fails (no
z) or recurses after consuming. Whenever it fails, the second alternative calls a at the
original index, which calls b again. Our simple left_recursive doesn't handle it, because the
recursion is indirect.







Q12. hard Why can't the applicative combinators (&,
map, |, pure) parse netstrings, while they can parse nested lists, which
aren't regular either?


Solution

Applicative combinators plus recursion describe PEG-style grammars: the structure of the parser is fixed before
parsing starts, and only the path through it depends on the input. Nested lists are context-free:
the grammar is fixed, and the nesting is handled by recursion. Netstrings need the number 5 to determine how many
characters the next step consumes, an unbounded family of different grammars (one per length). A fixed grammar cannot
encode “read exactly the number you just parsed”; that requires feeding a parsed value back into the parser's
structure, which is what bind does.

25. Extensions



    
  
  • Source spans in the AST. Record (start, end) on every node by wrapping rules in a
  combinator that captures the indices. Every later error message (type errors, runtime errors) can then point at
  source code.
    • 
  
  • Incremental parsing. Editors reparse on every keystroke. Packrat memo tables can be partially
  reused after an edit (Dubroy and Warth, “Incremental Packrat Parsing”, 2017; used in the Ohm toolkit); tree-sitter does
  the same for GLR.
    • 
  
  • Streaming input. Our parsers need the whole text. Attoparsec-style libraries accept input in
  chunks and return a “partial” result that asks for more.
    • 
  
  • Error recovery (homework 3), and “labelled failures” for PEGs, which attach recovery rules to
  specific failure labels (Medeiros and Mascarenhas).
    • 
  
  • Pretty printers as inverse parsers. If the grammar is data (homework 6), the same description can
  print an AST back to text, so you can round-trip.
    • 
  
  • Parsing with derivatives (Might, Darais and Spiewak, 2011): a very different algorithm that
  handles all context-free grammars, built from Brzozowski derivatives of regular expressions.

Appendix: combo.py in full



The complete library, exactly as built in sections 10–18, in one block. It passes mypy --strict, and
every example on this page imports it.



combo.py
"""combo: a small parser combinator library, built step by step."""

from __future__ import annotations

import re
from collections.abc import Callable, Generator, Sequence
from contextvars import ContextVar
from dataclasses import dataclass, replace
from typing import Any

@dataclass(frozen=True, slots=True)
class Ok[T]:
    value: T
    index: int  # where the next parser should continue
    # The furthest position where some attempt failed along the way,
    # and what was expected there. Used only for error messages.
    furthest: int = -1
    expected: frozenset[str] = frozenset()


@dataclass(frozen=True, slots=True)
class Err:
    furthest: int
    expected: frozenset[str]
    committed: bool = False  # True means "do not try alternatives"


type Result[T] = Ok[T] | Err


def merge[R: Ok[Any] | Err](result: R, earlier: Ok[Any] | Err) -> R:
    """Keep whichever failure information got further into the input."""
    if earlier.furthest > result.furthest:
        return replace(result, furthest=earlier.furthest, expected=earlier.expected)
    if earlier.furthest == result.furthest and not earlier.expected <= result.expected:
        return replace(result, expected=result.expected | earlier.expected)
    return result


@dataclass(frozen=True, slots=True)
class Parser[T]:
    run: Callable[[str, int], Result[T]]

    def __call__(self, text: str, index: int) -> Result[T]:
        return self.run(text, index)

    def parse(self, text: str) -> T:
        """Parse all of `text`, or raise ParseError."""
        memo_token = _memo_table.set({})
        try:
            result = (self << eof)(text, 0)
        finally:
            _memo_table.reset(memo_token)
        match result:
            case Ok(value):
                return value
            case Err(furthest, expected):
                raise ParseError(text, furthest, expected)

    def map[U](self, transform: Callable[[T], U]) -> Parser[U]:
        def run(text: str, index: int) -> Result[U]:
            match self(text, index):
                case Ok(value, end, furthest, expected):
                    return Ok(transform(value), end, furthest, expected)
                case Err() as error:
                    return error

        return Parser(run)

    def bind[U](self, choose_next: Callable[[T], Parser[U]]) -> Parser[U]:
        def run(text: str, index: int) -> Result[U]:
            match self(text, index):
                case Ok(value, end) as first:
                    return merge(choose_next(value)(text, end), first)
                case Err() as error:
                    return error

        return Parser(run)

    #@part operators
    def __or__[U](self, other: Parser[U]) -> Parser[T | U]:
        """Ordered choice: try self; only if it fails, try other at the same index."""

        def run(text: str, index: int) -> Result[T | U]:
            first = self(text, index)
            if isinstance(first, Ok) or first.committed:
                return first
            return merge(other(text, index), first)

        return Parser(run)

    def __and__[U](self, other: Parser[U]) -> Parser[tuple[T, U]]:
        """Sequence: run self, then other where self stopped; keep both values."""

        def run(text: str, index: int) -> Result[tuple[T, U]]:
            first = self(text, index)
            if isinstance(first, Err):
                return first
            second = merge(other(text, first.index), first)
            if isinstance(second, Err):
                return second
            return Ok((first.value, second.value), second.index, second.furthest, second.expected)

        return Parser(run)

    def __rshift__[U](self, other: Parser[U]) -> Parser[U]:
        """Sequence, keep only the right value."""
        return (self & other).map(lambda pair: pair[1])

    def __lshift__(self, other: Parser[Any]) -> Parser[T]:
        """Sequence, keep only the left value."""
        return (self & other).map(lambda pair: pair[0])

    #@part repetition
    def many(self) -> Parser[Sequence[T]]:
        """Zero or more repetitions, as many as possible (greedy, no backtracking)."""

        def run(text: str, index: int) -> Result[Sequence[T]]:
            values: list[T] = []
            info: Ok[Any] | Err = Ok(None, index)
            while True:
                result = merge(self(text, index), info)
                match result:
                    case Err(committed=True):
                        return result
                    case Err():
                        return Ok(values, index, result.furthest, result.expected)
                    case Ok(value, end):
                        if end == index:
                            raise ValueError("many(): the parser succeeded without consuming input")
                        values.append(value)
                        index, info = end, result

        return Parser(run)

    def many1(self) -> Parser[Sequence[T]]:
        return (self & self.many()).map(lambda pair: [pair[0], *pair[1]])

    def optional[D](self, default: D) -> Parser[T | D]:
        return self | pure(default)

    def sep_by(self, separator: Parser[Any]) -> Parser[Sequence[T]]:
        return self.sep_by1(separator) | pure([])

    def sep_by1(self, separator: Parser[Any]) -> Parser[Sequence[T]]:
        return (self & (separator >> self).many()).map(lambda pair: [pair[0], *pair[1]])

    #@part label
    def label(self, name: str) -> Parser[T]:
        """On a failure right at the start, report `name` instead of the details."""

        def run(text: str, index: int) -> Result[T]:
            result = self(text, index)
            if isinstance(result, Err) and result.furthest <= index:
                return Err(index, frozenset({name}), result.committed)
            return result

        return Parser(run)

    #@part memo
    def memo(self) -> Parser[T]:
        """Packrat memoization: compute each (parser, index) at most once per parse()."""
        slot = object()  # a unique, hashable identity for this memoized parser

        def run(text: str, index: int) -> Result[T]:
            table = _memo_table.get(None)
            if table is None:  # called outside parse(): no table, no caching
                return self(text, index)
            key = (slot, index)
            if key not in table:
                table[key] = self(text, index)
            return table[key]

        return Parser(run)


_memo_table: ContextVar[dict[tuple[object, int], Result[Any]] | None] = ContextVar("memo_table")

def string(expected_text: str) -> Parser[str]:
    def run(text: str, index: int) -> Result[str]:
        if text.startswith(expected_text, index):
            return Ok(expected_text, index + len(expected_text))
        return Err(index, frozenset({repr(expected_text)}))

    return Parser(run)


def regex(pattern: str, flags: int = 0) -> Parser[str]:
    compiled = re.compile(pattern, flags)

    def run(text: str, index: int) -> Result[str]:
        found = compiled.match(text, index)  # anchored at index, no slicing
        if found:
            return Ok(found.group(), found.end())
        return Err(index, frozenset({f"/{pattern}/"}))

    return Parser(run)


def pure[T](value: T) -> Parser[T]:
    """Succeed with `value` without consuming anything."""
    return Parser(lambda text, index: Ok(value, index))


def fail(expected: str) -> Parser[Any]:
    """Fail without consuming anything."""
    return Parser(lambda text, index: Err(index, frozenset({expected})))


def _eof(text: str, index: int) -> Result[None]:
    if index == len(text):
        return Ok(None, index)
    return Err(index, frozenset({"end of input"}))


eof: Parser[None] = Parser(_eof)

def lazy[T](make_parser: Callable[[], Parser[T]]) -> Parser[T]:
    """Defer building a parser until first use; this is how grammars recurse."""
    built: list[Parser[T]] = []

    def run(text: str, index: int) -> Result[T]:
        if not built:
            built.append(make_parser())
        return built[0](text, index)

    return Parser(run)

class ParseError(Exception):
    def __init__(self, text: str, index: int, expected: frozenset[str]) -> None:
        self.text, self.index, self.expected = text, index, expected
        self.line = text.count("\n", 0, index) + 1
        line_start = text.rfind("\n", 0, index) + 1
        self.column = index - line_start + 1
        line_end = text.find("\n", index)
        self.source_line = text[line_start : line_end if line_end != -1 else len(text)]
        super().__init__(str(self))

    def __str__(self) -> str:
        found = repr(self.text[self.index]) if self.index < len(self.text) else "end of input"
        wanted = " or ".join(sorted(self.expected)) or "nothing (internal error)"
        return (
            f"line {self.line}, column {self.column}: expected {wanted}, found {found}\n"
            f"    {self.source_line}\n"
            f"    {' ' * (self.column - 1)}^"
        )

def cut[T](parser: Parser[T]) -> Parser[T]:
    """If `parser` fails, the failure is final: enclosing `|` and many() won't backtrack."""

    def run(text: str, index: int) -> Result[T]:
        result = parser(text, index)
        if isinstance(result, Err) and not result.committed:
            return replace(result, committed=True)
        return result

    return Parser(run)

type ParserBody[T] = Generator[Parser[Any], Any, T]


def generate[T](body: Callable[[], ParserBody[T]]) -> Parser[T]:
    """Write a parser as a generator: `value = yield some_parser`."""

    def run(text: str, index: int) -> Result[T]:
        steps = body()
        info: Ok[Any] | Err = Ok(None, index)
        try:
            next_parser = next(steps)
            while True:
                result = merge(next_parser(text, index), info)
                if isinstance(result, Err):
                    return result
                index, info = result.index, result
                next_parser = steps.send(result.value)
        except StopIteration as finished:
            return Ok(finished.value, index, info.furthest, info.expected)

    return Parser(run)

def chainl1[T](operand: Parser[T], operator: Parser[Callable[[T, T], T]]) -> Parser[T]:
    """operand (operator operand)*, folded to the LEFT: ((a - b) - c)."""

    def fold(parts: tuple[T, Sequence[tuple[Callable[[T, T], T], T]]]) -> T:
        accumulated, rest = parts
        for combine, right in rest:
            accumulated = combine(accumulated, right)
        return accumulated

    return (operand & (operator & operand).many()).map(fold)


def chainr1[T](operand: Parser[T], operator: Parser[Callable[[T, T], T]]) -> Parser[T]:
    """operand (operator operand)*, folded to the RIGHT: a ^ (b ^ c)."""

    def fold(parts: tuple[T, Sequence[tuple[Callable[[T, T], T], T]]]) -> T:
        first, rest = parts
        if not rest:
            return first
        operands = [first, *(right for _, right in rest)]
        combines = [combine for combine, _ in rest]
        accumulated = operands[-1]
        for combine, left in zip(reversed(combines), reversed(operands[:-1])):
            accumulated = combine(left, accumulated)
        return accumulated

    return (operand & (operator & operand).many()).map(fold)

def left_recursive[T](make_parser: Callable[[], Parser[T]]) -> Parser[T]:
    """A rule that may call itself at the same index (Warth-style seed growing).

    Only for direct left recursion; must be used inside parse().
    """
    slot = object()
    built: list[Parser[T]] = []

    def run(text: str, index: int) -> Result[T]:
        if not built:
            built.append(make_parser())
        table = _memo_table.get(None)
        if table is None:
            raise RuntimeError("left_recursive() parsers need parse()")
        key = (slot, index)
        if key in table:  # a recursive call at the same index: answer from the table
            return table[key]
        table[key] = Err(index, frozenset())  # the seed: "the rule fails here"
        while True:
            attempt = built[0](text, index)
            best = table[key]
            if isinstance(attempt, Err) or (isinstance(best, Ok) and attempt.index <= best.index):
                return merge(best, attempt)  # stopped growing
            table[key] = attempt  # grew further: plant the bigger seed and retry

    return Parser(run)

whitespace: Parser[str] = regex(r"\s*")


def token[T](parser: Parser[T]) -> Parser[T]:
    """A lexeme: the parser followed by any trailing whitespace."""
    return parser << whitespace


def symbol(expected_text: str) -> Parser[str]:
    return token(string(expected_text))
