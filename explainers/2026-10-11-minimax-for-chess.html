1. Two positions

Here are two chess positions. In both it is White's move, and in both the material is exactly level.

In position A, the white queen can capture the pawn on d5. A pawn is a pawn. But the d5 pawn is defended three times, by the rook on d8, the knight on f6 and the pawn on c6, and whichever of them takes back, White has traded a queen for a pawn. The capture is a blunder.

In position B, the white queen can move to d8, giving check, where the black rook simply takes it. That looks even worse than position A: a queen for nothing. But after the rook takes, White's own rook recaptures on d8, and the black king, boxed in by its own pawns on f7, g7 and h7, is checkmated. Giving away the queen wins the game.

So a rule like "take material when you can" plays the wrong move in A, and a rule like "never give material away" misses the win in B. We could try to patch the rules: "take material unless the piece is defended", "give material away if it leads to mate", and so on, and we would never finish, because chess has more exceptions than we have patience.

This page is about a different approach, one with no chess-specific rules of thumb at all. It plays the correct move in both positions with the same dozen lines of code, and the only chess knowledge it has is the rules of the game and a table saying a queen is worth nine pawns. The approach is called minimax, and with one refinement, alpha-beta pruning, it was the core of every strong chess program from the 1950s until 2017 and is still the core of Stockfish today.

We'll build it from the bottom up. First two pieces of background that everything else leans on: what a game tree is, and how brutally fast it grows. Then the naive engine and its failure, then minimax itself, then the long list of improvements that make it practical. All the code is Python with the python-chess library, which handles the rules (move generation, check, checkmate) so that our code can be about the search and nothing else.

2. Prerequisite: game trees

Start from the initial position of chess. White has 20 legal moves: each of the eight pawns can advance one square or two, which makes 16, and each knight has two squares to jump to, which makes 4 more. Whichever move White picks, we get a new position, and in it Black has, again, 20 legal moves.

Draw the starting position as a dot. Draw one line down from it for each legal move, ending in a new dot for the position that move produces. Then do the same for each of those. The picture we get is the game tree.

Some vocabulary, which is standard and which the rest of the page uses constantly.

  • A node of the tree is a position, including whose turn it is. An edge is a legal move. The children of a position are the positions one move away from it.
  • The root is the position we are thinking about now: the one on the board.
  • A ply is one move by one player, also called a half-move. Chess players say "one move" for a White move plus a Black reply; that is two plies. Programmers count plies because the tree has one level per ply. The depth of a node is the number of plies from the root to it.
  • The branching factor of a node is how many children it has, that is, how many legal moves there are. The starting position has branching factor 20. A typical middlegame position has about 30 to 40, and the usual round figure for chess is 35.
  • A terminal node is a position where the game is over: checkmate, stalemate, or a draw by some rule. It has no children.
  • A leaf is any node at the bottom of the part of the tree we chose to draw. Every terminal node is a leaf; but in the figure above all 400 bottom positions are leaves too, only because we stopped drawing there.

Notice that the levels of the tree alternate. At the root it is White's turn, so the edges going down from it are White's moves. One level down it is Black's turn. This alternation is the whole reason the algorithm we are building has "min" and "max" in its name, as we'll see.

Two properties of chess make this tree picture a complete description of the game. First, there is no hidden information: both players see the whole board, so a node really is everything there is to know. Second, there is no chance: a move leads to exactly one position, never to "one of these, depending on the dice". Games like this are called deterministic games of perfect information. Poker fails the first test and backgammon fails the second, and both need different tools.

Counting the tree in code

The tree is not a data structure we build in memory. It is implicit: given a position, the rules tell us its children. So we walk it with ordinary depth-first recursion, making a move to go down an edge and un-making it to come back up. In python-chess those two operations are board.push(move) and board.pop(), and board.legal_moves lists the edges. Here is a function that counts the nodes at a given depth.

def count_positions(board: chess.Board, plies_left: int) -> int:
    """Count the positions exactly `plies_left` half-moves below `board`."""
    if plies_left == 0:
        return 1
    position_count = 0
    for move in board.legal_moves:
        board.push(move)  # walk down one edge of the tree
        position_count += count_positions(board, plies_left - 1)
        board.pop()  # walk back up
    return position_count

This is the skeleton of everything that follows. Minimax is this same recursion with one change: instead of adding up the counts from the children, it will combine scores from the children.

Problem 2.1 · easy

After 1.e4 (White pushes the king's pawn two squares), how many legal moves does Black have? After 1.e4 e5, how many legal moves does White have? Count by hand, piece by piece.

Solution

After 1.e4 Black's own pieces have not been touched, and the white pawn on e4 doesn't block or attack anything Black can move to, so Black still has the same 20 moves: 16 pawn moves and 4 knight moves.

After 1.e4 e5, count White's moves piece by piece. Seven pawns (a, b, c, d, f, g, h) have 2 moves each: 14. The e4 pawn is blocked by the pawn on e5: 0. The b1 knight goes to a3 or c3: 2. The g1 knight now has e2 as well as f3 and h3: 3. The f1 bishop is free along the diagonal e2, d3, c4, b5, a6: 5. The queen has e2, f3, g4, h5: 4. The king can step to e2: 1. Total \(14 + 2 + 3 + 5 + 4 + 1 = 29\).

Checked with board.legal_moves.count(): 20 and 29. This is why the third number in the table is 8,902 and not \(20^3 = 8000\): the branching factor isn't constant, and it goes up as the pieces come out.

Problem 2.2 · medium

The tree has 8,902 nodes at ply 3. But if you collect the positions at those nodes into a set, the set has only 5,362 elements. How can two different nodes hold the same position? Give a concrete example at ply 3, and explain why there can be no example at ply 2.

Hint

A node is reached by one specific sequence of moves. A position doesn't remember the order in which its pieces got there.

Solution

Two different move orders can produce the same arrangement of pieces. For example 1.e4 e5 2.d4 and 1.d4 e5 2.e4 are different paths down the tree, so they end at different nodes, but the board at the end is identical: white pawns on d4 and e4, a black pawn on e5, Black to move. Arriving at an already-seen position by another route is called a transposition.

At ply 3 White has made two moves, and they can be made in either order. At ply 2 each side has made exactly one move, so there is nothing to reorder: the position after "White plays X, Black plays Y" determines X and Y. That is why all 400 positions at ply 2 are distinct.

So the "game tree" is, strictly speaking, a graph in which paths merge. We will treat it as a tree for most of the page, which means doing some work twice, and in section 19 we'll use a hash table to stop doing that. (At ply 4 it gets worse: 197,281 nodes, 72,078 distinct positions by python-chess's notion of "same position".)

3. Prerequisite: how fast bd grows

The counts above went 20, 400, 8,902, 197,281, 4,865,609. Each is roughly the previous one times 20-something. That's the signature of exponential growth, and since the whole story of chess programming is a fight against this one fact, it's worth a few minutes to get a feel for it.

Take an idealised tree in which every position has exactly \(b\) legal moves (\(b\) for branching factor), and look \(d\) plies ahead (\(d\) for depth). The root has \(b\) children. Each of them has \(b\) children, so there are \(b \cdot b = b^2\) positions at depth 2. Each of those has \(b\) children, so \(b^3\) at depth 3. At depth \(d\):

\[ \text{leaves at depth } d \;=\; \underbrace{b \cdot b \cdots b}_{d \text{ times}} \;=\; b^d . \]

Now put in chess-sized numbers and move the sliders.

Three things to take from this demo.

Each extra ply multiplies the work by \(b\). Going from depth 6 to depth 7 with \(b = 35\) is not "a bit more work"; it is 35 times the work. If depth 6 takes one minute, depth 7 takes thirty-five minutes and depth 8 takes twenty hours.

Speed buys depth only logarithmically. Suppose your machine becomes \(k\) times faster. How many extra plies, call it \(x\), can you search in the same time? The work for \(x\) extra plies is \(b^x\) times bigger, so we need \(b^x = k\). The number \(x\) with this property is by definition the logarithm of \(k\) in base \(b\):

\[ b^x = k \quad\Longleftrightarrow\quad x = \log_b k = \frac{\ln k}{\ln b}. \]

For \(b = 35\) and a machine twice as fast, \(x = \ln 2 / \ln 35 = 0.693 / 3.555 \approx 0.19\) plies. Doubling the speed doesn't even get you a fifth of a ply. This is why the important advances in chess programming were algorithmic: as we'll see, alpha-beta pruning effectively replaces \(b\) by \(\sqrt{b}\), which doubles the reachable depth, something no hardware upgrade does.

The whole game is out of reach, for ever. A game of chess lasts about 40 moves by each side, 80 plies. With about 30 choices per ply, Claude Shannon estimated in 1950 that there are something like \(10^{120}\) possible games. There are around \(10^{80}\) atoms in the observable universe. We will never search chess to the end, so any chess program has to stop its search early and guess. Where it stops, and how it guesses, are the two big design questions.

Detour · the whole tree, not only its last level

We've been counting only the leaves, \(b^d\). A search also visits everything above them: \(1 + b + b^2 + \dots + b^d\) nodes. Is it sloppy to ignore the rest? No, and seeing why gives a rule of thumb we'll use later: in an exponential tree, the last level is almost everything.

Call the total \(S = 1 + b + b^2 + \dots + b^d\). Multiply both sides by \(b\): every term moves one place to the right, so \(bS = b + b^2 + \dots + b^d + b^{d+1}\). Subtract the first equation from the second. Every term from \(b\) to \(b^d\) appears in both and cancels, leaving \(bS - S = b^{d+1} - 1\). The left side is \((b-1)S\), so

\[ S = \frac{b^{d+1} - 1}{b - 1}. \]

For large \(b^{d+1}\) the "\(-1\)" is negligible, so \(S \approx b^{d+1}/(b-1) = b^d \cdot \frac{b}{b-1}\). With \(b = 35\) that factor is \(35/34 \approx 1.03\): all the levels above the leaves add up to only 3% on top of the leaves. So counting leaves is counting the work.

Problem 3.1 · easy

With \(b = 35\), how many leaves are there at depth 4? At depth 8? (You can use the fact that the second is the square of the first.)

Solution

\(35^2 = 1225\), and \(35^4 = 1225^2 = 1{,}500{,}625\): about a million and a half. Then \(35^8 = (35^4)^2 \approx (1.5 \times 10^6)^2 = 2.25 \times 10^{12}\) (exactly 2,251,875,390,625). Doubling the depth squares the leaf count. Keep that sentence in mind for the alpha-beta section, where we'll run it backwards.

Problem 3.2 · medium

The Python engine we are about to write evaluates about 18,500 leaves per second on my machine. With \(b = 35\) and one minute to think, what is the deepest full search it can finish? What if we rewrote it in C and it became 1,000 times faster?

Solution

In one minute it evaluates \(18{,}500 \times 60 = 1{,}110{,}000\) leaves. Depth 3 needs \(35^3 = 42{,}875\), which fits. Depth 4 needs 1,500,625, which doesn't. So: depth 3.

A 1,000-fold speed-up buys \(\log_{35} 1000 = \ln 1000 / \ln 35 = 6.908 / 3.555 \approx 1.94\) extra plies. Check directly: the budget becomes \(1.11 \times 10^9\) leaves; depth 5 needs \(35^5 \approx 5.3 \times 10^7\), fine; depth 6 needs \(35^6 \approx 1.8 \times 10^9\), too many. So depth 5: two more plies for a thousand times the speed. The common wrong answer is to expect a thousand times the speed to give something like a thousand times the depth.

Problem 3.3 · medium

Use the formula from the detour to compute what fraction of all the nodes in a tree with \(b = 2\), \(d = 10\) are leaves. Compare with \(b = 35\). What does this say about binary trees versus chess trees?

Solution

For \(b = 2\), \(d = 10\): leaves are \(2^{10} = 1024\) and the total is \((2^{11} - 1)/(2 - 1) = 2047\), so the fraction is \(1024/2047 \approx 0.50\). Half the nodes are leaves, half are internal.

In general the fraction is about \(b^d / \bigl(b^d \cdot \tfrac{b}{b-1}\bigr) = \tfrac{b-1}{b}\). For \(b = 35\) that is \(34/35 \approx 0.97\). The wider the tree, the more the bottom level dominates. For chess, whatever we do at the leaves (which will be: call the evaluation function) is where nearly all the running time goes.

4. The problem, stated

With the vocabulary in place we can say what we want precisely.

The problem

Given a chess position, choose a move for the side whose turn it is. We are allowed to look at the game tree below the position, but only a tiny part of it: a few plies deep. The opponent is not our friend: after our move, they will choose their best move, not the one we were hoping for.

The last sentence is the heart of it. When we played through position A, the phrase that exposed the blunder was "whichever of them takes back". We didn't evaluate the queen capture by the position right after it; we evaluated it by the position after Black's best reply. And in position B, the queen sacrifice was good because of what happens after Black's only reply.

To make "best" mean something to a computer, we need to turn positions into numbers. We'll need exactly one ingredient that knows about chess:

Definition · evaluation function

An evaluation function takes a position and, without looking ahead at all, returns a number saying how good the position looks. We fix the convention once and for all: positive means good for White, negative means good for Black, zero means level. So White wants the number as high as possible and Black wants it as low as possible.

The simplest evaluation function that isn't useless is the one every beginner is taught: count the pieces. A pawn is worth 1, a knight or bishop 3, a rook 5, a queen 9. To avoid fractions later, programs traditionally count in hundredths of a pawn, centipawns, so a pawn is 100 and a queen is 900.

PIECE_VALUE: dict[chess.PieceType, int] = {
    chess.PAWN: 100,
    chess.KNIGHT: 300,
    chess.BISHOP: 300,
    chess.ROOK: 500,
    chess.QUEEN: 900,
    chess.KING: 0,  # both sides always have exactly one king
}


def material(board: chess.Board) -> int:
    """Material balance in centipawns. Positive means White is ahead."""
    balance = 0
    for piece_type, piece_value in PIECE_VALUE.items():
        white_count = len(board.pieces(piece_type, chess.WHITE))
        black_count = len(board.pieces(piece_type, chess.BLACK))
        balance += piece_value * (white_count - black_count)
    return balance
import chess
from engine import material

start = chess.Board()
print("starting position:", material(start))

queen_up = chess.Board("rnb1kbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR w KQkq - 0 1")
print("Black has no queen:", material(queen_up))

rook_for_knight = chess.Board("1nbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/R1BQKBNR w Kk - 0 1")
print("White lost a knight, Black a rook:", material(rook_for_knight))
output
starting position: 0
Black has no queen: 900
White lost a knight, Black a rook: 200

In the last position White gave up a knight (300) and Black gave up a rook (500), so White is 200 centipawns, two pawns, ahead.

This function is blind to nearly everything a chess player cares about: it can't see threats, or a king about to be mated, or a knight stuck in the corner. That's fine. The surprise of this page is how well a blind evaluation function plays once a search is put on top of it. We'll improve the evaluation a little in section 14, but all the intelligence will come from the search.

5. The naive engine: grab what you can

We have a function that scores positions. The most direct way to use it to choose a move: try each legal move, score the position it leads to, and play the move with the best score. This looks exactly one ply ahead.

def greedy_move(board: chess.Board, evaluate: Evaluator) -> chess.Move:
    """Play the move whose resulting position looks best right away."""
    side_sign = 1 if board.turn == chess.WHITE else -1
    best_move: chess.Move | None = None
    best_value = -10**9
    for move in board.legal_moves:
        board.push(move)
        value = side_sign * evaluate(board)  # from the mover's point of view
        board.pop()
        if value > best_value:
            best_move, best_value = move, value
    assert best_move is not None, "no legal moves"
    return best_move

One detail deserves a comment because it will come back: side_sign. The evaluation is always from White's point of view. If it's White's turn, the best move is the one with the highest evaluation; if it's Black's turn, the lowest. Multiplying by \(-1\) for Black turns "lowest" into "highest", so one comparison serves both colours.

Let it play position A, for both sides.

import chess
from engine import greedy_move, material

board = chess.Board("3r2k1/pp3pp1/2p2n1p/3p4/8/8/PPP2PPP/3Q2K1 w - - 0 1")
print("material before:", material(board))

white_move = greedy_move(board, material)
print("White (greedy) plays:", board.san(white_move))
board.push(white_move)
print("material after White's move:", material(board))

black_move = greedy_move(board, material)
print("Black (greedy) plays:", board.san(black_move))
board.push(black_move)
print("material after Black's reply:", material(board))
output
material before: 0
White (greedy) plays: Qxd5
material after White's move: 100
Black (greedy) plays: Rxd5
material after Black's reply: -800

White took the pawn and was pleased: +100. Then Black took the queen: −800, which is +100 for the pawn minus 900 for the queen. The greedy engine walked straight into it, as promised.

6. Diagnosis

What exactly went wrong? It's tempting to say "it didn't look far enough ahead", but that's not specific enough to fix anything. Look at what the greedy engine computes: for each of its moves, the evaluation of the position immediately after that move. That position is one in which the opponent is about to move. The greedy engine scores it as if the game ended there, as if the opponent would pass.

The honest score of "I play Qxd5" is not the evaluation right after Qxd5. It is the evaluation after Qxd5 and Black's reply. But Black has several replies, leading to different numbers. Which one do we use? Not the average, and not the one we'd like. Black chooses, and Black wants the number low, so:

\[ \text{value of my move} \;=\; \min_{\text{Black's replies}} \;\text{evaluation after the reply}. \]

And then among my moves I pick the one where this value is highest. The best of the worst cases: a maximum of minimums. The demo below computes exactly that for every one of White's 27 moves in position A, for several look-ahead depths. (For depths 3 and 4 it uses the full algorithm we haven't written yet; treat those as a preview.)

Problem 6.1 · easy

At depth 2 the demo gives Qxd5 the value −8.00, and gives Qh5 and Qg4 the value −9.00. Explain each number from the board.

Solution

After Qxd5 Black's best reply is to capture the queen (with rook, knight or pawn, it makes no difference to the count). White has won a pawn, +1, and lost a queen, −9: total −8.

On h5 or g4 the queen is attacked by the knight on f6 and takes nothing on the way. Black plays Nxh5 or Nxg4: White has lost a queen for nothing, −9.

Problem 6.2 · medium

Would a depth-2 search (my move, then the opponent's best reply) find the queen sacrifice Qd8+ in position B? What score would it give that move?

Solution

No. After 1.Qd8+ Black's only legal reply is Rxd8, and a depth-2 search stops right there and counts: White is a queen down, −900. The point of the sacrifice, 2.Rxd8 mate, is White's second move, which is ply 3. So depth 2 scores Qd8+ as −9.00, the worst move on the board.

The lesson: two plies is not a magic number. Depth 1 was too shallow for position A; depth 2 is too shallow for position B. We need a method that works for any depth, and we should expect that whatever depth we pick, some position will need one more.

7. Warm-up: mate in two

Before dealing with numbers, let's solve an easier version of the problem in which every position has only two possible verdicts: "White has checkmated" or "not". This is the classic chess puzzle: White to move and mate in two. It contains the whole structure of minimax with the arithmetic removed, and since you're comfortable with logic, it's the shortest path to the idea.

Start with mate in one. White can mate in one if

\[ \exists\, \textcolor{#f4d35e}{\text{White move}}: \ \text{the resulting position is checkmate.} \]

That's a loop over White's moves that returns true as soon as one of them works. Now mate in two. Say it slowly in English: White can mate in two if there is a White move such that for every Black reply, there is a White move that gives checkmate.

\[ \exists\, \textcolor{#f4d35e}{m_1}\ \ \forall\, \textcolor{#5cc8e6}{r_1}\ \ \exists\, \textcolor{#f4d35e}{m_2}: \ \text{checkmate.} \]

The quantifiers alternate because the players alternate. Where it's my turn I get to choose, so I need only one good option: \(\exists\). Where it's the opponent's turn they choose, so I need all of their options to be good for me: \(\forall\). Here is that formula laid over the game tree of position B.

Translating the formula into code is mechanical: \(\exists\) becomes a loop that returns True at the first success, \(\forall\) becomes a loop that returns False at the first failure. The two functions call each other, one level of the tree each.

import chess


def attacker_can_force_mate(board: chess.Board, attacker_moves_left: int) -> bool:
    """Attacker to move. Is there SOME move after which the defender is lost?"""
    for move in board.legal_moves:
        board.push(move)
        defender_is_lost = defender_cannot_escape(board, attacker_moves_left - 1)
        board.pop()
        if defender_is_lost:
            return True  # one good move is enough
    return False


def defender_cannot_escape(board: chess.Board, attacker_moves_left: int) -> bool:
    """Defender to move. Does EVERY move still lose?"""
    if board.is_checkmate():
        return True
    if board.is_stalemate() or attacker_moves_left == 0:
        return False
    for move in board.legal_moves:
        board.push(move)
        still_lost = attacker_can_force_mate(board, attacker_moves_left)
        board.pop()
        if not still_lost:
            return False  # one escape is enough
    return True


back_rank = chess.Board("r5k1/5ppp/8/8/8/3Q4/1q3PPP/3R2K1 w - - 0 1")
print("mate in 1:", attacker_can_force_mate(back_rank, 1))
print("mate in 2:", attacker_can_force_mate(back_rank, 2))

winning_first_moves: list[str] = []
for move in back_rank.legal_moves:
    name = back_rank.san(move)
    back_rank.push(move)
    if defender_cannot_escape(back_rank, 1):
        winning_first_moves.append(name)
    back_rank.pop()
print("first moves that force it:", winning_first_moves)
output
mate in 1: False
mate in 2: True
first moves that force it: ['Qd8+']

The program found the queen sacrifice, and proved it's the only first move that works, without being told that sacrifices exist. It didn't need to be told: it never looked at the material at all. It only asked who ends up mated.

Edge case · "for every" over nothing

If the defender has no legal moves, the \(\forall\) loop runs zero times and falls through to return True: "every one of Black's zero moves loses". That's correct logic and wrong chess, unless Black is actually in check. No legal moves and not in check is stalemate, a draw. That's why defender_cannot_escape tests for checkmate and stalemate before the loop. Every search function on this page has the same two lines at the top for the same reason.

Problem 7.1 · easy

Write the quantifier formula for "White to move and mate in three". How many levels of the tree does it reach?

Solution

\(\exists m_1\ \forall r_1\ \exists m_2\ \forall r_2\ \exists m_3\): checkmate. Three White moves and two Black replies in between: 5 plies. In general mate in \(n\) is \(2n - 1\) plies, which is why back_rank needed depth 3 in the engine output we'll see below.

Problem 7.2 · medium

Negate the mate-in-two formula, pushing the negation all the way inside. Read the result as a statement about Black. What have you just proved about every position?

Solution

Negation flips each quantifier: \(\lnot(\exists m_1 \forall r_1 \exists m_2: \text{mate}) = \forall m_1\ \exists r_1\ \forall m_2: \text{not mate}\). In words: whatever White plays, Black has a reply after which no White move mates. That is "Black can survive two moves".

Since a statement or its negation is always true, in every position exactly one of these holds: White can force mate in two, or Black can prevent it. There is no third case in which it "depends on how they play". This is a tiny instance of the theorem that a finite game of perfect information is determined, which we'll prove with numbers in section 12.

8. Key insight: from true/false to numbers

The mate-in-two solver is perfect on mate-in-two puzzles and useless on everything else: in position A it would answer "no forced mate" for every move and have no opinion on whether to take the pawn. Real positions need shades: a pawn up, a queen down. We already have a function producing shades, material. So keep the shape of the solver and replace its true/false leaves with numbers. What do \(\exists\) and \(\forall\) turn into?

Write false as 0 and true as 1 and look at what the quantifiers do to those numbers. "There exists a child that is 1" is 1 exactly when the largest child is 1. "Every child is 1" is 1 exactly when the smallest child is 1.

\[ \exists \;\longrightarrow\; \max \qquad\qquad \forall \;\longrightarrow\; \min \]

And max and min, unlike \(\exists\) and \(\forall\), make sense for any numbers at all, not just 0 and 1. So here is the generalisation. At a position where White is to move, White will choose the child with the largest value, so the position is worth the max of its children. Where Black is to move, Black will choose the smallest, so the position is worth the min of its children. And at the bottom, where we stop looking, we ask the evaluation function.

Definition · minimax value

The minimax value \(v(p)\) of a position \(p\) in a game tree is

\[ v(p) = \begin{cases} \text{evaluate}(p) & \text{if } p \text{ is a leaf,} \\[4pt] \textcolor{#f4d35e}{\max}\ \{\, v(c) : c \text{ a child of } p \,\} & \text{if } \textcolor{#f4d35e}{\text{White}} \text{ is to move in } p, \\[4pt] \textcolor{#5cc8e6}{\min}\ \{\, v(c) : c \text{ a child of } p \,\} & \text{if } \textcolor{#5cc8e6}{\text{Black}} \text{ is to move in } p. \end{cases} \]

It is the evaluation of the leaf the game will reach if both sides play as well as possible, as far as this tree can tell. The move to play at the root is the one leading to the child whose value equals the root's.

The names: White is the maximising player, or just MAX, and Black is the minimising player, MIN. The procedure of computing \(v\) at the root by this recursion is minimax search.

Our earlier attempts are special cases. The greedy engine is minimax on a tree one ply deep. The formula from the diagnosis section, max over my moves of min over replies, is minimax on a tree two plies deep. The mate solver is minimax with leaves in \(\{0, 1\}\).

9. Walking a tree by hand

The definition is three lines, but it's worth watching it run, because the order in which the values appear is what the alpha-beta trick will exploit later. Below is a small made-up tree: White to move at the root with three moves, Black has two replies to each, White has two answers to each reply, and then we stop and evaluate. The twelve leaf numbers are evaluations in pawns from White's point of view; they're shown dimmed until the search actually reaches them.

The search is depth-first, exactly like count_positions: it dives to the leftmost leaf, and a node gets its final value only when all of its children have reported back.

Three things to notice in the finished tree.

The root is worth +7, yet the largest leaf in the tree is +9. White can't get the +9: it sits below a Black node, and Black, choosing between a branch worth +5 and one worth +9, takes the +5. The minimax value is not "the best thing that could happen". It's the best thing White can force.

Every one of the 12 leaves was evaluated, including leaves under the middle move, which turned out to be terrible. Remember the middle subtree; we'll come back for it.

A node's value while the search is still inside it is a bound, not yet a value. When a White node has seen one child worth +3, it knows it is worth at least +3. When a Black node has seen one child worth +5, it knows it is worth at most +5. This remark looks innocent, and it's the entire idea behind alpha-beta.

Problem 9.1 · easy

Compute the minimax value of the root, and say which move White should play (left, middle or right).

Solution

The middle level is Black's, so each of those nodes is the minimum of its leaves: \(\min(4, -2, 7) = -2\), \(\min(1, 9) = 1\), \(\min(5, 6, 3) = 3\). The root is White's: \(\max(-2, 1, 3) = 3\). White plays the right move and the value is +3.

The common wrong answer is the middle move "because it has the +9", or the left "because it has +7 and +4". The right move has the least exciting leaves and is the best, because its worst case is the best worst case.

Problem 9.2 · easy

Same tree and same leaf numbers, but now it is Black to move at the root (so the middle level is White's). What is the value and which move does Black play?

Solution

Now the middle nodes take the maximum: \(\max(4, -2, 7) = 7\), \(\max(1, 9) = 9\), \(\max(5, 6, 3) = 6\). The root takes the minimum: \(\min(7, 9, 6) = 6\). Black plays the right move, value +6.

Same numbers at the bottom, different value at the top (+6 instead of +3): having the last word in the tree is worth something.

Problem 9.3 · medium

In the tree of problem 9.1, White plays the right move, expecting +3. Black then blunders and picks the leaf worth +6 instead of +3. Did minimax give White wrong information? More generally: if the opponent doesn't play the minimax-best replies, can White end up with less than the root's minimax value?

Solution

No on both counts. The value +3 was the minimum over Black's replies, so every Black reply gives White at least +3; the blunder gave +6, which is more. If White keeps choosing maximising moves, the result can never drop below the root value, whatever Black does. The minimax value is a guarantee, a floor, not a prediction.

There is a subtler point. Against a weak opponent, the minimax move might not be the move that wins the most: the middle move, with its +9, is a "trap" that pays off if Black errs and costs if Black doesn't. Minimax never sets traps. It assumes the opponent sees everything it sees.

10. The algorithm in Python

The definition of \(v(p)\) is already a recursive function; we only have to type it in. A leaf, for us, is one of two things: a position where the game is over, or a position where we've run out of depth. The parameter depth counts how many more plies we're allowed to look ahead, and each recursive call spends one.

MATE_SCORE = 100_000  # far above any material balance


def minimax_plain(board: chess.Board, depth: int, evaluate: Evaluator) -> int:
    """Value of `board` from White's side, looking `depth` plies ahead."""
    if board.is_checkmate():
        # The side to move is the one that got mated.
        return -MATE_SCORE if board.turn == chess.WHITE else MATE_SCORE
    if board.is_stalemate() or board.is_insufficient_material():
        return 0
    if depth == 0:
        return evaluate(board)

    child_values: list[int] = []
    for move in board.legal_moves:
        board.push(move)
        child_values.append(minimax_plain(board, depth - 1, evaluate))
        board.pop()

    if board.turn == chess.WHITE:
        return max(child_values)  # White picks the child that is best for White
    return min(child_values)  # Black picks the child that is worst for White

Compare with count_positions: the same loop, the same push and pop, the same depth - 1. The only new things are the terminal cases at the top and the max/min at the bottom. A checkmate is scored as a huge number, far bigger than any material count, with the sign depending on who got mated. Stalemate and bare kings are draws, worth 0.

That function returns a value. To play chess we need a move, so at the root we run the loop one more time ourselves and remember which move produced the best value.

Search = Callable[[chess.Board, int, Evaluator], int]


def best_move(
    board: chess.Board, depth: int, evaluate: Evaluator, search: Search = minimax
) -> tuple[chess.Move, int]:
    """Try every move at the root; return the best one and its value for White."""
    side_sign = 1 if board.turn == chess.WHITE else -1
    chosen_move: chess.Move | None = None
    chosen_value = 0
    for move in board.legal_moves:
        board.push(move)
        value = search(board, depth - 1, evaluate)  # one ply is already spent
        board.pop()
        if chosen_move is None or side_sign * value > side_sign * chosen_value:
            chosen_move, chosen_value = move, value
    assert chosen_move is not None, "no legal moves"
    return chosen_move, chosen_value

Problem 10.1 · medium · predict

At depth 2, position B gets the value −100: the search believes White is about to lose a pawn. But White isn't losing a pawn in any sensible line. Which Black capture is the search worried about, and why is it wrong?

Hint

Which black piece is anywhere near a white pawn? What does the search see after that capture, and what does it not see?

Solution

After any quiet White move such as Qd7, Black can play Qxf2+, taking the pawn on f2. The depth-2 search stops immediately after that capture and counts: Black is a pawn up, −100. What it doesn't see is ply 3: the pawn was protected by the king, Kxf2 wins the black queen, and the true result of the capture is +800 for White.

So at depth 2 the search makes, on Black's behalf, the same mistake the greedy engine made in position A: it assumes the last capture in the line goes unpunished. Whoever moves last in the tree gets to make a capture "for free". This is called the horizon effect, it afflicts every fixed-depth search, and section 18 is about curing it.

Problem 10.2 · easy · find the bug

Someone writes the loop of minimax_plain like this. What goes wrong?

    for move in board.legal_moves:
        board.push(move)
        child_values.append(minimax_plain(board, depth - 1, evaluate))
Solution

There's no board.pop(). After the first child returns, the board is still in the child position, so the second "sibling" move is not played from the parent position. python-chess will play it anyway (push doesn't check legality), producing nonsense positions: the same side moving twice in a row, pieces teleporting. Worse, the iterator board.legal_moves is being consumed while the board it reads from changes underneath it. Every push needs its pop; this is the make/unmake discipline of backtracking, and it's the most common bug in a first chess engine.

11. Mate scores

There's a small flaw in minimax_plain, and it produces a behaviour that looks almost like a sense of humour. Take this position, where White can mate at once with Qa8.

output
depth 1: minimax_plain Qa8#  +100000   minimax Qa8#  +100000
depth 3: minimax_plain Kf7   +100000   minimax Qa8#  +100002
depth 5: minimax_plain Kf7   +100000   minimax Qa8#  +100004

At depth 1, minimax_plain plays the mate. At depth 3 and 5, with more time to think, it plays Kf7 instead, a move that mates two plies later. Why? Because it scores every checkmate as +100000 regardless of when it happens. Qa8# is worth +100000; Kf7, which forces mate in two, is also worth +100000; it's a tie, and ties go to whichever move was generated first. A program like this can fail to win a won game: on each move it finds a move that still mates "eventually" and never gets around to it.

The fix is to make a mate that comes sooner worth slightly more. When the search discovers a checkmate, depth tells it how many plies of its budget are still unspent; the more are left, the earlier in the line the mate happened. So we add depth to the mate score.

def minimax(board: chess.Board, depth: int, evaluate: Evaluator) -> int:
    """Like minimax_plain, but a mate found sooner scores more than one found later."""
    if board.is_checkmate():
        # `depth` plies were still unused when the mate appeared: more unused = sooner.
        mate_value = MATE_SCORE + depth
        return -mate_value if board.turn == chess.WHITE else mate_value
    if board.is_stalemate() or board.is_insufficient_material():
        return 0
    if depth == 0:
        return evaluate(board)

    child_values: list[int] = []
    for move in board.legal_moves:
        board.push(move)
        child_values.append(minimax(board, depth - 1, evaluate))
        board.pop()
    return max(child_values) if board.turn == chess.WHITE else min(child_values)

Now Qa8# scores +100002 at depth 3 (mate found with 2 plies to spare) and Kf7 scores +100000, and the engine takes the quick win. The same bonus makes the losing side prefer the slowest loss, which is also what we want: it makes the opponent prove it.

Problem 11.1 · medium

With the fixed minimax, best_move(board, 5, material) reports the value +100004 at the root for the position above. A chess GUI would rather display "mate in 1". Give a formula that converts a mate value \(V \ge 100000\) returned by a depth-\(D\) search from the root into "mate in \(n\) moves" for the side to move at the root.

Solution

The mate value is \(100000 + (\text{depth remaining at the mated node})\). If the mate happens \(k\) plies below the root, the remaining depth there is \(D - k\), so \(V = 100000 + D - k\) and \(k = D - (V - 100000)\). Here \(k = 5 - 4 = 1\) ply.

The winner makes plies 1, 3, 5, …, so a mate delivered on ply \(k\) (odd) is the winner's move number \(n = (k + 1)/2\). With \(k = 1\): mate in 1. For Kf7 at depth 5: value 100002, \(k = 3\), mate in 2. (Note best_move calls the search with depth - 1 after making the root move, which is consistent: one ply spent, one less remaining.)

12. Why the minimax value is the right number

We've been saying that \(v(\text{root})\) is "what happens when both sides play their best". That can sound circular: best according to what? Here is the precise statement and its proof. It's short, and it's the same induction you'd use for any recursive function on trees.

Fix a finite tree with a number at each leaf. A strategy for White is a rule that picks one move at every White node; similarly for Black.

Theorem

Let \(v\) be the minimax value. Then:

(a) White has a strategy that reaches a leaf of value at least \(v(\text{root})\), whatever Black does.

(b) Black has a strategy that reaches a leaf of value at most \(v(\text{root})\), whatever White does.

Together these pin the number down from both sides. White can't hope for more than \(v\), because of (b); Black can't hope for less, because of (a). If both use these strategies, the game ends at a leaf of value exactly \(v(\text{root})\).

Proof of (a), by induction on the height of a node \(p\) (the number of plies from \(p\) down to its deepest leaf). We prove the claim for the subtree under every node \(p\), not just the root.

Height 0. Then \(p\) is a leaf. The game is already at a leaf of value \(v(p)\). Nothing to do.

Height \(h > 0\), White to move at \(p\). By definition \(v(p)\) is the maximum of the children's values, so there is a child \(c^*\) with \(v(c^*) = v(p)\). White's strategy: move to \(c^*\). The child has height less than \(h\), so by the induction hypothesis White has a strategy from \(c^*\) that guarantees at least \(v(c^*) = v(p)\). Play that from there on.

Height \(h > 0\), Black to move at \(p\). By definition \(v(p)\) is the minimum of the children's values, which means every child \(c\) satisfies \(v(c) \ge v(p)\). Black moves to some child \(c\); we don't control which. But whichever it is, by the induction hypothesis White has a strategy from \(c\) guaranteeing at least \(v(c)\), and \(v(c) \ge v(p)\). So White is guaranteed at least \(v(p)\).

That covers every node, so in particular the root. Part (b) is the same proof with the roles of the players, max and min, and \(\ge\) and \(\le\) swapped. \(\blacksquare\)

Look at how the two cases use the definition. At White's node we used that a maximum is attained by some child: White picks it. At Black's node we used that a minimum is a lower bound on all children: Black can't do damage. The quantifiers \(\exists\) and \(\forall\) from the warm-up are still there, hiding inside max and min.

What the theorem does and doesn't say

If the tree were the complete game of chess with leaves worth +1 (White wins), 0 (draw) and −1 (Black wins), the theorem would say that chess has a definite value: either White can force a win, or Black can, or both can force at least a draw. That is true, it was first shown by Ernst Zermelo in 1913, and nobody knows which of the three it is.

Our tree is cut off after a few plies and its leaves hold guesses from an evaluation function. The theorem still holds, but about that tree: minimax plays perfectly in the game "reach the best-looking position \(d\) plies from now". It's exactly as right as its leaves. A deeper search is stronger not because minimax gets more correct, but because the guesses are made later, closer to the truth.

Problem 12.1 · medium · prove

Suppose we add 5 to every leaf of a tree. Prove that the minimax value of the root goes up by exactly 5 and the best move doesn't change. Then decide: is the same true if we multiply every leaf by −1?

Solution

Induction on height, with the claim "every node's value goes up by 5". Leaves: by assumption. Inner White node: \(\max(v(c_1) + 5, \dots, v(c_k) + 5) = \max(v(c_1), \dots, v(c_k)) + 5\), because adding a constant to every number doesn't change which is largest. Same for min. Since every child of the root moved by the same amount, the child with the best value is the same child: same move. The same argument works for any strictly increasing transformation of the leaves, for instance doubling them. Only the order of evaluations matters to minimax, not their size.

Multiplying by −1 reverses the order, and \(\max(-a, -b) = -\min(a, b)\), not \(-\max(a, b)\). So no: the max nodes would start computing (minus) minimums. The tree's value is not simply negated… unless you also swap which player is max and which is min. That observation is the whole content of the next section.

13. Negamax: one function instead of two

Our minimax has an if on whose turn it is, to choose between max and min. With only max and min it's a one-line nuisance. But the alpha-beta version coming up needs two whole loops, one per player, mirror images of each other, and mirror-image code is where sign bugs live. There's a standard way to fold the two cases into one, and nearly every real engine uses it.

The observation: Black minimising White's score is the same as Black maximising Black's own score, if we agree that Black's score is the negative of White's. Chess is zero-sum: whatever is good for one side is exactly that bad for the other. In symbols, for any numbers \(a\) and \(b\),

\[ \min(a, b) = -\max(-a, -b). \]

(Check: negating flips the order, so the larger of \(-a, -b\) is the negative of the smaller of \(a, b\).)

So change the convention for what a search function returns. Instead of "the value for White", let it return the value for whoever is to move in that position. Call this \(n(p)\). It's related to the old value by a sign: \(n(p) = v(p)\) when White is to move, \(n(p) = -v(p)\) when Black is.

Now work out the recursion for \(n\). Take a position \(p\) with White to move. Its children have Black to move, so for each child \(n(c) = -v(c)\), that is, \(v(c) = -n(c)\). Then

\[ n(p) = v(p) = \max_c v(c) = \max_c \bigl(-n(c)\bigr). \]

Take instead a position with Black to move. Its children have White to move, so \(v(c) = n(c)\). Then, using the identity above in the middle step,

\[ n(p) = -v(p) = -\min_c v(c) = \max_c \bigl(-v(c)\bigr) = \max_c \bigl(-n(c)\bigr). \]

The same formula in both cases. Everyone maximises; the value passed up from a child is negated on the way, because my opponent's gain is my loss.

Negamax \[ n(p) = \max_{c \text{ child of } p} \bigl(-\,n(c)\bigr), \qquad n(\text{leaf}) = \pm\,\text{evaluate}(\text{leaf}) \]

with the sign at the leaf being \(+\) if White is to move there and \(-\) if Black is.

INFINITY = 10**9


def negamax(board: chess.Board, depth: int, evaluate: Evaluator) -> int:
    """Value of `board` from the side to move's point of view."""
    if board.is_checkmate():
        return -(MATE_SCORE + depth)  # I am the one who is mated
    if board.is_stalemate() or board.is_insufficient_material():
        return 0
    if depth == 0:
        side_sign = 1 if board.turn == chess.WHITE else -1
        return side_sign * evaluate(board)

    best_value = -INFINITY
    for move in board.legal_moves:
        board.push(move)
        # The child is scored from the opponent's side, so flip its sign.
        best_value = max(best_value, -negamax(board, depth - 1, evaluate))
        board.pop()
    return best_value

With material, it plays 1.Nh3, a move no chess player would choose, and reports a value of 0. From its point of view all 20 first moves are identical: nobody can win material within three plies, so every leaf is 0, so everything ties, and Nh3 is simply the first move python-chess generates. Minimax can only tell moves apart if the evaluation function tells leaves apart.

The cheapest improvement is to pay a small bonus for putting pieces on squares where they are usually useful. Knights and bishops are stronger near the centre, where they reach more squares; pawns are worth more as they advance, and central pawns control important squares. Real engines store such bonuses as one 8×8 table per piece type, called piece-square tables. To keep ours short, we compute the bonuses from a formula instead of typing in 384 numbers.

def center_distance(square: chess.Square) -> int:
    """0 for the four centre squares, 3 for the rim of the board."""
    file_distance = max(3 - chess.square_file(square), chess.square_file(square) - 4)
    rank_distance = max(3 - chess.square_rank(square), chess.square_rank(square) - 4)
    return max(file_distance, rank_distance)


def placement(board: chess.Board, color: chess.Color) -> int:
    """A small bonus for putting pieces where they usually belong."""
    bonus = 0
    for piece_type in (chess.KNIGHT, chess.BISHOP):
        for square in board.pieces(piece_type, color):
            bonus += 10 * (3 - center_distance(square))  # minor pieces like the centre
    for square in board.pieces(chess.PAWN, color):
        rank = chess.square_rank(square)
        ranks_advanced = rank - 1 if color == chess.WHITE else 6 - rank
        bonus += 5 * ranks_advanced  # pawns like to advance...
        if center_distance(square) == 0:
            bonus += 15  # ...and to stand in the centre
    return bonus


def evaluate(board: chess.Board) -> int:
    """Material plus piece placement, in centipawns, from White's side."""
    return material(board) + placement(board, chess.WHITE) - placement(board, chess.BLACK)

The bonuses are deliberately small next to a pawn's 100: we want the engine to prefer a centralised knight, but never to give up a pawn for it. With this evaluation the engine opens 1.e4, since the pawn advances two ranks (+10) and lands on a central square (+15), which is the +25 in the output. At depth 2 the value is 0 because Black replies with the same idea and the bonuses cancel.

This is still a crude function. Serious hand-written evaluations add terms for pawn structure, king safety, piece mobility, rooks on open files, the bishop pair, and a hundred other things, each with a weight tuned by playing millions of games. Since 2020 the top engines have replaced all of that with a small neural network (see section 24). For this page the function above is enough: everything from here on is about the search, and works with any evaluation you plug in.

The division of labour

The evaluation function handles what is static: things that are true of a position and will stay true for a while (material, structure). The search handles what is dynamic: threats, captures, combinations, anything that changes from one ply to the next. A static evaluation that tries to judge tactics will be wrong; a search with nothing static to aim for will be aimless.

Solution

The knight on g1 was on the rim: center_distance is 3 (the rank distance is \(3 - 0 = 3\)), bonus \(10 \cdot (3 - 3) = 0\). On f3: file f has index 5, so the file distance is \(\max(3 - 5,\ 5 - 4) = 1\); rank 3 has index 2, so the rank distance is \(\max(3 - 2,\ 2 - 4) = 1\). 15. Complexity

How much work is minimax? It visits every node of the tree down to depth \(d\), and from section 3 we know that for branching factor \(b\) nearly all of those are the \(b^d\) leaves.

  • Time: \(\Theta(b^d)\) evaluations. Exponential in the depth.
  • Memory: \(\Theta(d)\). The search is depth-first, so at any moment it holds only the current path from the root: \(d\) moves on the board's undo stack and \(d\) stack frames. Memory is never the problem; time always is.

Here is the real thing, measured on a quiet opening position with 39 legal moves.

import time

import chess
from engine import evaluate, negamax, CountingEvaluator

board = chess.Board("r1bqk2r/ppp2ppp/2np1n2/2b1p3/2B1P3/2PP1N2/PP3PPP/RNBQK2R w KQkq - 0 6")
counter = CountingEvaluator(evaluate)
started = time.perf_counter()
negamax(board, 3, counter)
elapsed = time.perf_counter() - started
print(f"{counter.call_count:,} leaves in {elapsed:.2f} s = {counter.call_count / elapsed:,.0f} leaves per second")
output
57,088 leaves in 3.07 s = 18,572 leaves per second

About 18,500 leaves a second. (Python and python-chess are slow for this kind of work; an engine in C++ or Rust is easily a thousand times faster, which by problem 3.2 is worth about two plies.) At this speed depth 4, about 2.2 million leaves in this position, takes two minutes, and depth 6 would take two days. And a search of 6 plies, three moves by each side, is still shallow: club players routinely calculate forcing lines longer than that.

So plain minimax is correct and hopeless. It spends almost all of its time on positions that cannot possibly matter, like the eleven sensible continuations after you've hung your queen. The next section is about not doing that.

16. Alpha-beta pruning

Go back to position A and think about how you rejected Qxd5. You saw that the rook takes the queen, and you stopped. You did not go on to ask whether taking with the knight would be even better for Black, or whether taking with the pawn would be better still. One refutation was enough: the move was already worse than the alternatives, and learning exactly how much worse would change nothing.

Minimax doesn't stop. To compute the value of Qxd5 it dutifully takes the minimum over all of Black's replies. That's wasted work, and the mate-in-two solver already showed us the cure: its loops returned early, the \(\exists\) loop at the first success and the \(\forall\) loop at the first failure. When we went from true/false to numbers we lost the early exit, because a max over numbers seems to need every number. The insight of alpha-beta is that it doesn't, as long as we remember what we already have elsewhere in the tree.

The argument on our example tree

Here is the tree from the walkthrough again, at the moment when the left move has been fully searched and found to be worth +5, and the search has just looked at the first reply to the middle move.

Read the situation in the figure in plain words. White, at the root, already has a move in hand worth +5. Now White is examining the middle move. Black's first reply to it leads to a position worth +2. Black may have even better replies, but Black certainly has this one, so the middle move is worth at most +2 to White. And +2 is less than the +5 White already has. So White will not play the middle move, no matter what the rest of its subtree contains. The remaining two leaves could hold +100 or −100; neither can change the decision at the root. We skip them.

If you step back to the start, you'll see a smaller cutoff earlier, one level further down, with the roles reversed. Black has a reply worth +5 in hand. In the next reply, White's first option is worth +6, so that reply is worth at least +6, which is worse for Black than the +5 already available. Black won't go there; the +9 next door is never looked at.

Alpha and beta

To do this mechanically, the search carries two numbers down the tree with it.

Definition · the window

\(\alpha\) (alpha) is the best value White is already sure of, from some alternative at a White node on the path from the root to here. White will not accept less.

\(\beta\) (beta) is the best (that is, lowest) value Black is already sure of, from some alternative at a Black node on the path. Black will not accept more.

The interval \((\alpha, \beta)\) is the window. A node's exact value matters only if it lies inside the window. As soon as we learn it lies outside, we can stop searching the node: this is a cutoff.

At the root nobody is sure of anything: \(\alpha = -\infty\), \(\beta = +\infty\). As the search proceeds:

  • At a White node, each child that returns raises the node's best-so-far, and \(\alpha\) is raised to match: White is now sure of that much. If the best-so-far reaches \(\beta\), stop: this node is worth at least \(\beta\), and Black, higher up, has an alternative worth \(\beta\) and will avoid this node. This is called a beta cutoff.
  • At a Black node, each child lowers the best-so-far, and \(\beta\) with it. If it drops to \(\alpha\), stop: White has an alternative worth \(\alpha\) higher up and will avoid this node. An alpha cutoff.

Both conditions are the same test, \(\alpha \ge \beta\): the window has closed, no value can be inside it. Each child inherits its parent's current window. Here is the two-loop version, as close to the description as code can be.

def alphabeta_two_sided(
    board: chess.Board, depth: int, alpha: int, beta: int, evaluate: Evaluator
) -> int:
    """Minimax value for White, skipping branches that cannot matter.

    alpha: a value White can already force somewhere above this node.
    beta:  a value Black can already force somewhere above this node.
    """
    if board.is_checkmate():
        mate_value = MATE_SCORE + depth
        return -mate_value if board.turn == chess.WHITE else mate_value
    if board.is_stalemate() or board.is_insufficient_material():
        return 0
    if depth == 0:
        return evaluate(board)

    if board.turn == chess.WHITE:
        best_value = -INFINITY
        for move in board.legal_moves:
            board.push(move)
            child_value = alphabeta_two_sided(board, depth - 1, alpha, beta, evaluate)
            board.pop()
            best_value = max(best_value, child_value)
            alpha = max(alpha, best_value)
            if alpha >= beta:
                break  # Black already has something better elsewhere
        return best_value

    best_value = INFINITY
    for move in board.legal_moves:
        board.push(move)
        child_value = alphabeta_two_sided(board, depth - 1, alpha, beta, evaluate)
        board.pop()
        best_value = min(best_value, child_value)
        beta = min(beta, best_value)
        if alpha >= beta:
            break  # White already has something better elsewhere
    return best_value

Notice what a child's return value means now. If the loop finishes normally, the function returns the true minimax value. If it breaks early, it returns only a bound: after a beta cutoff, "at least this much". That's fine, because the caller is only going to use it to conclude "too good for White, Black avoids it", and for that a lower bound is as good as the truth.

The negamax form

Those two loops are mirror images, which is exactly what negamax was introduced to remove. In negamax everything is from the point of view of the side to move, so the window has to be flipped when we hand it to the opponent, along with the sign of the result. If I am sure of at least \(\alpha\) and my opponent is sure I get at most \(\beta\), then from the opponent's side of the table: they are sure of at least \(-\beta\), and I am sure they get at most \(-\alpha\). My window \((\alpha, \beta)\) is their window \((-\beta, -\alpha)\).

def alphabeta(
    board: chess.Board,
    depth: int,
    alpha: int,
    beta: int,
    evaluate: Evaluator,
    order_moves: bool = True,
) -> int:
    """Negamax with an alpha-beta window, from the side to move's point of view."""
    if board.is_checkmate():
        return -(MATE_SCORE + depth)
    if board.is_stalemate() or board.is_insufficient_material():
        return 0
    if depth == 0:
        side_sign = 1 if board.turn == chess.WHITE else -1
        return side_sign * evaluate(board)

    moves = ordered_moves(board) if order_moves else list(board.legal_moves)
    best_value = -INFINITY
    for move in moves:
        board.push(move)
        # My window (alpha, beta) is the opponent's window (-beta, -alpha).
        child_value = -alphabeta(board, depth - 1, -beta, -alpha, evaluate, order_moves)
        board.pop()
        best_value = max(best_value, child_value)
        alpha = max(alpha, best_value)
        if alpha >= beta:
            break  # cutoff: the opponent will never let the game reach this node
    return best_value

This is the function at the centre of nearly every chess engine written between 1960 and now: a dozen lines. (The order_moves switch belongs to the next section.)

Problem 16.1 · medium · trace

Run alpha-beta by hand, left to right, on the tree from problem 9.1 (leaves 4, −2, 7 | 1, 9 | 5, 6, 3; White to move at the root). Which leaves are skipped? Then reorder the three root moves and the leaves under them so that as many leaves as possible are skipped. How many must still be evaluated?

Solution

As drawn. Left Black node, window \((-\infty, +\infty)\): sees 4, −2, 7, value −2. There's no cutoff here, because \(\alpha\) is still \(-\infty\): White has no alternative yet. Back at the root \(\alpha = -2\). Middle node: sees 1. It's now worth at most 1; is \(1 \le \alpha = -2\)? No, so continue: sees 9, value 1. Root: \(\alpha = 1\). Right node: sees 5 (at most 5, not \(\le 1\)), 6, then 3 (not \(\le 1\)): value 3. Nothing is skipped: all 8 leaves are evaluated. The moves came in the order worst, middle, best, which is the worst possible order for White.

Best order. Search the best move, the right one, first. All three of its leaves are needed (a Black node that turns out to be the best has to be searched in full): value 3, so \(\alpha = 3\). Now for the left node put −2 first: the node is worth at most \(-2 \le 3\), cutoff after one leaf. For the middle node put 1 first: at most \(1 \le 3\), cutoff after one leaf. Total \(3 + 1 + 1 = 5\) leaves instead of 8.

You can't do better than 5: to know the root is worth exactly 3 you must see all replies to the best move (3 leaves), and at least one refuting reply to each other move (1 + 1).

Problem 16.2 · medium · find the bug

In the negamax version, someone writes the recursive call as

child_value = -alphabeta(board, depth - 1, -alpha, -beta, evaluate, order_moves)

(the window negated but not swapped). What happens on the very first call from the root, where the window is (-INFINITY, INFINITY)?

Solution

The child receives alpha = -(-INFINITY) = +INFINITY and beta = -INFINITY: a window whose lower end is above its upper end. Inside the child, after the first grandchild returns, alpha = max(+INFINITY, …) = +INFINITY ≥ beta, so the loop breaks immediately. Every node below the root examines exactly one move. The search runs astonishingly fast and plays terribly: it returns the value of the line consisting of everyone's first-generated move.

"My search got 1000 times faster after I added alpha-beta" is the tell-tale sign. A correct alpha-beta must return the same value as minimax at the root; assert that in a test, as the measurement code below does.

Why pruning never changes the answer

The story above ("that node can't matter") is convincing, but it's the kind of argument that hides off-by-one errors, so here is a real proof. It's worth following, because the three cases of this lemma reappear later as the three kinds of entry in a transposition table.

Use the negamax form. Let \(n\) be the true negamax value of a position searched to some depth, and let \(r\) be what alphabeta returns for it when called with a window \(\alpha < \beta\).

Lemma

(1) If \(\alpha < n < \beta\), then \(r = n\). Inside the window: exact.

(2) If \(n \le \alpha\), then \(r \le \alpha\). Too low to matter: reported as too low.

(3) If \(n \ge \beta\), then \(r \ge \beta\). Too high to matter: reported as too high.

The root is called with \((-\infty, +\infty)\), every value is inside that window, so by (1) the root's result is exactly the minimax value. That's what we want. But (1) can't be proved on its own, because the recursive calls use narrower windows; we need all three statements together.

Proof, by induction on the depth. If the depth is 0 or the game is over, the function returns \(n\) itself and all three statements hold trivially. Otherwise the position has children. For a child \(c\), write \(x_c\) for what it's truly worth to us (minus its own negamax value), so that \(n = \max_c x_c\). Write \(y_c\) for what the code computes for it: minus the result of the recursive call. Write \(a\) for the current value of the variable alpha when the child is called; it starts at \(\alpha\) and only grows. The child is called with the window \((-\beta, -a)\). Apply the lemma to the child (allowed by the induction hypothesis, its depth is smaller) and translate each statement back through the minus signs:

  • (1′) if \(a < x_c < \beta\) then \(y_c = x_c\);
  • (2′) if \(x_c \ge \beta\) then \(y_c \ge \beta\); (the child's case 2: its own value \(-x_c \le -\beta\), its lower bound)
  • (3′) if \(x_c \le a\) then \(y_c \le a\). (the child's case 3)

Now the three cases for the parent.

Case (2): \(n \le \alpha\). Every child has \(x_c \le n \le \alpha\). For the first child \(a = \alpha\), so (3′) gives \(y_c \le \alpha\), and alpha stays at \(\alpha\). Then the same holds for the second child, and so on. No cutoff happens (alpha never reaches \(\beta\)), and the result is \(r = \max_c y_c \le \alpha\).

Case (3): \(n \ge \beta\). Some child \(c^*\) has \(x_{c^*} = n \ge \beta\). Either the loop stops before reaching \(c^*\), which only happens when the best-so-far is already \(\ge \beta\); or it reaches \(c^*\), and (2′) gives \(y_{c^*} \ge \beta\). Either way \(r \ge \beta\).

Case (1): \(\alpha < n < \beta\). We claim \(a \le n\) throughout the loop. It's true at the start, since \(a = \alpha < n\). For each child, \(x_c \le n < \beta\), so only (1′) or (3′) can apply. Under (3′), \(y_c \le a\) and alpha doesn't move. Under (1′), \(y_c = x_c \le n\), and alpha rises to at most \(n\). So \(a \le n < \beta\) always: there is never a cutoff, every child is examined, and every \(y_c \le n\), hence \(r \le n\). Finally look at the best child \(c^*\), with \(x_{c^*} = n\). When it's reached, either \(a < n\), and (1′) gives \(y_{c^*} = n\) exactly; or \(a = n\) already, which (because \(\alpha < n\)) means some earlier child already produced the value \(n\). Either way \(r \ge n\). So \(r = n\). \(\blacksquare\)

And the measurement agrees with the proof. On the same opening position as before, here are the numbers of leaves evaluated by plain minimax, by alpha-beta taking moves in whatever order python-chess generates them, and by alpha-beta with the move ordering from the next section.

17. Move ordering and the best case

You've seen it in the demo and in problem 16.1: how much alpha-beta prunes depends entirely on the order in which moves are tried. A cutoff happens when a move is found that's good enough to close the window. If that move is tried first, everything after it is skipped. If it's tried last, nothing is.

Worst case. If at every node the moves happen to come worst-first, no cutoff ever fires and alpha-beta evaluates all \(b^d\) leaves, the same as minimax. It's never worse than minimax, apart from the trivial cost of carrying two extra numbers.

Best case. Suppose the best move always comes first. How many leaves are needed then? Go back to the proof in section 12: knowing that the root is worth exactly \(v\) means knowing two things.

  • White can get at least \(v\). To demonstrate this we need one move at each White node (the right one) but all the replies at each Black node. Along any path, half the levels branch \(b\) ways and half don't branch: about \(b^{d/2}\) leaves.
  • Black can hold White to at most \(v\). Symmetrically: all moves at White nodes, one refuting reply at each Black node. Again about \(b^{d/2}\) leaves.

The two demonstrations share exactly one leaf, the end of the principal variation. So the minimum is

\[ b^{\lceil d/2 \rceil} + b^{\lfloor d/2 \rfloor} - 1 \ \text{ leaves,} \]

where \(\lceil\cdot\rceil\) and \(\lfloor\cdot\rfloor\) round up and down (they matter only for odd \(d\)). This count is analysed in Donald Knuth and Ronald Moore's 1975 paper on alpha-beta, which shows that perfectly ordered alpha-beta achieves it and that no ordering does better. Our 12-leaf demo tree has branching 3, 2, 2: White's demonstration needs \(1 \cdot 2 \cdot 1 = 2\) leaves and Black's needs \(3 \cdot 1 \cdot 2 = 6\), minus the shared one: 7, the number the demo shows for "best move first".

The work drops from \(b^d\) to about \(2\,b^{d/2} = 2\,(\sqrt{b})^{d}\). It's as if the branching factor of chess were \(\sqrt{35} \approx 6\) instead of 35. Equivalently, since \(b^{d/2}\) at depth \(2d\) equals \(b^d\): with the same time budget, alpha-beta with good ordering searches twice as deep as minimax. Recall from section 3 that doubling the machine's speed bought 0.19 plies. This is the largest single improvement in the history of game programming, and it costs four lines of code and no accuracy at all.

Ordering moves without knowing the answer

There's an obvious circularity: to order moves best-first we'd need to know which move is best, which is what we're searching for. But we don't need a perfect order, only a good guess, and a cheap one. The classic guess in chess: try captures first, and among captures, try taking the most valuable piece with the least valuable piece first. Pawn takes queen is almost always good; queen takes pawn is often a blunder. This is known as MVV-LVA, "most valuable victim, least valuable attacker".

def capture_gain(board: chess.Board, move: chess.Move) -> int:
    """A rough guess at how good a move is, without searching it."""
    gain = 0
    if board.is_capture(move):
        victim = board.piece_type_at(move.to_square) or chess.PAWN  # en passant
        attacker = board.piece_type_at(move.from_square)
        assert attacker is not None
        # Most valuable victim first; among equal victims, least valuable attacker.
        gain += 10 * PIECE_VALUE[victim] - PIECE_VALUE[attacker]
    if move.promotion is not None:
        gain += PIECE_VALUE[move.promotion]
    return gain


def ordered_moves(board: chess.Board) -> list[chess.Move]:
    """Legal moves, the most promising ones first."""
    return sorted(
        board.legal_moves,
        key=lambda move: capture_gain(board, move),
        reverse=True,
    )

Why does such a crude rule work so well? Because most positions in a search tree are absurd. The search tries every move, including the ones that hang a queen, and in the resulting positions the refutation is nearly always "take the queen", which is the very first move this ordering tries. One capture examined, cutoff, done.

In the measurement above, the ordered search needed 7,970 leaves at depth 4. The ideal for that tree, taking \(b \approx 38.5\) (the fourth root of 2,192,376), is \(2 \cdot 38.5^2 - 1 \approx 2{,}960\). So this simple heuristic already gets within a factor of 3 of perfection. Engines add further ordering heuristics (killer moves, history tables), and the strongest one of all, which we'll get to in section 19: try first whatever was best the last time you searched this position.

Problem 17.1 · easy · compute

For \(b = 36\) and \(d = 6\), compute the number of leaves for minimax and for perfectly ordered alpha-beta. What's the ratio?

Solution

Minimax: \(36^6 = (36^3)^2 = 46{,}656^2 = 2{,}176{,}782{,}336\). Alpha-beta: \(36^3 + 36^3 - 1 = 93{,}311\). The ratio is about 23,000. In general the ratio is about \(b^{d/2}/2\), so the saving itself grows exponentially with depth.

Problem 17.2 · medium

Take a uniform tree with \(b = 3\) and \(d = 3\) (White to move at the root, 27 leaves). Using the "two demonstrations" argument, count the leaves in White's demonstration and in Black's separately, and check the total against the formula. Why are the two counts different when the depth is odd?

Solution

The levels are: White (ply 0), Black (ply 1), White (ply 2), then leaves. White's demonstration ("I can get at least \(v\)") takes one move at White nodes and all moves at Black nodes: \(1 \cdot 3 \cdot 1 = 3\) leaves. Black's demonstration ("you get at most \(v\)") takes all moves at White nodes and one at Black nodes: \(3 \cdot 1 \cdot 3 = 9\) leaves. They share one leaf: \(3 + 9 - 1 = 11\). The formula: \(3^{\lceil 3/2 \rceil} + 3^{\lfloor 3/2 \rfloor} - 1 = 9 + 3 - 1 = 11\). So 11 of 27.

With an odd depth, two of the three levels belong to the side that moves first. The demonstration that must consider all moves at those two levels (Black's, here) is the big one, \(b^{\lceil d/2 \rceil}\); the other has only one branching level, \(b^{\lfloor d/2 \rfloor}\). This is why going from an even depth to the next odd depth costs alpha-beta much more than going from odd to even: the rounded-up term jumps by a factor of \(b\) at every odd depth. You can see it in the measured table: depth 2 to 3 multiplied the ordered count by 8.6, depth 3 to 4 only by 4.0.

18. The horizon effect and quiescence search

Look again at the last column of the measurement table: the value of the same position at depths 1, 2, 3, 4 was +120, −130, +215, −20. The position didn't change. It's a calm opening position that a chess player would call roughly equal. Yet the search swings between "White is winning a pawn" and "Black is winning a pawn" depending on whether the depth is odd or even.

We've met this twice already: in problem 10.1 and in the flicker of the ranking demo. The cause is always the same. The search stops at a fixed depth and evaluates whatever position it finds there, and very often that position is in the middle of an exchange. At depth 1 here, the engine plays Nxe5, a knight taking a pawn that is defended twice, and counts itself a pawn up because it stopped before the recapture. With an odd depth White makes the last move and gets the last free capture; with an even depth Black does.

The horizon effect

A fixed-depth search can't see anything beyond its last ply, its horizon. Anything bad that happens one ply later doesn't exist for it. Worse, the search will actively push bad news over the horizon: if losing a piece is unavoidable, it will throw in pointless checks and sacrifices that delay the loss past the last ply, and then report that all is well.

Searching one ply deeper doesn't help: the horizon moves one ply and the problem moves with it. The real mistake is applying a static evaluation, which only counts pieces, to a position that isn't static. So let's not do that. At depth 0, instead of calling the evaluation function immediately, we keep searching, but only the moves that make a position unstable: captures. When no captures are left (or none of them helps), the position is quiet, and only then do we trust the evaluation. This is quiescence search.

There's one subtlety that makes it work. In a normal search the side to move must play one of its moves. In quiescence search we're only generating captures, and it would be absurd to force a player to capture: if the only capture is queen takes defended pawn, the player would just play something else. So the side to move always has the option to stand pat: decline all captures and accept the static evaluation. The static evaluation therefore acts as a floor on the node's value, and the search starts from it instead of from \(-\infty\).

def quiescence(board: chess.Board, alpha: int, beta: int, evaluate: Evaluator) -> int:
    """Play out captures until the position is quiet, then evaluate it."""
    if board.is_checkmate():
        return -MATE_SCORE
    if board.is_stalemate() or board.is_insufficient_material():
        return 0

    side_sign = 1 if board.turn == chess.WHITE else -1
    stand_pat = side_sign * evaluate(board)  # value if I decline every capture
    if stand_pat >= beta:
        return stand_pat
    alpha = max(alpha, stand_pat)

    best_value = stand_pat
    for move in ordered_moves(board):
        if not board.is_capture(move):
            continue
        board.push(move)
        child_value = -quiescence(board, -beta, -alpha, evaluate)
        board.pop()
        best_value = max(best_value, child_value)
        alpha = max(alpha, best_value)
        if alpha >= beta:
            break
    return best_value

It's the alpha-beta loop again with three differences: no depth counter, only captures are searched, and best_value starts at stand_pat. It needs no depth limit because every capture removes a piece from the board, so a line of captures can be at most 30 moves long; in practice the lines are short, because MVV-LVA ordering plus the stand-pat cutoff end most of them after a move or two.

Problem 18.1 · medium

Suppose we deleted the stand-pat logic from quiescence and started best_value at -INFINITY, returning the static evaluation only if there are no captures at all. What value would it give for position A before Qxd5, with White to move, where White's only capture is Qxd5? What does the correct version give?

Solution

Without stand pat, White would be forced to take whenever a capture exists. White's only capture is Qxd5; after it Black recaptures (Black is also "forced", and happy to be); after, say, Rxd5 White has no captures left and the static evaluation is −800. So the broken version reports −800 for a position that is level: it believes White must lose the queen.

The correct version computes stand_pat = 0, then tries Qxd5, gets −800 for it, and keeps the maximum: 0. "I don't have to capture" is the whole difference.

19. Iterative deepening and transposition tables

Two practical problems remain, and they turn out to have one solution between them.

Problem one: what depth should we ask for? In a real game the engine has a clock, not a depth. The time a depth-\(d\) search takes varies wildly from one position to the next, and a search interrupted halfway through is useless: it has examined some moves fully and others not at all. The standard answer sounds wasteful: search to depth 1; then start over and search to depth 2; then depth 3; and so on until time runs out, and play the best move from the last completed depth. This is iterative deepening.

It's not wasteful, for the reason we worked out in the detour of section 3: in an exponential tree the last level dominates. If each depth costs \(k\) times the previous one, then all the earlier depths together cost \(1/k + 1/k^2 + \dots\), which is about \(1/(k-1)\) of the last one. With alpha-beta \(k\) is around 6, so re-searching all the shallower depths adds about 20%.

Problem two: the tree isn't a tree. In problem 2.2 we saw that different move orders reach the same position, and our search evaluates such a position again every time. At depth 4 from the starting position, 197,281 nodes hold only 72,078 distinct positions, and the redundancy grows with depth.

The common solution is a cache: a hash table from positions to what the search learned about them, called a transposition table. It fixes problem two directly. And it turns problem one from a 20% cost into a net gain, because of what we store: along with the value, we remember which move was best. When iteration \(d\) arrives at a position, the table still holds the best move from iteration \(d - 1\). That move is very likely still the best, so we try it first, and we know from section 17 what trying the best move first does to alpha-beta.

Detour · Zobrist hashing

To use positions as dictionary keys we need to hash them, and fast, since it happens at every node. The trick, published by Albert Zobrist in 1970, is worth knowing outside chess too. Generate one random 64-bit number for every (piece, colour, square) combination, \(6 \times 2 \times 64 = 768\) numbers, plus a few for side to move, castling rights and en passant. The hash of a position is the XOR of the numbers for everything that's true of it.

Because XOR is its own inverse, the hash can be updated when a move is made, without recomputing it: XOR out the piece on its old square, XOR it in on its new square, XOR the side-to-move number. Three operations instead of a pass over the board. And because XOR doesn't care about order, positions reached by different move orders get the same hash automatically.

import random

import chess

random.seed(2026)
# One random 64-bit number for every (piece type, colour, square) combination.
PIECE_KEY: dict[tuple[chess.PieceType, chess.Color, chess.Square], int] = {
    (piece_type, color, square): random.getrandbits(64)
    for piece_type in chess.PIECE_TYPES
    for color in chess.COLORS
    for square in chess.SQUARES
}
BLACK_TO_MOVE_KEY = random.getrandbits(64)


def position_hash(board: chess.Board) -> int:
    """XOR together the keys of everything that is true about the position."""
    hash_value = 0
    for square, piece in board.piece_map().items():
        hash_value ^= PIECE_KEY[(piece.piece_type, piece.color, square)]
    if board.turn == chess.BLACK:
        hash_value ^= BLACK_TO_MOVE_KEY
    return hash_value


def play(moves: list[str]) -> chess.Board:
    board = chess.Board()
    for move in moves:
        board.push_san(move)
    return board


knight_first = play(["Nf3", "Nf6", "g3", "g6"])
pawn_first = play(["g3", "g6", "Nf3", "Nf6"])
other = play(["Nf3", "Nf6", "g3", "d6"])
print(f"Nf3 Nf6 g3 g6: {position_hash(knight_first):016x}")
print(f"g3 g6 Nf3 Nf6: {position_hash(pawn_first):016x}")
print(f"Nf3 Nf6 g3 d6: {position_hash(other):016x}")

# Incremental update: moving the g1 knight to f3 changes only three keys.
start = chess.Board()
updated_hash = (
    position_hash(start)
    ^ PIECE_KEY[(chess.KNIGHT, chess.WHITE, chess.G1)]  # knight leaves g1
    ^ PIECE_KEY[(chess.KNIGHT, chess.WHITE, chess.F3)]  # knight lands on f3
    ^ BLACK_TO_MOVE_KEY  # the turn passes to Black
)
print("incremental update matches:", updated_hash == position_hash(play(["Nf3"])))

The third differs by one move: a completely different hash. python-chess has a production version of this built in, chess.polyglot.zobrist_hash, which our engine uses. (It recomputes from scratch on each call, which is slow; a serious engine keeps the hash updated incrementally as in the last lines of the example.)

What exactly to store

Here's where the lemma from section 16 comes back. Alpha-beta doesn't always return a node's true value. Depending on how the true value relates to the window, the result is one of three kinds, and a cached result is only safe to reuse if we remember which kind it was:

What happenedWhat the result \(r\) meansStored as
Some move raised alpha, no cutofftrue value \(= r\)EXACT
A move caused a cutoff (\(r \ge \beta\))true value \(\ge r\)LOWER bound
No move reached alpha (\(r \le \alpha\))true value \(\le r\)UPPER bound

(The proof showed slightly less: for instance in the cutoff case, that \(r \ge \beta\). The stronger fact that the true value is at least \(r\) holds for our implementation because every number it maximises over is itself either exact or a lower bound of the right kind; implementations with this property are called fail-soft.)

When the search reaches a position that's in the table and was searched to the same depth, an exact entry can be returned at once. A bound can't, but it can narrow the window: a lower bound raises alpha, an upper bound lowers beta, and if that closes the window we have a cutoff without searching anything.

class Bound(Enum):
    EXACT = "exact"  # the stored value is the true value
    LOWER = "lower"  # the true value is at least the stored value (search was cut off)
    UPPER = "upper"  # the true value is at most the stored value (no move reached alpha)


@dataclass
class TableEntry:
    depth: int
    value: int
    bound: Bound
    best_move: chess.Move | None


TranspositionTable = dict[int, TableEntry]


def search(
    board: chess.Board,
    depth: int,
    alpha: int,
    beta: int,
    evaluate: Evaluator,
    table: TranspositionTable,
) -> int:
    """Alpha-beta + quiescence + a transposition table."""
    if board.is_checkmate():
        return -(MATE_SCORE + depth)
    if board.is_stalemate() or board.is_insufficient_material():
        return 0
    if depth == 0:
        return quiescence(board, alpha, beta, evaluate)

    original_alpha = alpha
    position_key = chess.polyglot.zobrist_hash(board)
    entry = table.get(position_key)
    if entry is not None and entry.depth == depth:
        if entry.bound == Bound.EXACT:
            return entry.value
        if entry.bound == Bound.LOWER:
            alpha = max(alpha, entry.value)
        else:
            beta = min(beta, entry.value)
        if alpha >= beta:
            return entry.value

    moves = ordered_moves(board)
    if entry is not None and entry.best_move in moves:
        # Whatever was best last time is tried first, even if the depth differs.
        moves.remove(entry.best_move)
        moves.insert(0, entry.best_move)

    best_value = -INFINITY
    best_move_here: chess.Move | None = None
    for move in moves:
        board.push(move)
        child_value = -search(board, depth - 1, -beta, -alpha, evaluate, table)
        board.pop()
        if child_value > best_value:
            best_value, best_move_here = child_value, move
        alpha = max(alpha, best_value)
        if alpha >= beta:
            break

    if best_value <= original_alpha:
        bound = Bound.UPPER
    elif best_value >= beta:
        bound = Bound.LOWER
    else:
        bound = Bound.EXACT
    table[position_key] = TableEntry(depth, best_value, bound, best_move_here)
    return best_value

The top is the alpha-beta we know, now calling quiescence at depth 0. The middle is the table probe and the move ordering: the remembered best move goes to the front even when the stored depth is different, since a best move from a shallower search is still an excellent first guess. The bottom classifies the result by comparing it to the window we were originally given and stores it.

One simplification: we reuse a stored value only if it was computed to exactly the same depth. Real engines also accept entries from deeper searches, which are more accurate; that needs care with mate scores (ours encode the remaining depth) and it means the result is no longer identical to a plain fixed-depth search, so we skip it here.

The driver loop is short.

def iterative_deepening(
    board: chess.Board, max_depth: int, evaluate: Evaluator
) -> tuple[chess.Move, int]:
    """Search depth 1, then 2, ... reusing the table between rounds."""
    table: TranspositionTable = {}
    chosen_move: chess.Move | None = None
    value = 0
    for depth in range(1, max_depth + 1):
        value = search(board, depth, -INFINITY, INFINITY, evaluate, table)
        chosen_move = table[chess.polyglot.zobrist_hash(board)].best_move
        assert chosen_move is not None, "no legal moves"
        print(f"depth {depth}: {board.san(chosen_move):6} value {value:+5d}")
    assert chosen_move is not None, "max_depth must be at least 1"
    return chosen_move, value

Problem 19.1 · medium

A buggy engine stores every result in the table as if it were exact, with no bound flag. Describe a concrete sequence of events in which this makes the search return a wrong value.

Solution

Position P is first reached with a narrow window, say \((\alpha, \beta) = (50, 60)\). Its first move is worth 200 to the side to move. That's \(\ge \beta\), so there's a cutoff and the function returns 200 without looking at the other moves; one of them might be worth 900. The honest meaning of the result is "at least 200". The buggy engine stores "P = 200".

Later P is reached by another move order (a transposition) with a wide window, say \((0, 1000)\), in which the exact value matters. The buggy engine returns the stored 200. The true value is 900, and the engine has just misjudged a line that wins a queen as one that wins two pawns, and may prefer something else. With the flag, the entry says LOWER 200: alpha is raised to 200 and the position is searched again in the window \((200, 1000)\), finding 900.

Problem 19.2 · medium · compute

A 64-bit hash has \(2^{64}\) possible values, far fewer than the number of chess positions (more than \(10^{40}\)), so two different positions can share a hash, and our dictionary would then confuse them. An engine searches \(10^8\) positions per second for 10 minutes. Roughly how likely is it that some two of the positions it stores collide? Use the birthday estimate: among \(N\) random values out of \(M\), the expected number of colliding pairs is about \(N^2 / (2M)\).

Solution

\(N = 10^8 \times 600 = 6 \times 10^{10}\) positions (an overestimate of the distinct ones, since many repeat). \(M = 2^{64} \approx 1.8 \times 10^{19}\). Expected colliding pairs: \(N^2/(2M) = 3.6 \times 10^{21} / 3.7 \times 10^{19} \approx 100\).

So collisions do happen in long searches: a hundred or so here, if every position were kept. In practice far fewer are kept (tables have a fixed size and overwrite old entries), a collision only matters if the wrong entry happens to be probed at a moment where it changes a decision, and engines add a cheap sanity check (is the stored best move even legal here?). Experiments by engine authors have repeatedly found the effect on playing strength unmeasurable, which is why everyone uses 64 bits and accepts the risk. Our own code does have the check: entry.best_move in moves.

20. Pitfalls

A list of the mistakes that are easy to make and hard to notice, most of which we've met along the way.

  • Unbalanced push and pop. Every path out of the loop body must restore the board, including early breaks and returns. In our code the pop always comes immediately after the recursive call, before any decision is made, for this reason.
  • Wrong point of view at the leaves of negamax. The evaluation is for White; negamax needs it for the side to move. The bug hides at some depths and for one colour (problem 13.1).
  • Negating but not swapping the window. The child gets (-beta, -alpha), in that order (problem 16.2).
  • Negating the most negative integer. In Python integers are unbounded, but in C, Rust or Java, if you use INT_MIN as \(-\infty\), then -INT_MIN overflows, because two's-complement integers have one more negative value than positive. Use a constant like -1_000_000_000 whose negation is representable.
  • No legal moves means two different things. Checkmate or stalemate; a loop over zero moves can't tell which.
  • All mates look alike. Without a distance term the engine may never deliver a mate it has seen (section 11).
  • Comparing scores from odd and even depths without quiescence search: the last mover gets a free capture, so values see-saw (section 18).
  • Trusting non-best root scores from alpha-beta. After a full-window search, the best root move has an exact score, but every later root move was searched against the best one's alpha, and what came back may be only "no better than that". You can't read the second-best move off those numbers.
  • Treating a bound in the table as exact (problem 19.1).
  • Draws by repetition and the fifty-move rule. Our engine ignores them. Since a position's value in the search depends only on the position, a winning engine can shuffle between two positions for ever, each time "seeing" that it's still winning; and those rules make a position's value depend on the path that led to it, which sits awkwardly with a table keyed on positions alone. Engines check for repetition along the current path explicitly.
  • Believing the number. The value is the evaluation of a position a few plies away, under the assumption that the opponent sees exactly what the engine sees. It's a guarantee about the tree, not about the game.

21. Summary

Cheat sheet
  • Game tree: positions are nodes, moves are edges, levels alternate between the players. Size \(b^d\) with \(b \approx 35\) for chess: one more ply costs 35 times more; twice the speed buys a fifth of a ply.
  • Minimax: a leaf is worth its evaluation; a White node is worth the max of its children; a Black node the min. It's \(\exists/\forall\) with numbers. The root value is what each side can force against any defence.
  • Negamax: score every node for the side to move; then every node is a max of the negated child scores. One loop instead of two.
  • Alpha-beta: carry a window \((\alpha, \beta)\) of values that could still matter; stop searching a node when \(\alpha \ge \beta\). Same answer as minimax, always. With good move ordering the cost is about \(2b^{d/2}\): twice the depth for the same time.
  • Making it practical: order moves (captures first, then the table move first); never evaluate in the middle of an exchange (quiescence search); deepen iteratively and remember results and best moves in a transposition table keyed by a Zobrist hash.

The dependency between the two halves of an engine is worth one more sentence: the search makes a weak evaluation strong by looking where evaluation can't, and the evaluation gives the search something to aim for where it can't look. Neither is much use alone.

Quiz 1 · easy

Compute the minimax value of this tree (White to move at the root).

Solution

Bottom White nodes: \(\max(2,8) = 8\), \(\max(5,1) = 5\), \(\max(3,4) = 4\), \(\max(9,7) = 9\). Black nodes: \(\min(8, 5) = 5\) and \(\min(4, 9) = 4\). Root: \(\max(5, 4) = 5\). White plays the left move.

Quiz 2 · medium

Run alpha-beta left to right on the tree of Quiz 1. Which leaves are never evaluated, and what are \(\alpha\) and \(\beta\) at the moment of the cutoff?

Solution

Left subtree: the first White node sees 2 and 8, value 8; its Black parent now has \(\beta = 8\). The second White node sees 5 (not \(\ge 8\)), then 1; value 5. The Black node is worth 5. Root: \(\alpha = 5\).

Right subtree, entered with \(\alpha = 5\), \(\beta = +\infty\): the first White node sees 3 and 4, value 4. Its Black parent is now worth at most 4, so \(\beta = 4\), and \(\alpha = 5 \ge \beta = 4\): cutoff. The leaves 9 and 7 are never evaluated; 6 of 8 leaves are. The root is 5, as before.

A common mistake is to expect a cutoff in the left subtree at the leaf 1. There the White node already holds 5, and the question at a White node is whether its value has reached \(\beta = 8\); it hasn't, and anyway 1 is the last leaf.

Quiz 3 · easy · true or false

(a) Alpha-beta can return a different root value from minimax when its move ordering is bad. (b) With the worst possible move ordering, alpha-beta evaluates as many leaves as minimax. (c) A computer twice as fast searches one ply deeper in the same time. (d) Negamax relies on the game being zero-sum.

Solution

(a) False. Ordering affects only how much work is done; the lemma in section 16 doesn't mention order at all.

(b) True. No cutoffs ever fire. The demo with "worst move first" shows 12 of 12.

(c) False. One more ply costs a factor of \(b \approx 35\) for minimax, or about 6 for well-ordered alpha-beta. A factor of 2 buys 0.19 plies of minimax, or \(\ln 2 / \ln 6 \approx 0.39\) plies of alpha-beta.

(d) True. The step "my value is minus my opponent's value" is the zero-sum assumption. In a game where both players could gain at once, a node would need a separate score per player, and neither negamax nor alpha-beta would be valid.

Quiz 4 · medium

negamax(board, 6, evaluate) returns −100002 for some position. In chess terms, what does that mean for the side to move?

Solution

Negative and beyond the mate score: the side to move is getting checkmated. The mated node contributed \(-(100000 + \text{remaining depth})\), so the remaining depth there was 2, which puts it \(6 - 2 = 4\) plies below the root. Four plies: I move, they move, I move, they move and it's mate. So "I will be checkmated by the opponent's second move, and that's with my best defence": the engine, as the loser, prefers the longest possible resistance, so no defence lasts longer.

Quiz 5 · medium

An engine with good move ordering reaches depth 12 in the time plain minimax needs for depth 6 on the same positions. If the true branching factor is 36, what is the engine's effective branching factor, the number \(b'\) such that its work grows like \((b')^d\)?

Solution

Equal work: \((b')^{12} = 36^6\), so \(b' = 36^{6/12} = \sqrt{36} = 6\). This is how engine authors measure search quality in practice: run to depth \(d\) and \(d + 1\), divide the node counts. Modern engines, with further pruning techniques that are no longer exact, get below 2.

Quiz 6 · medium

Why can quiescence search use the static evaluation as a lower bound on a node's value ("stand pat"), while the main search can't do the same thing at interior nodes?

Solution

In quiescence search only captures are generated, so there is a large set of moves (all the quiet ones) that the side to move could play and we aren't looking at. Standing pat is a stand-in for them: "I could play some quiet move and keep roughly the current evaluation". That's a reasonable floor.

In the main search every legal move is examined, so there's nothing left to stand in for; the node's value is simply the max over the moves. Using the static evaluation as a floor there would amount to letting a player skip their turn, and in chess having to move is sometimes a disadvantage. (Engines do exploit a version of this idea, null-move pruning, as a risky but effective speed-up.)

Quiz 7 · hard

You call alphabeta(board, 4, 100, 101, evaluate): a window just one unit wide. The function returns 57. What exactly do you know about the true value \(n\)? Why might such a call be useful, given that it can never return an exact value?

Solution

With integers there's no value strictly between 100 and 101, so case (1) of the lemma can't occur. If \(n \ge 101\) the lemma says the result would be \(\ge 101\); we got 57, so that's ruled out, and therefore \(n \le 100\). The lemma promises no more than that; the fail-soft property of our code gives the sharper \(n \le 57\).

So a one-unit window asks a yes/no question, "is this position worth more than 100?", and because the window is so narrow nearly everything cuts off and the answer comes very cheaply. This is the basis of principal variation search: search the first move with the full window to get its value \(v\), then for every other move only ask "is it better than \(v\)?" with the window \((v, v+1)\). With good ordering the answer is almost always no. If it's yes, re-search that move properly. We're back to the booleans of the mate-in-two solver, used as a probe inside the numeric search.

24. Beyond minimax

Minimax with alpha-beta is one answer to "how do I choose a move in a game tree too big to search". Here are its main relatives and rivals, briefly.

More pruning, no longer exact

Everything on this page computes exactly the minimax value of the depth-limited tree. Modern alpha-beta engines go much deeper by giving that up: they search unpromising moves to a reduced depth (late move reductions), skip subtrees when even passing the turn would be good enough (null-move pruning), and discard moves that seem unable to raise alpha (futility pruning). Each of these can miss something, and each is tuned by playing enormous numbers of games. The result is a search that's 30 or more plies deep along the main line and very thin elsewhere: the "search everything to depth \(d\)" picture of this page is the skeleton, not the animal.

Expectiminimax: games with dice

In backgammon a third kind of node appears between the players' moves: a chance node for the dice roll. Its value is neither a max nor a min but the probability-weighted average of its children. Minimax extends naturally; alpha-beta mostly doesn't, because an average can't be bounded by seeing only some of the children unless the leaf values are known to lie in a fixed range.

Monte Carlo tree search

Alpha-beta needs an evaluation function, and for the game of Go nobody could write a good one by hand. Monte Carlo tree search (MCTS), developed around 2006, avoids the need: it estimates a position's value by playing many games from it to the end and averaging the results, and it grows its tree unevenly, spending more simulations on moves that have looked good so far while still occasionally trying the others. Its backed-up values are averages, not minimums and maximums, though with enough simulations they converge to the minimax value.

AlphaZero and neural networks

AlphaZero (2017) combined MCTS with a deep neural network that, given a position, outputs both an evaluation and a probability for each move, the latter steering the search toward plausible moves. Trained only by playing against itself, it beat Stockfish while examining about 80 thousand positions per second against Stockfish's 70 million: a thousand times fewer, each judged far better. The open-source Leela Chess Zero follows the same design.

NNUE: the networks come to alpha-beta

The alpha-beta engines answered by keeping their search and replacing the hand-written evaluation with a small neural network designed to be updated incrementally when a move is made, so that it can still be run millions of times per second on a CPU. This design, NNUE, came from computer shogi (Yu Nasu, 2018) and was adopted by Stockfish in 2020. So today's strongest chess engine is still, at its core, the algorithm on this page: negamax, alpha-beta, quiescence, iterative deepening, a transposition table, with a far better evaluation at the leaves and much more aggressive pruning.

25. History

  • 1913. Ernst Zermelo publishes a set-theoretic analysis of chess, the origin of the theorem that in such a game one side can force a win or both can force a draw.
  • 1928. John von Neumann proves the minimax theorem for two-player zero-sum games, covering the much harder case where the players move simultaneously or with hidden information. For games like chess the "theorem" is the easy induction of section 12, but the name minimax comes from this line of work.
  • 1948. Alan Turing and David Champernowne design Turochamp, a chess program with a look-ahead and a material-plus-position evaluation. No machine of the time could run it; in 1952 Turing executed it by hand, with pencil and paper, in a game against Alick Glennie, and lost.
  • 1950. Claude Shannon publishes "Programming a Computer for Playing Chess", which lays out almost everything in the first half of this page: the evaluation function, minimax to a fixed depth (his "type A" strategy), the estimate of \(10^{120}\) games, and the observation that evaluation should only be applied to quiescent positions.
  • 1956 to 1963. Alpha-beta is discovered several times over. John McCarthy proposed the idea around the 1956 Dartmouth workshop; Newell, Shaw and Simon used a form of it in their chess program in 1958; Hart and Edwards described it in an MIT memo in 1961; Alexander Brudno published an independent version in the Soviet Union in 1963.
  • 1970. Albert Zobrist introduces his hashing method.
  • 1975. Donald Knuth and Ronald Moore publish "An Analysis of Alpha-Beta Pruning", with a correctness proof and a thorough analysis of the best and average cases, written in the negamax form used on this page.
  • 1997. IBM's Deep Blue, an alpha-beta searcher on custom chips examining about 200 million positions per second, beats world champion Garry Kasparov 3½ to 2½ in a six-game match.
  • 2017. AlphaZero shows that a learned evaluation with a selective search can outplay the best alpha-beta engine of the day.
  • 2020. Stockfish 12 ships with an NNUE evaluation, combining the two traditions.

27. The whole engine in one file

engine.py 
"""engine.py - a chess engine that grows from a move counter into alpha-beta search."""

from collections.abc import Callable
from dataclasses import dataclass
from enum import Enum

import chess
import chess.polyglot

Evaluator = Callable[[chess.Board], int]


def count_positions(board: chess.Board, plies_left: int) -> int:
    """Count the positions exactly `plies_left` half-moves below `board`."""
    if plies_left == 0:
        return 1
    position_count = 0
    for move in board.legal_moves:
        board.push(move)  # walk down one edge of the tree
        position_count += count_positions(board, plies_left - 1)
        board.pop()  # walk back up
    return position_count


PIECE_VALUE: dict[chess.PieceType, int] = {
    chess.PAWN: 100,
    chess.KNIGHT: 300,
    chess.BISHOP: 300,
    chess.ROOK: 500,
    chess.QUEEN: 900,
    chess.KING: 0,  # both sides always have exactly one king
}


def material(board: chess.Board) -> int:
    """Material balance in centipawns. Positive means White is ahead."""
    balance = 0
    for piece_type, piece_value in PIECE_VALUE.items():
        white_count = len(board.pieces(piece_type, chess.WHITE))
        black_count = len(board.pieces(piece_type, chess.BLACK))
        balance += piece_value * (white_count - black_count)
    return balance


def greedy_move(board: chess.Board, evaluate: Evaluator) -> chess.Move:
    """Play the move whose resulting position looks best right away."""
    side_sign = 1 if board.turn == chess.WHITE else -1
    best_move: chess.Move | None = None
    best_value = -10**9
    for move in board.legal_moves:
        board.push(move)
        value = side_sign * evaluate(board)  # from the mover's point of view
        board.pop()
        if value > best_value:
            best_move, best_value = move, value
    assert best_move is not None, "no legal moves"
    return best_move


MATE_SCORE = 100_000  # far above any material balance


def minimax_plain(board: chess.Board, depth: int, evaluate: Evaluator) -> int:
    """Value of `board` from White's side, looking `depth` plies ahead."""
    if board.is_checkmate():
        # The side to move is the one that got mated.
        return -MATE_SCORE if board.turn == chess.WHITE else MATE_SCORE
    if board.is_stalemate() or board.is_insufficient_material():
        return 0
    if depth == 0:
        return evaluate(board)

    child_values: list[int] = []
    for move in board.legal_moves:
        board.push(move)
        child_values.append(minimax_plain(board, depth - 1, evaluate))
        board.pop()

    if board.turn == chess.WHITE:
        return max(child_values)  # White picks the child that is best for White
    return min(child_values)  # Black picks the child that is worst for White


def minimax(board: chess.Board, depth: int, evaluate: Evaluator) -> int:
    """Like minimax_plain, but a mate found sooner scores more than one found later."""
    if board.is_checkmate():
        # `depth` plies were still unused when the mate appeared: more unused = sooner.
        mate_value = MATE_SCORE + depth
        return -mate_value if board.turn == chess.WHITE else mate_value
    if board.is_stalemate() or board.is_insufficient_material():
        return 0
    if depth == 0:
        return evaluate(board)

    child_values: list[int] = []
    for move in board.legal_moves:
        board.push(move)
        child_values.append(minimax(board, depth - 1, evaluate))
        board.pop()
    return max(child_values) if board.turn == chess.WHITE else min(child_values)


Search = Callable[[chess.Board, int, Evaluator], int]


def best_move(
    board: chess.Board, depth: int, evaluate: Evaluator, search: Search = minimax
) -> tuple[chess.Move, int]:
    """Try every move at the root; return the best one and its value for White."""
    side_sign = 1 if board.turn == chess.WHITE else -1
    chosen_move: chess.Move | None = None
    chosen_value = 0
    for move in board.legal_moves:
        board.push(move)
        value = search(board, depth - 1, evaluate)  # one ply is already spent
        board.pop()
        if chosen_move is None or side_sign * value > side_sign * chosen_value:
            chosen_move, chosen_value = move, value
    assert chosen_move is not None, "no legal moves"
    return chosen_move, chosen_value


INFINITY = 10**9


def negamax(board: chess.Board, depth: int, evaluate: Evaluator) -> int:
    """Value of `board` from the side to move's point of view."""
    if board.is_checkmate():
        return -(MATE_SCORE + depth)  # I am the one who is mated
    if board.is_stalemate() or board.is_insufficient_material():
        return 0
    if depth == 0:
        side_sign = 1 if board.turn == chess.WHITE else -1
        return side_sign * evaluate(board)

    best_value = -INFINITY
    for move in board.legal_moves:
        board.push(move)
        # The child is scored from the opponent's side, so flip its sign.
        best_value = max(best_value, -negamax(board, depth - 1, evaluate))
        board.pop()
    return best_value


def alphabeta_two_sided(
    board: chess.Board, depth: int, alpha: int, beta: int, evaluate: Evaluator
) -> int:
    """Minimax value for White, skipping branches that cannot matter.

    alpha: a value White can already force somewhere above this node.
    beta:  a value Black can already force somewhere above this node.
    """
    if board.is_checkmate():
        mate_value = MATE_SCORE + depth
        return -mate_value if board.turn == chess.WHITE else mate_value
    if board.is_stalemate() or board.is_insufficient_material():
        return 0
    if depth == 0:
        return evaluate(board)

    if board.turn == chess.WHITE:
        best_value = -INFINITY
        for move in board.legal_moves:
            board.push(move)
            child_value = alphabeta_two_sided(board, depth - 1, alpha, beta, evaluate)
            board.pop()
            best_value = max(best_value, child_value)
            alpha = max(alpha, best_value)
            if alpha >= beta:
                break  # Black already has something better elsewhere
        return best_value

    best_value = INFINITY
    for move in board.legal_moves:
        board.push(move)
        child_value = alphabeta_two_sided(board, depth - 1, alpha, beta, evaluate)
        board.pop()
        best_value = min(best_value, child_value)
        beta = min(beta, best_value)
        if alpha >= beta:
            break  # White already has something better elsewhere
    return best_value


def capture_gain(board: chess.Board, move: chess.Move) -> int:
    """A rough guess at how good a move is, without searching it."""
    gain = 0
    if board.is_capture(move):
        victim = board.piece_type_at(move.to_square) or chess.PAWN  # en passant
        attacker = board.piece_type_at(move.from_square)
        assert attacker is not None
        # Most valuable victim first; among equal victims, least valuable attacker.
        gain += 10 * PIECE_VALUE[victim] - PIECE_VALUE[attacker]
    if move.promotion is not None:
        gain += PIECE_VALUE[move.promotion]
    return gain


def ordered_moves(board: chess.Board) -> list[chess.Move]:
    """Legal moves, the most promising ones first."""
    return sorted(
        board.legal_moves,
        key=lambda move: capture_gain(board, move),
        reverse=True,
    )


def alphabeta(
    board: chess.Board,
    depth: int,
    alpha: int,
    beta: int,
    evaluate: Evaluator,
    order_moves: bool = True,
) -> int:
    """Negamax with an alpha-beta window, from the side to move's point of view."""
    if board.is_checkmate():
        return -(MATE_SCORE + depth)
    if board.is_stalemate() or board.is_insufficient_material():
        return 0
    if depth == 0:
        side_sign = 1 if board.turn == chess.WHITE else -1
        return side_sign * evaluate(board)

    moves = ordered_moves(board) if order_moves else list(board.legal_moves)
    best_value = -INFINITY
    for move in moves:
        board.push(move)
        # My window (alpha, beta) is the opponent's window (-beta, -alpha).
        child_value = -alphabeta(board, depth - 1, -beta, -alpha, evaluate, order_moves)
        board.pop()
        best_value = max(best_value, child_value)
        alpha = max(alpha, best_value)
        if alpha >= beta:
            break  # cutoff: the opponent will never let the game reach this node
    return best_value


def quiescence(board: chess.Board, alpha: int, beta: int, evaluate: Evaluator) -> int:
    """Play out captures until the position is quiet, then evaluate it."""
    if board.is_checkmate():
        return -MATE_SCORE
    if board.is_stalemate() or board.is_insufficient_material():
        return 0

    side_sign = 1 if board.turn == chess.WHITE else -1
    stand_pat = side_sign * evaluate(board)  # value if I decline every capture
    if stand_pat >= beta:
        return stand_pat
    alpha = max(alpha, stand_pat)

    best_value = stand_pat
    for move in ordered_moves(board):
        if not board.is_capture(move):
            continue
        board.push(move)
        child_value = -quiescence(board, -beta, -alpha, evaluate)
        board.pop()
        best_value = max(best_value, child_value)
        alpha = max(alpha, best_value)
        if alpha >= beta:
            break
    return best_value


def center_distance(square: chess.Square) -> int:
    """0 for the four centre squares, 3 for the rim of the board."""
    file_distance = max(3 - chess.square_file(square), chess.square_file(square) - 4)
    rank_distance = max(3 - chess.square_rank(square), chess.square_rank(square) - 4)
    return max(file_distance, rank_distance)


def placement(board: chess.Board, color: chess.Color) -> int:
    """A small bonus for putting pieces where they usually belong."""
    bonus = 0
    for piece_type in (chess.KNIGHT, chess.BISHOP):
        for square in board.pieces(piece_type, color):
            bonus += 10 * (3 - center_distance(square))  # minor pieces like the centre
    for square in board.pieces(chess.PAWN, color):
        rank = chess.square_rank(square)
        ranks_advanced = rank - 1 if color == chess.WHITE else 6 - rank
        bonus += 5 * ranks_advanced  # pawns like to advance...
        if center_distance(square) == 0:
            bonus += 15  # ...and to stand in the centre
    return bonus


def evaluate(board: chess.Board) -> int:
    """Material plus piece placement, in centipawns, from White's side."""
    return material(board) + placement(board, chess.WHITE) - placement(board, chess.BLACK)


class Bound(Enum):
    EXACT = "exact"  # the stored value is the true value
    LOWER = "lower"  # the true value is at least the stored value (search was cut off)
    UPPER = "upper"  # the true value is at most the stored value (no move reached alpha)


@dataclass
class TableEntry:
    depth: int
    value: int
    bound: Bound
    best_move: chess.Move | None


TranspositionTable = dict[int, TableEntry]


def search(
    board: chess.Board,
    depth: int,
    alpha: int,
    beta: int,
    evaluate: Evaluator,
    table: TranspositionTable,
) -> int:
    """Alpha-beta + quiescence + a transposition table."""
    if board.is_checkmate():
        return -(MATE_SCORE + depth)
    if board.is_stalemate() or board.is_insufficient_material():
        return 0
    if depth == 0:
        return quiescence(board, alpha, beta, evaluate)

    original_alpha = alpha
    position_key = chess.polyglot.zobrist_hash(board)
    entry = table.get(position_key)
    if entry is not None and entry.depth == depth:
        if entry.bound == Bound.EXACT:
            return entry.value
        if entry.bound == Bound.LOWER:
            alpha = max(alpha, entry.value)
        else:
            beta = min(beta, entry.value)
        if alpha >= beta:
            return entry.value

    moves = ordered_moves(board)
    if entry is not None and entry.best_move in moves:
        # Whatever was best last time is tried first, even if the depth differs.
        moves.remove(entry.best_move)
        moves.insert(0, entry.best_move)

    best_value = -INFINITY
    best_move_here: chess.Move | None = None
    for move in moves:
        board.push(move)
        child_value = -search(board, depth - 1, -beta, -alpha, evaluate, table)
        board.pop()
        if child_value > best_value:
            best_value, best_move_here = child_value, move
        alpha = max(alpha, best_value)
        if alpha >= beta:
            break

    if best_value <= original_alpha:
        bound = Bound.UPPER
    elif best_value >= beta:
        bound = Bound.LOWER
    else:
        bound = Bound.EXACT
    table[position_key] = TableEntry(depth, best_value, bound, best_move_here)
    return best_value


def iterative_deepening(
    board: chess.Board, max_depth: int, evaluate: Evaluator
) -> tuple[chess.Move, int]:
    """Search depth 1, then 2, ... reusing the table between rounds."""
    table: TranspositionTable = {}
    chosen_move: chess.Move | None = None
    value = 0
    for depth in range(1, max_depth + 1):
        value = search(board, depth, -INFINITY, INFINITY, evaluate, table)
        chosen_move = table[chess.polyglot.zobrist_hash(board)].best_move
        assert chosen_move is not None, "no legal moves"
        print(f"depth {depth}: {board.san(chosen_move):6} value {value:+5d}")
    assert chosen_move is not None, "max_depth must be at least 1"
    return chosen_move, value


@dataclass
class CountingEvaluator:
    """Wraps an evaluator and counts how many positions it was asked to judge."""

    evaluate: Evaluator
    call_count: int = 0

    def __call__(self, board: chess.Board) -> int:
        self.call_count += 1
        return self.evaluate(board)
