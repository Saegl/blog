How colours are used

Each object has one colour, and it keeps that colour in the prose, the formulas, the diagrams and the demos: the base \(\cb{b}\), a digit \(\cd{d_i}\), a place value (weight) \(\cw{b^i}\), the number \(\cn{n}\) being represented, and a carry or remainder \(\cc{r}\).

1Four puzzles

Here are four things you have almost certainly seen and probably shrugged at.

  1. A debugger shows a variable as 0x7e8. Your logs print the same value as 2024. Both are correct. Why does the debugger's version need only three symbols?
  2. You type chmod 755 deploy.sh. Somehow the three digits 7, 5, 5 each encode three separate yes/no switches (read, write, execute) for owner, group and others. How does one digit hold three bits, and why is it exactly three?
  3. In Python, 0.1 + 0.2 == 0.3 is False, while 0.5 + 0.25 == 0.75 is True. What makes one tenth harder than one quarter?
  4. Spreadsheet columns go A, B, …, Z, AA, AB, …. If A were the digit “1” of some base-26 system, you would expect Z to be followed by BA (or A0), the way 9 is followed by 10. Instead you get AA. Why?

All four have one answer: they are all positional number systems, a single idea you have used since primary school without looking at it closely. By the end of this page each puzzle will feel obvious, and you will be able to:

  • convert between any two bases by hand, and know why the algorithms work;
  • prove that every whole number has exactly one representation in each base, and how many digits it needs;
  • do arithmetic directly in binary or hex, with carries;
  • predict which fractions a base can write exactly, which explains the 0.1 mystery;
  • read two's complement and IEEE 754 floating point as the positional notation they really are;
  • handle the stranger cousins: balanced ternary, negative bases, “no-zero” bases like spreadsheet columns, and mixed-radix systems like clocks and permutation ranks.

We build bottom up. First we sharpen four tools the whole page leans on. Then we go back to the problem people faced before positional notation: how do you write down a large number at all?

2The toolkit

Positional notation rests on four small pieces of math: integer division with remainder, powers and logarithms, geometric series, and evaluating polynomials. You know all of them at some level, but this page will use each of them in a slightly sharper form than you probably carry around, so we rebuild each one here with its own problems. If a subsection feels familiar, try its problems. If you get them right, skip ahead.

2.1Division with remainder

You have 23 cookies and boxes that hold 5 each. You fill boxes until you can't fill another one. You end up with 4 full boxes and 3 loose cookies:

That last sentence is the whole content of the following theorem, which we will use more than any other fact on this page.

Division theorem

For any integer \(n\) and any integer \(b \ge 1\), there is exactly one pair of integers \(q\) (the quotient) and \(\cc{r}\) (the remainder) with \[ n = q\cdot b + \cc{r} \qquad\text{and}\qquad 0 \le \cc{r} < b. \] In Python this pair is divmod(n, b), that is (n // b, n % b).

Why it exists. Line up the multiples of \(b\) on the number line: \(\dots, -2b, -b, 0, b, 2b, \dots\). They chop the line into half-open intervals \([qb, (q+1)b)\) of length \(b\). Every integer \(n\) falls into exactly one of these intervals. Call that interval's left end \(qb\). Then \(\cc{r} = n - qb\) is the distance from the left end, so \(0 \le \cc{r} < b\).

Why it's unique. Suppose \(n = qb + r = q'b + r'\) with both remainders in \([0, b)\). Subtracting gives \((q - q')\,b = r' - r\). The right side lies strictly between \(-b\) and \(b\), since both remainders are in \([0, b)\). The left side is a multiple of \(b\). The only multiple of \(b\) strictly between \(-b\) and \(b\) is \(0\). So \(r = r'\), and then \(q = q'\).

In code:

divmod_demo.py
cookie_count = 23
box_size = 5

full_boxes, leftover = divmod(cookie_count, box_size)
print(f"{cookie_count} cookies -> {full_boxes} full boxes, {leftover} left over")
print(f"check: {full_boxes} * {box_size} + {leftover} = {full_boxes * box_size + leftover}")

# Python floors toward minus infinity, so the remainder keeps the divisor's sign.
for dividend in (7, -7):
    quotient, remainder = divmod(dividend, 3)
    print(f"divmod({dividend:>2}, 3) = ({quotient:>2}, {remainder})")
output
23 cookies -> 4 full boxes, 3 left over
check: 4 * 5 + 3 = 23
divmod( 7, 3) = ( 2, 1)
divmod(-7, 3) = (-3, 2)
Negative numbers: languages disagree

The theorem asks for \(0 \le r < b\), which forces \(q = \lfloor n / b \rfloor\), rounding toward \(-\infty\). Python's // and % do exactly this, so divmod(-7, 3) == (-3, 2): indeed \(-7 = (-3)\cdot 3 + 2\). C, C++, Java, Rust and Go instead truncate toward zero: -7 / 3 == -2 and -7 % 3 == -1, which gives \(-7 = (-2)\cdot 3 + (-1)\). That is still a true equation, but the remainder is negative. The base-conversion algorithms below assume non-negative remainders, so in those languages you have to fix the sign yourself (or use rem_euclid in Rust, Math.floorMod in Java).

Why does this matter for number systems? Look at what the remainder means in the most familiar case. \(\operatorname{divmod}(5203, 10) = (520, 3)\). The remainder is the last digit, and the quotient is everything else. Dividing by 10 chops off the last digit and hands it to you. Keep this in mind, because the whole conversion algorithm grows out of it.

Practice · division with remainder

easy2.1.a What is divmod(47, 6)? Check it with the equation.

Solution

The largest multiple of 6 not exceeding 47 is \(42 = 7 \cdot 6\). So \(q = 7\) and \(r = 47 - 42 = 5\). Check: \(7\cdot 6 + 5 = 47\), and \(0 \le 5 < 6\). Answer: (7, 5).

medium2.1.b What does Python return for divmod(-17, 5)? What do C's -17 / 5 and -17 % 5 return?

Solution

Python floors: \(-17/5 = -3.4\), and the floor is \(-4\). Then \(r = -17 - (-4)(5) = -17 + 20 = 3\). So Python gives (-4, 3), and \(-4 \cdot 5 + 3 = -17\) ✓.

C truncates \(-3.4\) toward zero, giving \(-3\). Then the remainder is \(-17 - (-3)(5) = -17 + 15 = -2\). So C gives -3 and -2.

The common wrong answer for Python is (-3, -2), which is C's behaviour. Python always returns a remainder with the same sign as the divisor.

medium2.1.c Show that if \(n = qb + r\) with \(0 \le r < b\), then \(q = \lfloor n/b \rfloor\). (So // really is “the \(q\) of the theorem”.)

Solution

Divide the equation by \(b\): \(n/b = q + r/b\). Since \(0 \le r < b\), we have \(0 \le r/b < 1\). So \(n/b\) lies in the interval \([q, q+1)\). The floor of a number in \([q, q+1)\) is \(q\), by definition of floor (the largest integer \(\le\) the number). Hence \(\lfloor n/b \rfloor = q\).

2.2Powers and logarithms

For a whole number \(k \ge 1\), \(b^k\) means \(b\) multiplied by itself \(k\) times. Two rules follow directly from counting factors:

\[ \begin{aligned} b^{j}\cdot b^{k} &= b^{j+k} &&(j\text{ factors, then }k\text{ more}) \\ (b^{j})^{k} &= b^{jk} &&(k\text{ groups of }j\text{ factors}) \end{aligned} \]

What about \(b^0\) and negative exponents? Nobody “multiplies \(b\) by itself zero times”, so we choose the definition that keeps the pattern going. Walk down the powers of 10: \(1000, 100, 10, \dots\). Each step divides by 10. Continuing the pattern gives \(10^0 = 10/10 = 1\), then \(10^{-1} = 1/10\), \(10^{-2} = 1/100\), and in general

\[ b^0 = 1, \qquad b^{-k} = \frac{1}{b^{k}}. \]

With these definitions the rule \(b^{j}b^{k} = b^{j+k}\) keeps working for all integers \(j, k\). For example, \(10^{3}\cdot 10^{-1} = 1000/10 = 100 = 10^{2}\). Positional notation uses exactly this sequence of powers: \(\dots, 100, 10, 1, \tfrac{1}{10}, \tfrac{1}{100}, \dots\), each one \(b\) times the next.

The logarithm answers the reverse question: which power? \(\log_b x\) is the exponent \(y\) with \(b^{y} = x\). So \(\log_{10} 1000 = 3\), \(\log_2 1024 = 10\), \(\log_2 \tfrac18 = -3\). For numbers that are not exact powers the logarithm falls between integers: \(\log_{10} 5203 \approx 3.716\), because \(10^3 = 1000 \le 5203 < 10000 = 10^4\).

The fact we'll use

For a positive integer \(n\), \(\lfloor \log_b n \rfloor\) is the largest \(k\) with \(b^{k} \le n\). In other words, it is the exponent of the biggest power of \(b\) that fits into \(n\). We will prove in §8 that \(n\) has exactly \(\lfloor \log_b n \rfloor + 1\) digits in base \(b\).

Change of base. Calculators and math.log give natural logs (\(\ln\), base \(e\)). To get \(\log_b x\): let \(y = \log_b x\), so \(b^{y} = x\). Take \(\ln\) of both sides: \(\ln(b^{y}) = \ln x\). Then \(y \ln b = \ln x\), because \(\ln(b^y) = y\ln b\) (a logarithm turns a power into a product). So

\[ \log_b x = \frac{\ln x}{\ln b}. \]

One consequence: \(\log_2 x = \log_{10} x \cdot \frac{\ln 10}{\ln 2} \approx 3.32 \log_{10} x\). Binary numbers are about 3.32 times as long as decimal ones. Keep that 3.32 in mind.

medium2.2.c Without computing \(2^{100}\), how many decimal digits does it have? Use \(\log_{10} 2 \approx 0.30103\).

Solution

\(\log_{10} 2^{100} = 100\log_{10} 2 \approx 30.103\). So \(10^{30} \le 2^{100} < 10^{31}\): the number is at least a 1 followed by 30 zeros (31 digits) and less than the smallest 32-digit number. It has \(\lfloor 30.103\rfloor + 1 = 31\) digits. Python agrees: len(str(2**100)) == 31. The common wrong answer is 30, from forgetting the “+1”: \(10^{30}\) itself already has 31 digits.

2.3Geometric series

A geometric series adds up powers of one number \(r\) (the ratio): \(S_k = 1 + r + r^2 + \dots + r^{k-1}\). There is a neat trick for its sum. Multiply \(S_k\) by \(r\): every term moves up one power.

\[ \begin{aligned} S_k &= 1 + r + r^2 + \dots + r^{k-1} \\ r\,S_k &= \phantom{1 + {}} r + r^2 + \dots + r^{k-1} + r^{k} \end{aligned} \]

Subtract the first line from the second. Everything in the middle cancels, leaving \(rS_k - S_k = r^{k} - 1\). Factor out \(S_k\): \((r - 1)S_k = r^k - 1\). For \(r \ne 1\) we get

\[ 1 + r + r^2 + \dots + r^{k-1} = \frac{r^{k} - 1}{r - 1}. \]

Here is the version you will see over and over on this page. Multiply both sides by \(r - 1\), and write \(b\) for \(r\):

\[ (b - 1)\cdot(1 + b + b^2 + \dots + b^{k-1}) = b^{k} - 1. \]

With \(b = 10\) and \(k = 3\) this reads \(9 \cdot 111 = 999 = 1000 - 1\). With \(b = 2\) and \(k = 8\) it reads \(1\cdot 11111111_2 = 255 = 256 - 1\). In words: a string of the largest digit is one less than the next power of the base. This fact will reappear as the odometer rolling over, as the bound in the digit-count proof, and as \(-1\) being all ones in two's complement.

Infinite version. If \(|r| < 1\), then \(r^{k}\) shrinks toward 0 as \(k\) grows, so the finite sum \(\frac{1 - r^{k}}{1 - r}\) (the same formula, with signs flipped top and bottom) approaches

\[ 1 + r + r^2 + r^3 + \dots = \frac{1}{1 - r} \qquad (|r| < 1). \]

This is why \(0.333\ldots = \tfrac13\). The digits mean \(\tfrac{3}{10} + \tfrac{3}{100} + \tfrac{3}{1000} + \dots = \tfrac{3}{10}\bigl(1 + \tfrac1{10} + \tfrac1{100} + \dots\bigr) = \tfrac{3}{10}\cdot\frac{1}{1 - 1/10} = \tfrac{3}{10}\cdot\tfrac{10}{9} = \tfrac13\). Repeating expansions in any base are geometric series in disguise. We'll come back to this in §11.

Practice · geometric series

easy2.3.a Compute \(1 + 2 + 4 + \dots + 128\) using the formula, not by adding.

Solution

This is \(\sum_{i=0}^{7} 2^i\) with \(k = 8\) terms and \(r = 2\): \(\frac{2^8 - 1}{2 - 1} = 255\). (In binary this sum is 11111111, the largest byte.)

medium2.3.b Show that \(0.999\ldots = 1\) using the infinite geometric series.

Solution

\(0.999\ldots = \tfrac{9}{10} + \tfrac{9}{100} + \dots = \tfrac{9}{10}\sum_{i \ge 0} (\tfrac{1}{10})^i = \tfrac{9}{10} \cdot \frac{1}{1 - 1/10} = \tfrac{9}{10}\cdot\tfrac{10}{9} = 1.\)

The intuition “it's always a little less than 1” describes every finite truncation \(0.99\ldots9\) correctly. The infinite decimal, though, is defined as the limit of those truncations, and the limit is exactly 1. So positional notation does not give real numbers unique names: \(1.000\ldots\) and \(0.999\ldots\) name the same number. Integers don't have this problem (we'll prove it), and it's worth remembering that fractions do.

medium2.3.c Simplify \((b - 1)(b^{3} + b^{2} + b + 1)\) by expanding it term by term, and check the result against the formula.

Solution

\(b\cdot(b^3 + b^2 + b + 1) = b^4 + b^3 + b^2 + b\). And \(-1\cdot(b^3 + b^2 + b + 1) = -b^3 - b^2 - b - 1\). Adding the two, everything cancels except \(b^4 - 1\). The formula with \(k = 4\) says the same thing: \((b-1)\sum_{i=0}^{3} b^i = b^4 - 1\). For \(b = 10\): \(9 \cdot 1111 = 9999\).

2.4Evaluating polynomials: Horner's rule

A polynomial in \(x\) is a sum of coefficients times powers: \(p(x) = a_0 + a_1x + a_2x^2 + \dots + a_kx^k\). Take \(p(x) = 3 + 0x + 2x^2 + 5x^3\) and evaluate it at \(x = 10\):

\[ p(10) = 3 + 0\cdot 10 + 2\cdot 100 + 5\cdot 1000 = 5203. \]

That should look suspicious. The coefficients, read from the highest power down, are 5, 2, 0, 3, and the value is 5203. Hold that thought. It's the subject of the next few sections.

Computing each power separately costs a lot of multiplications: \(x^3\) alone takes three. William George Horner's trick (known much earlier, in China and to Newton) is to pull out common factors of \(x\) repeatedly:

\[ 3 + 0x + 2x^2 + 5x^3 \;=\; 3 + x\bigl(0 + x\,(2 + x\cdot 5)\bigr). \]

Evaluate from the inside out: start with the leading coefficient, then repeatedly multiply by \(x\) and add the next coefficient:

\[ 5 \;\xrightarrow{\times 10 + 2}\; 52 \;\xrightarrow{\times 10 + 0}\; 520 \;\xrightarrow{\times 10 + 3}\; 5203. \]

That's one multiplication per coefficient after the first. A degree-\(k\) polynomial takes \(k\) multiplications instead of \(1 + 2 + \dots + k = k(k+1)/2\) for the naive method.

horner.py
def evaluate_naive(coefficients: list[int], x: int) -> tuple[int, int]:
    """coefficients[i] multiplies x**i. Returns (value, multiplication_count)."""
    total = 0
    multiplications = 0
    for power, coefficient in enumerate(coefficients):
        term = coefficient
        for _ in range(power):
            term *= x
            multiplications += 1
        total += term
    return total, multiplications


def evaluate_horner(coefficients: list[int], x: int) -> tuple[int, int]:
    """Same polynomial, evaluated from the highest coefficient down."""
    total = 0
    multiplications = 0
    for coefficient in reversed(coefficients):
        total = total * x + coefficient
        multiplications += 1
    return total, multiplications


# 3 + 0*x + 2*x^2 + 5*x^3, evaluated at x = 10 -> the decimal number 5203
coefficients = [3, 0, 2, 5]
print("naive :", evaluate_naive(coefficients, 10))
print("horner:", evaluate_horner(coefficients, 10))
output
naive : (5203, 6)
horner: (5203, 4)

(The Horner count is 4 rather than 3 because the loop starts from total = 0 and multiplies it once for nothing. Starting from the leading coefficient would save that one.)

The step “times 10, plus the next digit” is exactly what you do when someone reads out a phone number and you build the number in your head. It's also what every hand-written atoi or parseInt does. You have written Horner's rule many times, maybe without knowing its name.

medium2.4.b A parser reads digits left to right with value = value * 10 + digit. Show by induction that after reading the digits \(d_{k}, d_{k-1}, \dots, d_{j}\) (most significant first), value equals \(\sum_{i=j}^{k} d_i 10^{\,i-j}\).

Solution

3Before positions: tallies and Roman numerals

Now the actual problem. Forget everything you know about digits for a moment.

The problem

Design a way to write down any natural number \(n = 0, 1, 2, \dots\) as a string over a fixed, finite alphabet so that:

  1. every number has a name, and different numbers have different names;
  2. names are short: much shorter than \(n\) itself;
  3. you can compare and do arithmetic on names directly, with a mechanical procedure.

Running example: a shepherd's flock of 2024 sheep, and a merchant who has to add up 2024 + 999.

3.1Naive solution 1: tally marks

One stroke per sheep. The alphabet is a single symbol, every number has a name, and adding is just concatenating. It fails requirement 2 badly: the flock needs 2024 strokes. Grouping strokes in fives (|||| with a slash through it) makes them easier to count but doesn't make the name any shorter. The length is \(\Theta(n)\).

3.2Naive solution 2: additive symbols (Roman numerals)

The natural fix is to give bigger quantities their own symbols, so that one mark stands for many strokes: I = 1, V = 5, X = 10, L = 50, C = 100, D = 500, M = 1000. A name is a bag of symbols whose values add up. The flock is MMXXIV: 1000 + 1000 + 10 + 10 + 4. (IV is the later “subtractive” shorthand for IIII.)

3.3Diagnosis

  • The alphabet isn't fixed. To go past 3999 without writing M dozens of times, you need a new symbol for 5000, then 10 000, and so on: two new symbols per factor of ten. (The Romans used overlines and frames for this.) No finite alphabet covers all numbers efficiently. That breaks the problem's first constraint.
  • Length doesn't track size. C (100) is one symbol and LXXXVIII (88) is eight. You can't tell which number is bigger by looking at lengths, so comparison needs value-by-value work.
  • No mechanical arithmetic. Try MMXXIV + CMXCIX (2024 + 999) without converting. The subtractive pairs interfere, and there's no notion of “columns” to line up. Roman-era merchants did their sums on a counting board or abacus and only recorded the results in numerals.
  • No zero. There is nothing to write for “no sheep”, and more importantly, nothing to write for “no tens”, which turns out to be the crucial gap.

Look again at the abacus they used for actual calculation. It has columns: a ones column, a tens column, a hundreds column. A bead in the hundreds column is worth 100 because of which column it sits in, not because of its shape. All beads look the same. An empty column means “none of these”. The calculation tool was already positional; the writing system just hadn't caught up. The next section turns that abacus into notation.

Practice · additive systems

Solution

Split by decimal place: 1000 + 900 + 90 + 4 = M + CM + XC + IV = MCMXCIV. Notice that we used decimal place value to do it: even Roman numerals are easiest to write by thinking positionally first.

medium3.b In a purely additive system (no subtractive pairs) with symbols for \(1, 5, 10, 50, \dots, 10^{k-1}, 5\cdot 10^{k-1}\), what is the longest name of a number below \(10^{k}\), and how long is it? Compare with \(k\) decimal digits.

Solution

Each decimal place needs at most one “five” symbol and four “one” symbols, so the digit 9 costs 5 symbols (like VIIII) and is the worst case for that place. The longest name is for \(99\ldots9\) (\(k\) nines), with \(5k\) symbols. So additive notation is about 5× longer than decimal in the worst case and needs \(2k\) distinct symbols to get that far. Decimal uses 10 symbols forever. The length is fine; the unbounded alphabet is the real failure.

4Bundles of bundles

Let's rebuild the abacus from scratch and watch digits appear.

You have a pile of pebbles and you want to record how many there are, using as few marks as possible. You pick a bundle size, say \(\cb{b} = 4\), and follow one rule:

The bundling rule

Whenever you have \(\cb{b}\) loose things of the same size, tie them together into one thing of the next size up.

Four pebbles become a bag. Four bags become a crate. Four crates become a pallet. You keep going until no size has \(\cb{b}\) or more loose items. Then, at every size, you hold somewhere between \(0\) and \(\cb{b}-1\) items, so at every size the count is a single small symbol. Write those counts down from the biggest size to the smallest, and you have the number's name.

With 23 pebbles and \(\cb{b} = 4\): 23 pebbles make 5 bags with 3 pebbles left over. Five bags make 1 crate with 1 bag left over. One crate is fewer than 4, so we stop. Reading from the biggest size down: 1 crate, 1 bag, 3 pebbles. Write it as \(\cd{113}_{\cb{4}}\). To get back to the count, ask what each item is worth in pebbles: a crate is \(4\cdot 4 = 16\), a bag is \(4\), a pebble is \(1\), so

\[ \cd{1}\cdot\cw{16} + \cd{1}\cdot\cw{4} + \cd{3}\cdot\cw{1} = \cn{23}. \]

Three things make this work, and each fixes one of the failures from §3:

  1. Position carries the size. The symbol 1 means “one crate” in the crate column and “one bag” in the bag column. We don't need a new symbol for each size, just a new column. The alphabet is fixed at \(\cb{b}\) symbols forever: requirement 1 fixed.
  2. Zero holds a place. If there had been no loose bags, the bag column would be empty, and we'd need to write something there, or “1 crate, 3 pebbles” would be read as “1 bag, 3 pebbles”. That something is 0. Zero exists in positional notation first as a placeholder, and only later as a number in its own right.
  3. Each new column multiplies capacity by \(\cb{b}\). With \(k\) columns you can write every count from 0 up to \(\cb{b}^{k} - 1\). So the length grows like \(\log_{\cb{b}} n\) rather than \(n\): requirement 2 fixed. Columns also line up for arithmetic, which fixes requirement 3, as we'll see in §10.

And our usual numerals are exactly this with \(\cb{b} = 10\): 5203 is 5 “thousand-crates”, 2 “hundred-bags”, 0 “ten-packs”, 3 singles. The only thing special about ten is the number of fingers on two hands.

5The definition

Now we can say precisely what the pebbles were doing. Number the positions from the right, starting at 0. The column at position \(i\) holds bundles of size \(\cw{b^i}\), because each step left multiplies the bundle size by \(\cb{b}\), and position 0 holds single pebbles (\(\cw{b^0} = 1\)). That's why we count from zero: the position number is the exponent.

Definition: base-b representation

Fix an integer base \(\cb{b} \ge 2\). A string of digits \(\cd{d_{k-1}}\,\cd{d_{k-2}}\cdots\cd{d_1}\,\cd{d_0}\), where every digit satisfies \(0 \le \cd{d_i} \le \cb{b} - 1\), represents the number

\[ \cn{n} \;=\; \sum_{i=0}^{k-1} \cd{d_i}\,\cw{b^{i}} \;=\; \cd{d_{k-1}}\cw{b^{k-1}} + \dots + \cd{d_1}\cw{b} + \cd{d_0}. \]

We write \((\cd{d_{k-1}}\cdots\cd{d_0})_{\cb{b}}\), or just put the base as a subscript: \(\cd{3750}_{\cb{8}}\). The digit \(\cd{d_{k-1}}\) is the most significant digit and \(\cd{d_0}\) the least significant. \(\cw{b^{i}}\) is the weight or place value of position \(i\).

The diagram below is the picture we'll keep reusing: each digit sits in a cell under its weight, and the cell's contribution is digit × weight.

5.1Digits versus symbols

A digit is a number between \(0\) and \(\cb{b}-1\). A symbol is the squiggle we draw for it. In bases up to 10 we reuse 0–9. Base 16 needs six more symbols, and the convention is a–f for 10–15. Python's int(text, base) continues through z = 35, which is why it accepts bases 2 to 36. Nothing deep is going on here: the Babylonians wrote base 60 with digits that were themselves little base-10 clusters of wedges. In code we usually skip symbols entirely and store a number's digits as a list[int], as we'll do in the homework.

Programming languages mark the base with a prefix: 0b1011 (binary), 0o755 (octal), 0x7e8 (hex). Python's bin, oct, hex and format(n, "b"/"o"/"x") go the other way.

5.2Why the digits must stay below b

The restriction \(0 \le \cd{d_i} < \cb{b}\) looks fussy, but it is exactly the bundling rule: if a column held \(\cb{b}\) or more items, we would have bundled them. Drop the restriction and names stop being unique. Allow a decimal digit “A” worth ten, and the number ten gets two names, A and 10. A hundred gets 100, A0, 9A, and more. On the other side, lower the ceiling (say, forbid the digit 9 in base 10) and some numbers have no name at all. With \(\cb{b}\) digit values, from \(0\) to \(\cb{b} - 1\), the count comes out exactly right. §8 proves this.

5.3A number is a polynomial evaluated at the base

Compare the definition with §2.4. The number \(\cd{5203}_{10}\) is the polynomial \(p(x) = \cd{5}x^3 + \cd{2}x^2 + \cd{0}x + \cd{3}\) evaluated at \(x = \cb{10}\). The same digit string in base 8 is the same polynomial evaluated at \(x = \cb{8}\): \(p(8) = 2560 + 128 + 0 + 3 = 2691\). So a digit string is a polynomial waiting for a value of \(x\), and the base is the value you plug in.

Detour: numbers are polynomials with carries

This is worth a detour because it explains why grade-school multiplication works, and what carrying really is. Multiply \(12 \times 13\) and, separately, the polynomials \((x + 2)(x + 3)\):

\[ (x+2)(x+3) = x^2 + 5x + 6 \quad\xrightarrow{\;x\,=\,10\;}\quad 100 + 50 + 6 = 156 = 12\times 13. \]

The coefficients 1 5 6 are the digits of the answer. Now try \(17 \times 18\): \((x+7)(x+8) = x^2 + 15x + 56\). The coefficients 1, 15, 56 are perfectly good polynomial coefficients, but they are not digits, since they exceed 9. Carrying fixes this: \(56 = 5\cdot 10 + 6\), so keep 6 and pass 5 up. Then \(15 + 5 = 20 = 2\cdot 10 + 0\), so keep 0 and pass 2 up. Finally \(1 + 2 = 3\). The result is 306. Polynomial arithmetic is digit arithmetic without carries. Carrying is the bundling rule, applied after the fact to restore \(0 \le \cd{d_i} < \cb{b}\). Fast multiplication algorithms (Karatsuba, FFT-based) use exactly this: multiply the digit polynomials, then do one carry pass.

6Warm-up: a counting machine

Before converting or proving anything, it's worth getting a feel for counting in a strange base, because counting is where the carry comes from. A car's odometer is a positional numeral made of wheels. Each wheel shows a digit. When a wheel passes its largest digit it snaps back to 0 and nudges the wheel on its left forward by one. That nudge is the carry, and it is the bundling rule acting one pebble at a time.

Count in base 3 for a few steps and the pattern is the same as decimal, just with a smaller wheel: 0, 1, 2, 10, 11, 12, 20, 21, 22, 100. After the largest digit comes a carry. After a run of largest digits, “222”, comes a run of carries: \(222_3 + 1 = 1000_3\). That's the geometric-series identity again: \(222_3 = 3^3 - 1\).

Increment, as an algorithm

Start at position 0. If the digit is less than \(\cb{b} - 1\), add one to it and stop. Otherwise set it to 0 (carry) and move to the next position. In binary this is: flip trailing 1s to 0 and the first 0 to 1. That's why x & (x + 1) clears the trailing ones of x, and why x & -x isolates the lowest set bit (more on -x in §12).

7Reading and writing in any base

There are two directions. Reading takes a digit string in base \(\cb{b}\) and produces the number it stands for. Writing takes a number and produces its digits in base \(\cb{b}\). A conversion between two bases is a read followed by a write. In your head the number in the middle is held in decimal. Inside a computer it is a binary integer. In both cases the middle is just “the number”, and the base only matters at the edges.

7.1Reading: Horner's rule

The definition says \(\cn{n} = \sum \cd{d_i}\cw{b^i}\), and §2.4 says the efficient way to evaluate that sum is from the most significant digit down: start with 0, then for each digit, multiply by \(\cb{b}\) and add the digit. Reading 7e8 in base 16:

\[ 0 \;\xrightarrow{\times 16 + \cd{7}}\; 7 \;\xrightarrow{\times 16 + \cd{14}}\; 126 \;\xrightarrow{\times 16 + \cd{8}}\; \cn{2024}. \]

Each “×16” shifts everything read so far one place left, making room for the next digit, exactly like the parser in problem 2.4.b. In binary, multiplying by 2 is doubling, and that gives a nice mental method: read \(101101_2\) as \(1 \to 2 \to 5 \to 11 \to 22 \to 45\). At each step, double, and add 1 if the next bit is 1.

7.2Writing: repeated division

Now the reverse. Given \(\cn{2024}\), find its hex digits. The trick is to look at Horner's form from the other end:

\[ \cn{n} = \cd{d_0} + \cb{b}\cdot\bigl(\cd{d_1} + \cb{b}\cdot(\cd{d_2} + \cb{b}\cdot(\cdots))\bigr). \]

Read it as \(\cn{n} = \cd{d_0} + \cb{b}\cdot(\text{rest})\), where \(0 \le \cd{d_0} < \cb{b}\) and “rest” is the number whose digits are \(\cd{d_{k-1}}\cdots\cd{d_1}\). That is exactly the shape of the division theorem, \(n = q\cdot b + r\) with \(0 \le r < b\), and the theorem says such a pair is unique. So:

The writing algorithm

\(\operatorname{divmod}(\cn{n}, \cb{b}) = (\text{rest}, \cd{d_0})\). The remainder is the last digit, and the quotient is the number formed by all the other digits. Repeat on the quotient until it reaches 0. The digits come out least significant first.

Writing 2024 in base 16:

ndivmod(n, 16)digit produced
2024(126, 8)\(\cd{d_0} = 8\)
126(7, 14)\(\cd{d_1} = 14 = \mathtt{e}\)
7(0, 7)\(\cd{d_2} = 7\)

Read the digit column bottom to top: 7e8. This is the bundling demo from §4 again: each row ties the current column into bundles of 16 and leaves the remainder behind.

7.3Both directions in code

convert.py
DIGIT_SYMBOLS = "0123456789abcdefghijklmnopqrstuvwxyz"


def to_base(number: int, base: int) -> str:
    """Write a non-negative integer in the given base (2..36)."""
    if not 2 <= base <= 36:
        raise ValueError("base must be in 2..36")
    if number < 0:
        raise ValueError("number must be non-negative")
    if number == 0:
        return "0"
    digits: list[str] = []
    while number > 0:
        number, digit = divmod(number, base)
        digits.append(DIGIT_SYMBOLS[digit])  # least significant digit first
    return "".join(reversed(digits))


def from_base(text: str, base: int) -> int:
    """Read a digit string in the given base, using Horner's rule."""
    value = 0
    for symbol in text.lower():
        digit = DIGIT_SYMBOLS.index(symbol)
        if digit >= base:
            raise ValueError(f"digit {symbol!r} is not allowed in base {base}")
        value = value * base + digit
    return value


if __name__ == "__main__":
    for number, base in [(2024, 2), (2024, 3), (2024, 8), (2024, 16), (2024, 36), (0, 7)]:
        written = to_base(number, base)
        assert from_base(written, base) == number
        assert int(written, base) == number  # agrees with Python's built-in parser
        print(f"{number:>4} in base {base:>2} = {written}")

7.4A second way to write: peel off the biggest power

Repeated division produces digits from the right. You can also produce them from the left: find the biggest weight \(\cw{b^{k}} \le \cn{n}\), take as many copies of it as fit (that's the leading digit, and it is at most \(\cb{b}-1\), or the next weight would also fit), subtract, and repeat with the next smaller weight. For binary every “as many as fit” is 0 or 1, so this is the familiar mental method: \(45 = 32 + 8 + 4 + 1\), so \(45 = 101101_2\). It needs the powers ahead of time, which is fine in your head for binary and awkward elsewhere. Division needs nothing but divmod.

Two classic bugs

(1) Forgetting to reverse: repeated division yields \(\cd{d_0}\) first, so appending to a string produces the digits backwards. (2) Forgetting zero: the while number > 0 loop never runs for 0 and returns an empty string. Both are in the code above for a reason: the explicit if number == 0 and the final reversed.

8Why every number has exactly one name

So far we've been trusting two things: that the bundling always produces some digit string, and that no other digit string could also add up to the same number. Here are the proofs. Both are short, and both are the division theorem in disguise.

Theorem (positional representation)

Let \(\cb{b} \ge 2\). Every integer \(\cn{n} \ge 1\) can be written as \(\cn{n} = \sum_{i=0}^{k-1}\cd{d_i}\cw{b^i}\) with digits \(0 \le \cd{d_i} \le \cb{b} - 1\) and leading digit \(\cd{d_{k-1}} \ne 0\), and this representation is unique. (Zero is written 0 by convention.)

8.1Existence, by strong induction

Strong induction lets us assume the claim for every number smaller than \(\cn{n}\) while proving it for \(\cn{n}\).

  1. Divide: \(\cn{n} = q\,\cb{b} + \cc{r}\) with \(0 \le \cc{r} < \cb{b}\) (division theorem).
  2. If \(q = 0\), then \(\cn{n} = \cc{r}\) is a single non-zero digit (non-zero because \(\cn{n} \ge 1\)). Done.
  3. Otherwise \(1 \le q\), and \(q < \cn{n}\): since \(\cb{b} \ge 2\), \(q \le \cn{n}/\cb{b} \le \cn{n}/2 < \cn{n}\). By the induction hypothesis \(q = \sum_{i=0}^{m-1} e_i\cb{b}^i\) with \(e_{m-1} \ne 0\).
  4. Substitute: \(\cn{n} = \cb{b}\sum_{i=0}^{m-1} e_i\cb{b}^{i} + \cc{r} = \sum_{i=0}^{m-1} e_i\cb{b}^{i+1} + \cc{r}\cb{b}^0\). That's a valid representation with digits \(e_{m-1}, \dots, e_0, \cc{r}\) and non-zero leading digit. Done.

This proof is the writing algorithm. Step 3 is the recursive call, and the requirement \(\cb{b} \ge 2\) is what makes it terminate. With \(\cb{b} = 1\), \(q = n\) and the recursion never shrinks. That's the formal reason “base 1” isn't a positional system.

8.2Uniqueness

Suppose \(\sum_{i} \cd{d_i}\cb{b}^i = \sum_i e_i \cb{b}^i\), both with digits in \([0, \cb{b})\). Pad the shorter one with leading zeros so both have the same length. Pull out the last term on each side:

\[ \Bigl(\sum_{i\ge1} \cd{d_i}\cb{b}^{i-1}\Bigr)\cdot\cb{b} + \cd{d_0} \;=\; \Bigl(\sum_{i\ge1} e_i\cb{b}^{i-1}\Bigr)\cdot\cb{b} + e_0. \]

Both sides have the form \(q\cdot\cb{b} + r\) with \(0 \le r < \cb{b}\). The division theorem says that pair is unique, so \(\cd{d_0} = e_0\) and the two bracketed quotients are equal. The quotients are again numbers written with digits in \([0, \cb{b})\), one digit shorter, so repeat (formally: induct on the length). All digits agree, and after removing padding the two representations are identical. ∎

8.3A second proof by counting

Here's a slicker argument that shows why the digit range has to be exactly \(\{0, \dots, \cb{b}-1\}\). Consider all strings of exactly \(k\) digits, leading zeros allowed.

  • There are \(\cb{b}\) choices per position, so \(\cb{b}^{k}\) strings.
  • Each string's value lies in \([0, \cb{b}^{k} - 1]\): the smallest is all zeros, and the largest is all \((\cb{b}-1)\)s, which is \(\cb{b}^{k} - 1\) by the geometric-series identity.
  • That interval contains exactly \(\cb{b}^{k}\) integers.

So we have a function from \(\cb{b}^k\) strings to \(\cb{b}^k\) values. By existence (§8.1) it hits every value, i.e. it is surjective. A surjection between two finite sets of the same size is automatically a bijection, by pigeonhole: if two strings shared a value, the remaining \(\cb{b}^k - 2\) strings would have to cover \(\cb{b}^k - 1\) values. So it is injective as well: uniqueness for free.

The counting also shows that the digit range can't change. With fewer than \(\cb{b}\) digit values there are fewer strings than values, and some numbers go unnamed. With more, there are more strings than values, and some numbers get two names. Ordinary positional notation sits exactly at the balance point. (The “stranger systems” in §14 change which \(\cb{b}\) digit values are allowed, which is fine, but never how many.)

8.4How many digits?

A number with exactly \(k\) digits (leading digit non-zero) is at least \(\cb{b}^{k-1}\), since the leading term alone is \(\ge 1\cdot\cb{b}^{k-1}\). It is at most \(\cb{b}^{k} - 1\), the all-max string. So

\[ \cn{n}\text{ has exactly } k \text{ digits in base } \cb{b} \iff \cb{b}^{k-1} \le \cn{n} < \cb{b}^{k} \iff k - 1 = \lfloor \log_{\cb{b}} \cn{n} \rfloor. \]
Digit count

For \(\cn{n} \ge 1\): \(\operatorname{digits}_{\cb{b}}(\cn{n}) = \lfloor \log_{\cb{b}} \cn{n} \rfloor + 1\). In binary this is n.bit_length().

Computing this with floating-point logs is a trap. Floating point can't represent \(\log_{10} 1000 = 3\) through math.log(1000, 10) exactly, because that function computes \(\ln 1000 / \ln 10\) with rounding:

digit_count.py
import math


def digit_count_exact(number: int, base: int) -> int:
    """Number of base-`base` digits of a positive integer, using only integer arithmetic."""
    count = 0
    while number > 0:
        number //= base
        count += 1
    return count


def digit_count_float(number: int, base: int) -> int:
    """floor(log_base(number)) + 1, computed with floating point. Looks right, isn't always."""
    return math.floor(math.log(number, base)) + 1


for number in (999, 1000, 1001):
    print(f"{number}: exact={digit_count_exact(number, 10)}  float={digit_count_float(number, 10)}"
          f"  log10 via math.log={math.log(number, 10)!r}")

print("bits of 2**64 - 1:", digit_count_exact(2**64 - 1, 2), "| int.bit_length():", (2**64 - 1).bit_length())

Solution

It doesn't. The uniqueness proof only uses the uniqueness half of the division theorem, and that half holds for \(b = 1\) as well (the remainder is always 0). So in base 1, two digit strings of the same length with equal value are equal. That's true, but empty: the only digit is 0, so for each length there is exactly one string, and its value is 0.

What breaks is existence. No string names 1. The counting proof shows this at a glance: \(1^k = 1\) string of length \(k\) and \(1^k = 1\) value in \([0, 1^k - 1] = \{0\}\). So \(b \ge 2\) is needed for existence, not for uniqueness. Tally marks are not “base 1 with digit 0”. They use the digit set \(\{1\}\) instead, and we'll meet that idea in §14 as bijective numeration.

9Hex, octal and the bk shortcut

Back to the first two puzzles. Why does 0x7e8 need three symbols where binary needs eleven? And how does each digit of chmod 755 hold exactly three switches? Converting between bases normally means a full read and write through the number in the middle. But some pairs of bases are related so closely that you can convert digit group by digit group, with no arithmetic on the whole number at all.

Take the binary number \(1011011110_2\) and group its bits in fours from the right, padding the left with zeros:

\[ \underbrace{0010}_{\cd{2}}\;\underbrace{1101}_{\cd{\mathtt{d}}}\;\underbrace{1110}_{\cd{\mathtt{e}}} \quad\Longrightarrow\quad \mathtt{2de}_{16}. \]

Each 4-bit group is a number from 0 to 15, which is exactly one hex digit. That's the entire conversion. Why does this work?

9.1Why grouping works

Write out the bits of a number with their weights and group the terms in fours:

\[ \begin{aligned} \cn{n} &= (d_0 + 2d_1 + 4d_2 + 8d_3) \\ &+ (d_4 + 2d_5 + 4d_6 + 8d_7)\cdot 2^4 \\ &+ (d_8 + 2d_9 + 4d_{10} + 8d_{11})\cdot 2^8 + \cdots \end{aligned} \]

Since \(2^4 = 16\) and \(2^8 = 16^2\), this reads \(\cn{n} = \cd{h_0} + \cd{h_1}\cw{16} + \cd{h_2}\cw{16^2} + \cdots\), where each \(\cd{h_j}\) is the value of one 4-bit group. A 4-bit group is between 0 and \(1111_2 = 15\), so each \(\cd{h_j}\) is a legal hex digit. By uniqueness (§8) this is the hex representation: no other is possible.

The bk shortcut

If \(\cb{B} = \cb{b}^{k}\), then each base-\(\cb{B}\) digit corresponds to exactly \(k\) base-\(\cb{b}\) digits. To convert, group base-\(\cb{b}\) digits in blocks of \(k\) from the right, or expand each base-\(\cb{B}\) digit into \(k\) base-\(\cb{b}\) digits, padded with leading zeros.

So hex (\(16 = 2^4\)) ↔ binary in groups of 4, octal (\(8 = 2^3\)) ↔ binary in groups of 3, base 9 ↔ base 3 in groups of 2. But decimal ↔ hex has no shortcut, because 16 is not a power of 10 (or vice versa).

Here's the same thing as code:

9.2The puzzles, solved

Puzzle 1. 0x7e8 is 3 hex digits because 2024 has 11 bits, and \(\lceil 11/4 \rceil = 3\). Hex is popular in debuggers and dumps for exactly this reason: it is a lossless compression of binary for human eyes. Every hex digit is one nibble (4 bits), every byte is two hex digits, and a 32-bit word is 8. You can read bit patterns off a hex number without doing any arithmetic, which you cannot do with decimal: from 2024 alone you can't tell which bits are set.

Puzzle 2. Unix permissions are 9 bits, rwx for owner, group and others. Three bits make one octal digit, so octal is the natural notation: \(7 = 111_2\) is rwx, \(5 = 101_2\) is r-x, \(4 = 100_2\) is r--. chmod 755 is the bit string 111 101 101, which is rwxr-xr-x. The octal digits line up with the permission groups because the groups are 3 bits wide.

10Arithmetic in any base

Requirement 3 from §3 asked for mechanical arithmetic directly on names. Positional notation delivers it, and the procedures you learned in school for base 10 work unchanged in any base. Only the single-digit facts (the “times tables”) change, and the carry happens at \(\cb{b}\) instead of 10.

10.1Addition

Line up the columns, which lines up equal weights. Add column by column from the right. Whenever a column sum reaches \(\cb{b}\) or more, it's too big to be a digit, so apply divmod: keep the remainder, and carry the quotient into the next column. With two numbers, a column sum is at most \((\cb{b}-1) + (\cb{b}-1) + 1 = 2\cb{b} - 1\), so the carry is always 0 or 1.

column_add.py
DIGIT_SYMBOLS = "0123456789abcdefghijklmnopqrstuvwxyz"


def add_in_base(left: str, right: str, base: int) -> str:
    """Grade-school column addition, done directly on digit strings, printing each column."""
    width = max(len(left), len(right))
    left, right = left.rjust(width, "0"), right.rjust(width, "0")
    carry = 0
    result_digits: list[str] = []
    for column in range(width - 1, -1, -1):  # rightmost column first
        left_digit = DIGIT_SYMBOLS.index(left[column])
        right_digit = DIGIT_SYMBOLS.index(right[column])
        column_sum = left_digit + right_digit + carry
        print(f"  {left[column]} + {right[column]} + carry {carry} = {column_sum:>2}", end="")
        carry, digit = divmod(column_sum, base)
        print(f" = {carry}*{base} + {digit:>2}  -> write {DIGIT_SYMBOLS[digit]}, carry {carry}")
        result_digits.append(DIGIT_SYMBOLS[digit])
    if carry:
        result_digits.append(DIGIT_SYMBOLS[carry])
    return "".join(reversed(result_digits))

10.2Subtraction

Subtraction is the mirror image. When the top digit is too small, borrow one from the next column. That one is worth \(\cb{b}\) in the current column, because it's one bundle untied. In binary, \(10_2 - 1_2\): the right column is \(0 - 1\), so borrow, making it \(2 - 1 = 1\), and the left column becomes \(1 - 1 = 0\). Result \(1_2\). A run of zeros borrows all the way along, as in \(1000_2 - 1 = 0111_2\), the odometer running backwards. §12 shows how computers sidestep subtraction entirely by adding a complement.

10.3Multiplying and dividing by the base: shifts

Multiplying by \(\cb{b}\) multiplies every weight by \(\cb{b}\): \(\cd{d_i}\cw{b^i} \mapsto \cd{d_i}\cw{b^{i+1}}\). Every digit moves one place left, and a 0 fills position 0. That's why multiplying by 10 “adds a zero” in decimal and why x << k equals \(x\cdot 2^k\) in binary. In the other direction, \(\operatorname{divmod}(\cn{n}, \cb{b})\) chops off the last digit (§7.2), so x >> k is \(\lfloor x / 2^k \rfloor\) and x & (2**k - 1) is the remainder \(x \bmod 2^k\), the low \(k\) bits.

10.4Multiplication

Long multiplication expands \(x \cdot y = x \cdot \sum_j \cd{y_j}\cw{b^j} = \sum_j (x\cdot\cd{y_j})\cdot\cw{b^j}\): multiply \(x\) by each digit of \(y\), shift the partial product left by \(j\) places, and add everything up. In binary each digit \(\cd{y_j}\) is 0 or 1, so each partial product is either 0 or a shifted copy of \(x\). There is no times table at all, which makes binary multiplication pure shift-and-add:

\[ 101_2 \times 11_2 \;=\; 101_2\cdot 1 \;+\; 101_2\cdot 2 \;=\; 101_2 + 1010_2 \;=\; 1111_2. \]

In decimal that's \(5 \times 3 = 5 + 10 = 15\). This is how simple CPUs without a multiplier, and the “Russian peasant” method, compute products. The homework builds schoolbook multiplication for digit lists in any base.

11Digits after the point

Every weight so far has been a positive power of the base. But the powers keep going to the right: \(\dots, \cw{b^2}, \cw{b^1}, \cw{b^0}, \cw{b^{-1}}, \cw{b^{-2}}, \dots\), each one \(\cb{b}\) times smaller than the one before (§2.2). A radix point (decimal point, binary point) marks where position 0 ends. Digits to its right get negative indices:

\[ (\cd{d_{k-1}}\cdots\cd{d_0}\,.\,\cd{d_{-1}}\cd{d_{-2}}\cdots)_{\cb{b}} = \sum_{i} \cd{d_i}\cw{b^{i}}, \]

so for example

\[ 0.101_2 = \cd{1}\cdot\cw{\tfrac12} + \cd{0}\cdot\cw{\tfrac14} + \cd{1}\cdot\cw{\tfrac18} = 0.625. \]

11.1A picture: every digit zooms in by b

Here's the picture worth carrying around. Take the interval \([0, 1)\) and cut it into \(\cb{b}\) equal pieces. The first digit after the point says which piece \(x\) is in. Cut that piece into \(\cb{b}\) pieces again. The second digit says which of those. Each digit narrows down where \(x\) is by a factor of \(\cb{b}\). An infinite digit string is an infinite sequence of nested intervals closing in on a single point.

11.2The algorithm: repeated multiplication

The integer part was written by repeated division, which peels digits off the right. The fraction part is written by repeated multiplication, which pulls digits out from the left. If \(0 \le x < 1\) and \(x = 0.\cd{d_{-1}}\cd{d_{-2}}\cdots\), then multiplying by \(\cb{b}\) shifts the point one place right:

\[ \cb{b}\cdot x = \cd{d_{-1}}\,.\,\cd{d_{-2}}\cd{d_{-3}}\cdots \]

The integer part is the first digit, and the fractional part is “the rest”, ready for the next round. Converting \(0.375\) to binary:

x2xdigit (integer part)rest (fractional part)
0.3750.75\(\cd{0}\)0.75
0.751.5\(\cd{1}\)0.5
0.51.0\(\cd{1}\)0 → stop

So \(0.375 = 0.011_2\). Now try \(0.1\):

The state \(0.2\) has come back, so from here on the digits 0011 repeat forever: \(0.1 = 0.0\overline{0011}_2\). This is puzzle 3: a binary float cannot store one tenth exactly, for the same reason a finite decimal can't store one third. It has to cut the infinite expansion off somewhere, and \(0.1 + 0.2\) then adds two slightly wrong numbers (§13 does the exact accounting).

To run this on a computer without floating-point error, work with an exact fraction \(p/q\) and keep only the integer remainder \(r\) (the fractional part is \(r/q\)). One step is \(\operatorname{divmod}(r\cdot\cb{b}, q) = (\text{digit}, r')\). There are only \(q\) possible remainders, \(0\) to \(q-1\), so within \(q\) steps either the remainder hits 0 (the expansion terminates) or some remainder repeats, and from that point the digits cycle. That's a proof that every rational number has an eventually periodic expansion in every base. The code detects the cycle with a dictionary of remainders seen so far, the same idea as LeetCode 166 (“Fraction to Recurring Decimal”):

fraction_expand.py
from dataclasses import dataclass
from math import gcd

DIGIT_SYMBOLS = "0123456789abcdefghijklmnopqrstuvwxyz"


@dataclass
class Expansion:
    whole_part: int
    prefix_digits: str    # digits after the point that appear once
    repeating_digits: str  # the cycle, empty if the expansion terminates

    def __str__(self) -> str:
        cycle = f"({self.repeating_digits})" if self.repeating_digits else ""
        return f"{self.whole_part}.{self.prefix_digits}{cycle}" if self.prefix_digits or cycle else str(self.whole_part)


def expand_fraction(numerator: int, denominator: int, base: int) -> Expansion:
    """Digits of numerator/denominator in `base`, with the repeating block detected exactly."""
    whole_part, remainder = divmod(numerator, denominator)
    digits: list[str] = []
    first_seen_at: dict[int, int] = {}  # remainder -> index of the digit it is about to produce
    while remainder != 0 and remainder not in first_seen_at:
        first_seen_at[remainder] = len(digits)
        digit, remainder = divmod(remainder * base, denominator)  # shift left by one place, peel a digit
        digits.append(DIGIT_SYMBOLS[digit])
    if remainder == 0:
        return Expansion(whole_part, "".join(digits), "")
    cycle_start = first_seen_at[remainder]
    return Expansion(whole_part, "".join(digits[:cycle_start]), "".join(digits[cycle_start:]))


def terminates(numerator: int, denominator: int, base: int) -> bool:
    """True iff every prime factor of the reduced denominator divides the base."""
    denominator //= gcd(numerator, denominator)
    while (shared := gcd(denominator, base)) > 1:
        denominator //= shared  # strip the primes the denominator shares with the base
    return denominator == 1

    expansion = expand_fraction(numerator, denominator, base)
    print(f"{numerator}/{denominator:<2} in base {base:>2}: {str(expansion):<14} terminates={terminates(numerator, denominator, base)}")

11.3Which fractions terminate?

The output above hints at the rule: \(\tfrac{1}{10}\) terminates in base 10 but not in base 2, and \(\tfrac13\) terminates in base 3 but not in base 10. Let's derive it.

A base-\(\cb{b}\) expansion with \(k\) digits after the point is some integer divided by \(\cb{b}^k\), e.g. \(0.375 = 375/10^3\) and \(0.011_2 = 3/2^3\). So the fraction \(p/q\), in lowest terms, terminates within \(k\) digits exactly when \(\frac{p}{q}\cdot\cb{b}^k\) is an integer, that is, when \(q\) divides \(p\cdot\cb{b}^k\). Because \(p\) and \(q\) share no common factor, this is the same as \(q\) dividing \(\cb{b}^k\). And some power of \(\cb{b}\) is divisible by \(q\) exactly when every prime factor of \(q\) is also a prime factor of \(\cb{b}\) (raise \(\cb{b}\) to a high enough power to cover the multiplicities).

Termination rule

A fraction \(p/q\) in lowest terms has a terminating expansion in base \(\cb{b}\) iff every prime factor of \(q\) divides \(\cb{b}\). Otherwise the expansion is eventually periodic.

  • Base 10 \(= 2\cdot 5\): \(\tfrac12, \tfrac14, \tfrac15, \tfrac18, \tfrac1{20}, \tfrac{1}{40}\) terminate. \(\tfrac13, \tfrac16, \tfrac17\) repeat.
  • Base 2: only denominators that are powers of 2 terminate. \(\tfrac1{10}\) has the factor 5, so it repeats. That's why 0.5 + 0.25 == 0.75 is exact in floating point but 0.1 + 0.2 == 0.3 isn't.
  • Base 12 \(= 2^2\cdot 3\) and base 60 \(= 2^2\cdot3\cdot5\): thirds terminate. \(\tfrac13 = 0.4_{12}\), and \(\tfrac13\) hour is exactly 20 minutes. That convenience is a large part of why Babylonian astronomers' base 60 survives in our clocks and angles.

11.4From a repeating expansion back to a fraction

Use the geometric series. A block \(D\) of \(p\) digits repeating forever, \(0.\overline{D}\), means \(D\cdot\cb{b}^{-p} + D\cdot\cb{b}^{-2p} + \dots = D\cdot \frac{\cb{b}^{-p}}{1 - \cb{b}^{-p}} = \frac{D}{\cb{b}^{p} - 1}\). In words: put the block over as many copies of the largest digit as it has digits.

\[ \begin{aligned} 0.\overline{142857} &= \frac{142857}{999999} = \frac17, \\[4pt] 0.\overline{0011}_2 &= \frac{0011_2}{1111_2} = \frac{3}{15} = \frac15, \\[4pt] 0.0\overline{0011}_2 &= \frac12\cdot\frac15 = \frac1{10}. \end{aligned} \]

A non-repeating prefix just shifts things, as in the last example, where one leading 0 halves the value. And the all-max block \(0.\overline{(\cb{b}-1)}\) gives \(\frac{\cb{b}-1}{\cb{b}-1} = 1\): every base has its own \(0.999\ldots = 1\) (in binary, \(0.111\ldots_2 = 1\)). Real numbers with a terminating expansion have exactly two names, and every other real number has one.

Extension: how long is the cycle?

For \(q\) sharing no factor with \(\cb{b}\), the period of \(1/q\) is the smallest \(p \ge 1\) with \(\cb{b}^{p} \equiv 1 \pmod q\) (the multiplicative order of \(\cb{b}\) mod \(q\)). The reason: the expansion is purely periodic with period \(p\) iff \(1/q = D/(\cb{b}^p - 1)\) for an integer \(D\), iff \(q \mid \cb{b}^p - 1\). For prime \(q\), Fermat's little theorem says \(\cb{b}^{q-1} \equiv 1\), so the period divides \(q - 1\). \(\tfrac17\) attains the maximum, 6, in base 10. Each of \(\tfrac17, \tfrac27, \dots, \tfrac67\) is a rotation of 142857.

12Negative numbers in fixed width

On paper a negative number is just a minus sign in front of its digits. Hardware doesn't have a minus sign. A register is exactly \(k\) bits, which is \(2^{k}\) patterns, and we have to decide which patterns mean which numbers. The goal is to make the adder circuit, which we already have from §10, keep working without changes.

12.1Two near misses

Sign-magnitude. Spend the top bit on the sign and use the rest as a normal binary magnitude, so with 4 bits 0101 = +5 and 1101 = −5. That's easy to read, but there are two zeros (0000 and 1000), and addition needs case analysis: adding numbers of opposite signs means subtracting the magnitudes and choosing the sign. The plain adder gives \(0101 + 1101 = 10010\), which truncates to 0010 = +2 instead of 0. (Floating point still uses sign-magnitude, as we'll see in §13.)

Ones' complement. Negate by flipping every bit: −5 = 1010. Flipping turns \(x\) into \((2^k - 1) - x\), since every bit becomes \(1 - d_i\) and no borrows occur. That's close to working, but there are still two zeros (0000 and 1111), and addition needs an “end-around carry” fix-up. Old machines such as the CDC 6600 and the PDP-1 used it.

12.2Two's complement: give the top bit a negative weight

Here's the positional way to see the winning idea. Keep ordinary binary weights for every bit except the top one, and give the top bit the weight \(\cw{-2^{k-1}}\) instead of \(+2^{k-1}\):

Equivalently: a pattern whose unsigned value is \(U\) means \(U\) if the top bit is 0 and \(U - 2^{k}\) if it is 1. (Check: the top bit contributes \(+2^{k-1}\) to \(U\) but should contribute \(-2^{k-1}\), a difference of \(2^k\).) So the pattern for a negative \(v\) is the unsigned number \(v + 2^{k}\). For 8 bits, \(-5 \mapsto 251 = \texttt{11111011}\). In both cases:

Two's complement in one line

The \(k\)-bit pattern of \(v\) is \(v \bmod 2^{k}\), written in binary. The range is \([-2^{k-1},\, 2^{k-1} - 1]\): for 8 bits, −128 to 127.

Why the adder just works. An adder with \(k\) output bits throws away the carry out of the top, so it computes \((x + y) \bmod 2^{k}\). The pattern of \(v\) is congruent to \(v\) modulo \(2^{k}\), whether we read it as signed or unsigned. Since \((a \bmod m) + (b \bmod m) \equiv a + b \pmod m\), the adder's output is congruent to the true sum, and if the true sum is in range, it is the pattern of the true sum. The same circuit adds signed and unsigned numbers. The only difference is how you read the result and how you detect overflow. It's a clock with \(2^k\) hours:

12.3Negation: invert and add one

We want the pattern of \(-x\), which is \(2^{k} - x\). Split it as \((2^k - 1) - x + 1\). The first part, \((2^{k}-1) - x\), is the all-ones pattern minus \(x\), and subtracting from all ones never borrows: each bit becomes \(1 - d_i\), so it's just ~x. Then add 1:

\[ -x \equiv \underbrace{(2^{k} - 1) - x}_{\text{every bit of }x\text{ flipped}} + 1 \pmod{2^{k}}. \]

The all-ones pattern is \(2^k - 1 \equiv -1\). That's the geometric-series identity once more: 1111…1 is one less than the next power of two. In code:

twos_complement.py
BIT_WIDTH = 8
MODULUS = 2**BIT_WIDTH  # 256 patterns for 8 bits


def encode(value: int) -> str:
    """Two's complement bit pattern of `value`: just value mod 2^width, written in binary."""
    if not -MODULUS // 2 <= value < MODULUS // 2:
        raise OverflowError(f"{value} does not fit in {BIT_WIDTH} bits")
    return format(value % MODULUS, f"0{BIT_WIDTH}b")


def decode(bits: str) -> int:
    """Top bit has weight -2^(width-1) instead of +2^(width-1)."""
    unsigned = int(bits, 2)
    return unsigned - MODULUS if bits[0] == "1" else unsigned


def negate(bits: str) -> str:
    """Invert every bit, then add one (and drop any carry out of the top)."""
    inverted = "".join("1" if bit == "0" else "0" for bit in bits)
    return format((int(inverted, 2) + 1) % MODULUS, f"0{BIT_WIDTH}b")

12.4Widening: sign extension

To widen a \(k\)-bit value to more bits, copy the top bit into all the new positions. With 0 on top nothing changes. With 1 on top, compare the two weightings. Before, the top bit was worth \(-2^{k-1}\). After widening by one bit, the new top bit is worth \(-2^{k}\) and the old top bit becomes \(+2^{k-1}\), totalling \(-2^{k} + 2^{k-1} = -2^{k-1}\), the same as before. Repeat for each extra bit. So −3 = 1101 (4 bits) = 11111101 (8 bits).

Detour: Python's infinite two's complement

Python integers have no fixed width, yet ~5 == -6 and -1 & 0xff == 255. Python behaves as if every integer were sign-extended forever: \(-1\) is …11111111 with infinitely many ones. Formally, the geometric series \(1 + 2 + 4 + \cdots = \frac{1}{1 - 2} = -1\). That sum diverges over the real numbers, but it is literally true in the 2-adic integers, where high powers of 2 count as “small”. That number system is the natural home of two's complement. bin(-5) prints '-0b101', a sign-magnitude display, but the bitwise operators act on the infinite two's-complement pattern. To see a fixed-width pattern, mask it: format(-5 & 0xff, "08b").

medium12.c Explain why x & -x isolates the lowest set bit of x (as used in Fenwick trees).

Solution

Write \(x = \texttt{a 1 0…0}\): some prefix a, then the lowest 1, then \(t\) zeros. ~x = ~a 0 1…1. Adding 1 to that turns the trailing ones into zeros and the 0 into a 1, carrying no further (the increment rule from §6): -x = ~a 1 0…0. Now AND with \(x\): the prefix gives a & ~a = 0, the lowest-1 position gives 1, and the trailing zeros give 0. So the result is exactly \(2^t\), the lowest set bit.

hard12.d A bug report: “int mid = (low + high) / 2; crashes binary search on huge arrays.” Explain using this section, and explain why low + (high - low) / 2 and Java's (low + high) >>> 1 both fix it.

Solution

With 32-bit ints, low + high can exceed \(2^{31} - 1\) when both are above \(2^{30}\). The sum wraps around the wheel past the signed boundary into the negatives, so mid becomes negative, and indexing the array with it crashes. (This bug sat in the JDK's binarySearch for about nine years, until Joshua Bloch wrote it up in 2006.)

low + (high - low) / 2 never forms a value larger than high, so nothing wraps. (low + high) >>> 1 lets the addition wrap but then reads the 32-bit pattern as unsigned. Because addition is the same circuit for both readings, the pattern is the correct unsigned sum (it is below \(2^{32}\), since both inputs are below \(2^{31}\)). A logical right shift divides that unsigned value by 2, and the result is below \(2^{31}\), so it is also a valid non-negative signed int.

13Floating point: scientific notation in base 2

Fixed-width integers can't hold \(6.02\times10^{23}\) or \(1.6\times10^{-19}\). Scientists solved this long before computers: write a few significant digits (the significand) and a separate exponent that says where the point goes. The point “floats”. Floating point is exactly that, in base 2, packed into a fixed number of bits. With everything we've built, it decodes in a few lines.

13.1Normalised binary scientific notation

Any non-zero real number can be written as \(\pm\,\cd{1.f}_2 \times \cw{2^{e}}\): slide the binary point until exactly one non-zero digit sits to its left. In decimal that leading digit could be 1–9, but in binary the only non-zero digit is 1. So the leading digit is always 1, and storing it would waste a bit. IEEE 754 leaves it out (the “hidden bit”) and stores only the fraction \(\cd{f}\).

\[ -6.5 = -110.1_2 = -\cd{1.101}_2\times \cw{2^{2}}, \qquad 0.1 = 0.0\overline{0011}_2 = \cd{1.\overline{1001}}_2\times\cw{2^{-4}}. \]

13.2The bit layout

A 64-bit double (Python's float) stores three fields:

  • sign \(s\): 1 bit, 0 for positive. This is sign-magnitude (§12.1), which is why -0.0 exists.
  • exponent \(E\): 11 bits, stored biased: the true exponent is \(e = E - 1023\). Biasing (instead of two's complement) makes the bit patterns of positive floats sort in the same order as their values. \(E = 0\) and \(E = 2047\) are reserved for zero/subnormals and infinity/NaN.
  • fraction \(f\): 52 bits, the binary digits after the hidden leading 1.
\[ \text{value} = (-1)^{s}\times \cd{1.f}_2 \times \cw{2^{E - 1023}} = (-1)^s \times \Bigl(1 + \frac{\cd{f}}{2^{52}}\Bigr)\times \cw{2^{E-1023}}. \]

A 32-bit float uses the same scheme with an 8-bit exponent (bias 127) and a 23-bit fraction. The demo uses 32 bits so all of them fit on screen.

13.3Decoding by hand

Take −6.5. In binary \(6.5 = 4 + 2 + \tfrac12 = 110.1_2\). Normalise by moving the point two places left: \(1.101_2\times 2^{2}\). So \(s = 1\), \(E = 2 + 1023 = 1025\), and \(f\) is 101 followed by 49 zeros. Python agrees:

float_decode.py
import struct
from dataclasses import dataclass
from decimal import Decimal
from fractions import Fraction


@dataclass
class DoubleParts:
    sign_bit: int
    exponent_bits: int   # 11 bits, stored with a bias of 1023
    fraction_bits: int   # 52 bits after the implicit leading 1

    def exact_value(self) -> Fraction:
        """The exact rational number these bits stand for (normal numbers only)."""
        assert 0 < self.exponent_bits < 2047, "subnormals, infinities and NaN not handled here"
        significand = 1 + Fraction(self.fraction_bits, 2**52)  # 1.fraction in binary
        power = self.exponent_bits - 1023
        sign = -1 if self.sign_bit else 1
        return sign * significand * Fraction(2) ** power


def split_double(number: float) -> DoubleParts:
    (raw,) = struct.unpack(">Q", struct.pack(">d", number))  # the 64 bits as one integer
    return DoubleParts(raw >> 63, (raw >> 52) & 0x7FF, raw & (2**52 - 1))

13.4Puzzle 3, fully explained

Now we can account for every bit of 0.1 + 0.2 != 0.3:

  1. By §11.3, \(\tfrac1{10}\), \(\tfrac2{10}\) and \(\tfrac3{10}\) all have the prime 5 in the denominator, so none of them has a finite binary expansion. Each one is stored as the nearest double, with 53 significant bits.
  2. 0.1's expansion is \(1.100110011\ldots\) and the bits after the 52nd fraction bit start with 1, so it rounds up. The stored value is \(\frac{3602879701896397}{2^{55}}\), about \(5.55\times10^{-18}\) above \(\tfrac1{10}\). 0.2 is exactly twice that (same bits, exponent one higher), so its error is twice as large and also upward.
  3. The exact sum of the two stored values is \(0.3000000000000000166533\ldots\). Doubles near 0.3 are spaced \(2^{-54} \approx 5.55\times10^{-17}\) apart, and the two nearest are \(0.29999999999999998889\ldots\) (the stored “0.3”) and \(0.30000000000000004440\ldots\). The exact sum sits precisely halfway between them (we checked with Fraction). IEEE 754's default rule breaks ties toward the neighbour whose last significand bit is 0, “round half to even”, and that is the upper one.
  4. So the sum is a different double from the stored 0.3. Python prints the shortest decimal that round-trips to each double, giving 0.30000000000000004 versus 0.3.

Meanwhile, 0.5, 0.25 and 0.75 have denominators 2, 4 and 4. They are exact in binary, and their sum is exact, so 0.5 + 0.25 == 0.75.

How precise is a double?

With 53 significant bits (52 stored plus the hidden 1), neighbouring doubles near \(\cw{2^{e}}\) are \(\cw{2^{e-52}}\) apart: a relative spacing of \(2^{-52}\approx 2.2\times10^{-16}\), so rounding to nearest is off by at most \(2^{-53} \approx 1.1\times 10^{-16}\) relative. That's \(53\log_{10}2 \approx 15.95\) decimal digits. Every integer up to \(2^{53} = 9\,007\,199\,254\,740\,992\) is exact, and past that the gap is 2 and odd integers vanish. (For float32: 24 bits, about 7.2 digits, and integers are exact up to \(2^{24} = 16\,777\,216\).)

hard13.d Explain why reinterpreting the bits of non-negative doubles as 64-bit unsigned integers preserves order (\(x < y \iff \text{bits}(x) < \text{bits}(y)\)), and why that fails for negative doubles.

Solution

For non-negative doubles the sign bit is 0, so the integer is \(E\cdot 2^{52} + f\). Compare two such numbers. If their exponents differ, the one with the larger \(E\) is larger both as a float (every significand lies in \([1, 2)\), so a higher power of 2 always wins) and as an integer (\(E\) sits in the higher bits, and §10.d's comparison rule says higher positions decide). If the exponents are equal, both orders are decided by \(f\). Subnormals (\(E = 0\)) are below every normal number in both orders, and \(+\infty\) (\(E = 2047, f = 0\)) is above everything. This is why the exponent is biased rather than two's complement: a negative exponent stored in two's complement would have its top bit set and sort above the positive ones.

For negative doubles the representation is sign-magnitude: a bigger magnitude means a more negative value, but a bigger integer. So the order is reversed, and also every negative pattern (sign bit 1) is above every positive pattern as an unsigned integer. The standard fix used by radix sorts on floats: if the sign bit is set, flip all bits, otherwise flip only the sign bit.

14Stranger systems

The counting proof in §8.3 had two ingredients: the weights grow by a factor of \(\cb{b}\) per position, and each position offers exactly \(\cb{b}\) digit values. It never needed the digit values to be \(0, 1, \dots, \cb{b}-1\). Change the digit set, the sign of the base, or let the factor vary from position to position, and you get a family of cousins. Each one is useful somewhere.

14.1Balanced ternary: digits −1, 0, +1

Keep base 3, but use digits \(\{-1, 0, +1\}\), written −, 0, +. That's still 3 values per position, so the counting argument goes through, and something lovely happens: every integer, negative ones included, has a unique representation with no sign. \(8 = 9 - 1\) is +0−. \(-8\) is −0+: negating flips every digit, which is cheaper than two's complement's invert-and-add-one. Rounding to the nearest multiple of \(3^k\) is just truncating the last \(k\) digits, because the dropped tail is always at most half a unit.

Converting uses the ordinary algorithm with one twist. A remainder of 2 is not allowed, so write it as \(3 - 1\): emit −1 and carry 1 into the quotient. This is the classic answer to Bachet's weights problem. With weights of 1, 3, 9 and 27 kg and a two-pan balance, you can weigh every whole number from 1 to 40 kg: a + digit puts the weight on the opposite pan from the object, and a − digit puts it on the same pan. In 1958 a team at Moscow State University led by Nikolay Brusentsov built Setun, a production computer that used balanced ternary. About 50 were made.

14.2Negative base: negabinary

Use digits \(\{0, 1\}\) with base \(-2\). The weights are \(1, -2, 4, -8, 16, \ldots\): even positions add and odd positions subtract. Again every integer has a unique sign-free representation: \(-1 = 11_{-2}\) (\(-2 + 1\)), \(2 = 110_{-2}\) (\(4 - 2\)). The conversion is repeated division by \(-2\), with the remainder forced into \(\{0, 1\}\). Python's divmod(n, -2) returns a remainder in \(\{-1, 0\}\), so when it's \(-1\) we add 2 to the remainder and 1 to the quotient. Vittorio Grünwald described negative bases in 1885. Zdzisław Pawlak and A. Wakulicz studied them in 1957, and Polish machines of that era (BINEG, UMC) actually computed in negabinary.

14.3Bijective numeration: no zero digit (puzzle 4)

Now use digits \(\{1, 2, \dots, \cb{k}\}\) instead of \(\{0, \dots, \cb{k}-1\}\): still \(\cb{k}\) values, but with no zero. The weights are the usual \(\cb{k}^i\). Spreadsheet columns are exactly bijective base 26 with A = 1, …, Z = 26. That solves puzzle 4: Z is a digit (26), not “10”, so the column after Z is the smallest two-digit name, \(\mathrm{AA} = 1\cdot 26 + 1 = 27\). There's no column “A0” because there's no zero digit.

Without a zero there's no placeholder and no leading zeros, so every digit string, including every string of a given length, names a different positive integer. The \(\cb{k}^{\ell}\) strings of length \(\ell\) cover the next block of integers after the shorter strings. To convert, shift the digits down to 0-based before each division: \(\operatorname{divmod}(n - 1, 26)\) gives a remainder in \(0..25\), which is the digit minus one. This is LeetCode 168 (“Excel Sheet Column Title”), and the “−1” is the whole trick. With \(\cb{k} = 1\) you get the only base-1 system that works: one digit, “1”, and the number \(n\) is written as \(n\) ones. Tally marks are bijective base 1.

14.4Mixed radix: clocks and factorials

Finally, let the factor change from position to position. In mixed radix with radices \(r_0, r_1, r_2, \dots\), position \(i\) holds a digit in \([0, r_i - 1]\) and has weight \(w_i = r_0 r_1\cdots r_{i-1}\). You use one every day: seconds (radix 60), minutes (60), hours (24), days. The conversion is the same divmod loop with a different divisor at each step, and reading back is Horner with the radices in reverse:

Existence and uniqueness go through exactly as in §8, because the key bound still holds: the all-max digits below position \(i\) sum to \(w_i - 1\). For a single base that was the geometric series. For mixed radix it telescopes: \(\sum_{j<i} (r_j - 1)w_j = \sum_{j<i} (w_{j+1} - w_j) = w_i - w_0 = w_i - 1\).

The prettiest mixed radix is the factorial number system: radices \(1, 2, 3, 4, \dots\), so weights \(0!, 1!, 2!, 3!, \dots\), with the digit at position \(i\) in \([0, i]\). Telescoping gives \(\sum_{i=1}^{m} i\cdot i! = (m+1)! - 1\). Its killer application is ranking permutations. There are \(n!\) permutations of \(n\) items, and the factorial-base digits of a rank \(0 \le r < n!\) say, item by item, which of the remaining items to pick next. That's LeetCode 60 (“Permutation Sequence”) without generating any permutations:

exotic.py
from math import factorial


def to_balanced_ternary(number: int) -> str:
    """Digits -1, 0, +1 written as '-', '0', '+'. Works for negative numbers with no sign."""
    if number == 0:
        return "0"
    digits: list[str] = []
    while number != 0:
        remainder = number % 3          # 0, 1 or 2
        if remainder == 2:              # 2 = 3 - 1: write -1 and carry one into the next place
            digits.append("-")
            number = number // 3 + 1
        else:
            digits.append("0+"[remainder])
            number //= 3
    return "".join(reversed(digits))


def to_negabinary(number: int) -> str:
    """Base -2, digits 0 and 1. The remainder is forced into {0, 1} even when dividing negatives."""
    if number == 0:
        return "0"
    digits: list[str] = []
    while number != 0:
        quotient, remainder = divmod(number, -2)  # Python gives remainder in {-1, 0}
        if remainder < 0:
            quotient, remainder = quotient + 1, remainder + 2
        digits.append(str(remainder))
        number = quotient
    return "".join(reversed(digits))


def to_spreadsheet_column(column_number: int) -> str:
    """Bijective base 26: digits A..Z mean 1..26, there is no zero digit. 1 -> A, 26 -> Z, 27 -> AA."""
    letters: list[str] = []
    while column_number > 0:
        column_number, remainder = divmod(column_number - 1, 26)  # shift digits 1..26 down to 0..25
        letters.append(chr(ord("A") + remainder))
    return "".join(reversed(letters))


def kth_permutation(items: list[str], rank: int) -> list[str]:
    """Rank 0 is the sorted order. The factorial-base digits of `rank` pick each next item."""
    remaining = sorted(items)
    picked: list[str] = []
    for position in range(len(items) - 1, -1, -1):
        index, rank = divmod(rank, factorial(position))  # this digit has weight position!
        picked.append(remaining.pop(index))
    return picked

easy14.a What is +−0+ in balanced ternary? What is its negation?

Solution

easy14.b Which spreadsheet column number is CB? Which column title is number 702?

Solution

medium14.c Read \(11011_{-2}\). Then write \(-3\) in negabinary.

Solution

Weights from the right: 1, −2, 4, −8, 16. \(16 - 8 + 0 - 2 + 1 = 7\).

For −3: \(\operatorname{divmod}(-3, -2)\) in Python is \((1, -1)\). The remainder is negative, so adjust to quotient 2, remainder 1. Then \(\operatorname{divmod}(2, -2) = (-1, 0)\): remainder 0. Then \(\operatorname{divmod}(-1, -2) = (0, -1)\), adjusted to quotient 1, remainder 1. Then \(\operatorname{divmod}(1, -2) = (-1, -1)\), adjusted to quotient 0, remainder 1. hard14.e Prove that every integer has a balanced-ternary representation. (Uniqueness is similar, so skip it.)

Hint

Mimic §8.1, but choose the remainder in \(\{-1, 0, 1\}\). Then check that the quotient shrinks in absolute value.

Solution

Every integer \(n\) can be written as \(n = 3q + r\) with \(r \in \{-1, 0, 1\}\): take the ordinary remainder in \(\{0, 1, 2\}\), and if it is 2, use \(r = -1\) and \(q + 1\) instead. Strong induction on \(|n|\): \(n = 0\) is “0”. For \(n \ne 0\), if \(q = 0\) then \(n = r\) is a single digit. Otherwise \(|q| = |n - r|/3 \le (|n| + 1)/3 < |n|\) for \(|n| \ge 1\). By hypothesis \(q\) has a representation, and appending the digit \(r\) gives one for \(n\). This is exactly the to_balanced_ternary loop. The key property is that \(\{-1, 0, 1\}\) contains one representative of each remainder class mod 3, just as \(\{0, 1, 2\}\) does.

15Pitfalls

Every item here has appeared somewhere above. Collected in one place, they make a checklist for code review.

  • Digits come out backwards. Repeated division yields the least significant digit first. Reverse at the end, or prepend.
  • Zero is a special case. while n > 0 loops produce an empty string for 0.
  • Group from the right. When converting binary ↔ hex/octal, groups line up with the weights, which start at position 0 on the right. Pad on the left.
  • Negative remainders. % in C, C++, Java, JavaScript, Go and Rust takes the sign of the dividend: -7 % 3 == -1. Python, Ruby and Haskell's mod take the sign of the divisor. Base conversion of negatives, hash bucketing and “wrap an index around” all break in the first group of languages unless you fix up the sign.
  • Floating-point logs at boundaries. floor(log(n, b)) + 1 is wrong for some exact powers (it says 1000 has 3 digits). Use integer methods.
  • A leading zero means octal in C, C++, and JavaScript's legacy syntax: 010 == 8.
  • Symbol vs value. The character '7' is code point 55, not 7. ord(c) - ord('0') works for 0–9 only, and hex letters need their own case.
  • Terminating in decimal doesn't mean terminating in binary. Any denominator with a factor of 5 repeats in binary, so never store money in binary floats. Use integer cents or decimal.Decimal.
  • Never compare floats with == after arithmetic. Use a tolerance (math.isclose) or exact types.
  • Two's complement is lopsided. \(-\)INT_MIN overflows back to INT_MIN. abs of it stays negative. Signed overflow is undefined behaviour in C/C++.
  • (low + high) / 2 overflows in fixed-width languages. Use low + (high - low) / 2.
  • Off by one in bijective systems. Spreadsheet columns need divmod(n - 1, 26), not divmod(n, 26).
  • Python's display is not the bit pattern. bin(-5) == '-0b101' shows sign and magnitude. Mask with & 0xff… to see a fixed-width two's-complement pattern.
  • Byte order is not number base. A 32-bit integer is a 4-digit number in base 256. Endianness is just the order in which those four digits are stored in memory: little-endian puts the least significant byte first, so 0x12345678 is stored as 78 56 34 12. The value is the same, and only the storage order of the digits differs.

16Cheat sheet

1 · The definition

\(\cn{n} = \sum_i \cd{d_i}\cw{b^i}\), digits \(0 \le \cd{d_i} < \cb{b}\). Position = exponent. Each column is a bundle \(\cb{b}\) times bigger than the one to its right. Zero is a placeholder. A numeral is a polynomial evaluated at \(x = \cb{b}\), and carries keep its coefficients in digit range.

2 · Conversion

Read (digits → number): Horner, value = value*b + digit, left to right.
Write (number → digits): repeat n, digit = divmod(n, b), digits come out right to left.
Fractions: repeat digit, r = divmod(r*b, q), digits come out left to right, and a repeated remainder means a cycle.
\(\cb{B} = \cb{b}^k\): group \(k\) digits at a time from the right (hex = 4 bits, octal = 3).

3 · Why it works

The division theorem (unique \(q\), \(r\) with \(0\le r<b\)) gives both existence and uniqueness. Strings of length \(k\): \(\cb{b}^k\) of them for \(\cb{b}^k\) values. All-max digits equal \(\cb{b}^k - 1\). Digit count is \(\lfloor\log_{\cb{b}} \cn{n}\rfloor + 1\), and binary is about 3.32× as long as decimal.

4 · Fractions

\(p/q\) (lowest terms) terminates in base \(\cb{b}\) iff every prime factor of \(q\) divides \(\cb{b}\). Otherwise the expansion is eventually periodic, and \(0.\overline{D} = D/(\cb{b}^p - 1)\). 0.1 is 0.0(0011) in binary, so it is inexact in floats.

5 · Machines

Two's complement: the pattern of \(v\) is \(v \bmod 2^k\), the top weight is \(-2^{k-1}\), \(-x\) = ~x + 1, the range is \([-2^{k-1}, 2^{k-1}-1]\), and widening copies the sign bit.
IEEE 754 double: \((-1)^s\cdot 1.f\cdot 2^{E-1023}\), 1/11/52 bits, 53 significant bits ≈ 15.95 digits, integers exact up to \(2^{53}\).

6 · Cousins

Same rules, other digit sets or weights: balanced ternary \(\{-1,0,1\}\) and base −2 handle negatives with no sign. Bijective base \(k\) uses digits \(1..k\) (spreadsheet columns, and tally marks are base 1). Mixed radix (clocks, factorial base for permutation ranks) has weights \(w_{i+1} = r_i w_i\).

easyQ1 Convert 0x1F4 to decimal, and 100 to base 3.

Solution

Horner: \(1 \to 1\cdot16 + 15 = 31 \to 31\cdot 16 + 4 = 500\). For 100 in base 3: 100 = 33·3 + 1, 33 = 11·3 + 0, 11 = 3·3 + 2, 3 = 1·3 + 0, 1 = 0·3 + 1, so reading upward \(10201_3\). Check: \(81 + 18 + 1 = 100\) ✓.

easyQ2 A base-7 odometer shows 0666. What does it show after one more step, and why is that the geometric-series identity?

Solution

1000. \(666_7 = 6(1 + 7 + 49) = (7 - 1)\cdot\frac{7^3 - 1}{7 - 1} = 7^3 - 1 = 342\). Adding 1 gives \(7^3 = 1000_7\).

mediumQ3 In which base does the numeral 31 denote thirteen? Is there a base where 31 denotes six?

Solution

\(31_b = 3b + 1 = 13\) gives \(b = 4\), and the digit 3 is legal in base 4 ✓. For six: \(3b + 1 = 6\) has no integer solution, and even \(b = 5/3\) isn't a base. The common slip is to forget the legality check: a solution \(b \le 3\) would be invalid because the digit 3 must be smaller than the base.

mediumQ4 How many hex digits does the largest unsigned 64-bit integer have, and what is it in hex? How many decimal digits does it have? Use \(\log_{10} 2 \approx 0.30103\).

Solution

64 bits / 4 = 16 hex digits, all max: ffffffffffffffff = \(2^{64} - 1\). Decimal: \(\lfloor 64\cdot 0.30103 \rfloor + 1 = \lfloor 19.27\rfloor + 1 = 20\) digits (it's 18446744073709551615). Applying the log formula to \(2^{64}-1\) instead of \(2^{64}\) is safe here, because \(2^{64}\) is not a power of 10, so subtracting 1 can't cross a digit boundary.

mediumQ5 Which of these terminate in base 6: \(\tfrac13\), \(\tfrac14\), \(\tfrac15\), \(\tfrac{1}{36}\)? Write out the terminating ones.

Solution

\(6 = 2\cdot 3\). \(\tfrac13 = 2/6 = 0.2_6\) ✓. \(\tfrac14 = 9/36 = (1\cdot 6 + 3)/36 = 0.13_6\) ✓. \(\tfrac15\) repeats (5 does not divide 6). \(\tfrac1{36} = 0.01_6\) ✓.

mediumQ6 Which of these are stored exactly as doubles: 0.1, 0.375, \(\tfrac13\), \(2^{60}\), \(2^{60} + 1\), \(-0.0\)?

Solution

Exact: 0.375 (\(= 3/8\), a dyadic fraction), \(2^{60}\) (one significant bit), and \(-0.0\) (a real encoding with the sign bit set). Inexact: 0.1 (factor 5 in the denominator), \(\tfrac13\) (factor 3), and \(2^{60} + 1\) (61 significant bits, more than 53). The tempting mistake is to think “integers are always exact”. They are only exact up to \(2^{53}\).

mediumQ7 In 8-bit two's complement, compute \(-(-128)\), \(127 + 1\), and the 16-bit sign extension of 0xF0.

Solution

\(-(-128)\): invert 10000000 → 01111111, add 1 → 10000000 = −128 again. \(127 + 1\): 01111111 + 1 = 10000000 = −128 (signed overflow). Sign-extending 0xF0 (top bit 1, value −16) to 16 bits gives 0xFFF0, which is still −16.

mediumQ8 Write 25 in balanced ternary and \(-1\) in negabinary.

Solution

25: 25 mod 3 = 1, so digit +, quotient 8. 8 mod 3 = 2, so digit − and quotient \(2 + 1 = 3\). 3 mod 3 = 0, so digit 0, quotient 1. 1 gives digit +. Reading upward: +0−+ = \(27 + 0 - 3 + 1 = 25\) ✓. \(-1\) in negabinary is \(11_{-2} = -2 + 1\).

mediumQ9 Why is there no digit-grouping shortcut between decimal and hex, while there is one between base 9 and base 27?

Solution

Grouping works between \(b\) and \(b^k\), and more generally between two bases that are both powers of a common base: \(9 = 3^2\) and \(27 = 3^3\). Go 9 → 3 (each digit becomes 2 trits), then 3 → 27 (groups of 3 trits), using groups of 6 trits = 3 base-9 digits = 2 base-27 digits. 10 and 16 are not powers of a common integer (\(10 = 2\cdot5\) and \(16 = 2^4\)), so no block of decimal digits lines up with a block of hex digits: \(10^a = 16^c\) is impossible for positive \(a, c\) because of the factor 5.

mediumQ10 On a little-endian machine, the 4 bytes at an address are e8 07 00 00. What 32-bit unsigned integer is stored there?

Solution

Little-endian stores the least significant base-256 digit first, so the number is 0x000007e8 = 2024. (The hex digits within a byte don't get reversed, only the order of the bytes.)

hardQ11 Prove that a number is divisible by 9 iff the sum of its decimal digits is. Then state and prove the analogous rule for 15 in hex, and for 11 in decimal.

Hint

\(10 \equiv 1 \pmod 9\). What is \(16\) mod 15, and \(10\) mod 11?

Solution

\(10 \equiv 1 \pmod 9\), so \(10^i \equiv 1^i = 1\), hence \(n = \sum d_i 10^i \equiv \sum d_i \pmod 9\). In particular \(9 \mid n \iff 9 \mid \sum d_i\) (this is “casting out nines”). It works because \(9 = b - 1\).

In hex, \(16 \equiv 1 \pmod{15}\), so a number is divisible by 15 iff its hex digit sum is (and likewise for 3 and 5, the divisors of 15). Example: 0x2d = 45, digit sum \(2 + 13 = 15\) ✓.

For 11: \(10 \equiv -1 \pmod{11}\), so \(10^i \equiv (-1)^i\) and \(n \equiv d_0 - d_1 + d_2 - \cdots\). Divisible by 11 iff the alternating digit sum is. Example: 918082: \(2 - 8 + 0 - 8 + 1 - 9 = -22\), so it's divisible (918082 = 11 · 83462). Both rules are “evaluate the digit polynomial at \(x \equiv b\)” with a smarter representative of \(b\) mod the divisor.

hardQ12 Find the bug: a function rounds a positive float to 2 decimal places with math.floor(x * 100 + 0.5) / 100. For which kind of input does it give a surprising answer, and why?

Solution

Inputs whose decimal form ends in 5 in the third place, like 1.005, are not stored exactly. 1.005 is stored as 1.00499999999999989341858963598497211933135986328125, slightly below the halfway point. The multiplication 1.005 * 100 rounds again and gives 100.49999999999999. Adding 0.5 and flooring yields 100, so the function returns 1.0 instead of the expected 1.01.

It's not consistent either. 2.675 is also stored slightly below halfway (2.67499999999999982…), yet this formula returns 2.68, because here the multiplication happens to round up to exactly 267.5. Python's built-in round(2.675, 2), which rounds the exact stored value correctly, returns 2.67. The real bug is the assumption that the input is the decimal number you typed. When you need decimal rounding semantics, use decimal arithmetic: Decimal("1.005").quantize(Decimal("0.01"), ROUND_HALF_UP) gives 1.01.

Hint

For multiplication, accumulate every product \(x_i y_j\) into column \(i + j\) first, then do a single carry pass from the bottom, which is the “polynomial, then carry” view from §5.3.

Solution
hw_digits.py
import random

Digits = list[int]  # least significant digit first: [3, 0, 2, 5] is 5203 in base 10


def to_digits(number: int, base: int) -> Digits:
    digits: Digits = []
    while number > 0:
        number, digit = divmod(number, base)
        digits.append(digit)
    return digits


def from_digits(digits: Digits, base: int) -> int:
    value = 0
    for digit in reversed(digits):
        value = value * base + digit
    return value


def add_digits(left: Digits, right: Digits, base: int) -> Digits:
    result: Digits = []
    carry = 0
    for position in range(max(len(left), len(right))):
        column_sum = carry
        column_sum += left[position] if position < len(left) else 0
        column_sum += right[position] if position < len(right) else 0
        carry, digit = divmod(column_sum, base)
        result.append(digit)
    if carry:
        result.append(carry)
    return result


def multiply_digits(left: Digits, right: Digits, base: int) -> Digits:
    """Schoolbook multiplication: every digit pair lands in column i + j, then one carry pass."""
    columns = [0] * (len(left) + len(right))
    for left_position, left_digit in enumerate(left):
        for right_position, right_digit in enumerate(right):
            columns[left_position + right_position] += left_digit * right_digit
    result: Digits = []
    carry = 0
    for column_total in columns:
        carry, digit = divmod(column_total + carry, base)
        result.append(digit)
    while carry:
        carry, digit = divmod(carry, base)
        result.append(digit)
    while result and result[-1] == 0:  # strip leading zeros (they sit at the end of the list)
        result.pop()
    return result


random.seed(1)
for _ in range(2000):
    base = random.randint(2, 40)
    left_number, right_number = random.randrange(10**30), random.randrange(10**30)
    left, right = to_digits(left_number, base), to_digits(right_number, base)
    assert from_digits(add_digits(left, right, base), base) == left_number + right_number
    assert from_digits(multiply_digits(left, right, base), base) == left_number * right_number
print("2000 random add/multiply checks passed")
print("5203 * 17 in base 10:", multiply_digits([3, 0, 2, 5], [7, 1], 10), "=", 5203 * 17)

With \(b = 2^{30}\), each digit holds 30 bits, so a 3000-bit number has 100 digits instead of about 900 decimal digits, and multiplication does roughly 80× fewer digit operations. The base is a power of two so that divmod by \(b\) is a shift and a mask, and 30 bits (CPython's choice) leaves room for a digit product plus carries to fit in a 64-bit machine word. Decimal bases are used only when printing in decimal is the dominant operation.

import random
import struct
from fractions import Fraction


def encode_float32(value: Fraction) -> int:
    """Bits of the float32 nearest to a positive `value`, ties to even. Normal range only."""
    assert value > 0
    exponent = value.numerator.bit_length() - value.denominator.bit_length()
    if Fraction(2) ** exponent > value:  # make 2^exponent <= value < 2^(exponent+1)
        exponent -= 1
    assert -126 <= exponent <= 127, "subnormal or overflow: not handled in this sketch"
    scaled = value / Fraction(2) ** exponent * 2**23  # in [2^23, 2^24): 24 significant bits
    significand = scaled.numerator // scaled.denominator
    leftover = scaled - significand  # in [0, 1)
    if leftover > Fraction(1, 2) or (leftover == Fraction(1, 2) and significand % 2 == 1):
        significand += 1
    if significand == 2**24:  # rounding carried into a new bit: 1.111...1 -> 10.000...0
        significand //= 2
        exponent += 1
    return ((exponent + 127) << 23) | (significand - 2**23)

Solution

TRIT_VALUE = {"-": -1, "0": 0, "+": 1}
TRIT_SYMBOL = {-1: "-", 0: "0", 1: "+"}


def balanced_to_int(trits: str) -> int:
    value = 0
    for trit in trits:
        value = value * 3 + TRIT_VALUE[trit]
    return value


def add_balanced(left: str, right: str) -> str:
    """Column addition; a column sum lies in -3..3, and we split it as carry*3 + digit with digit in -1..1."""
    width = max(len(left), len(right))
    left, right = left.rjust(width, "0"), right.rjust(width, "0")
    carry = 0
    result: list[str] = []
    for column in range(width - 1, -1, -1):
        column_sum = TRIT_VALUE[left[column]] + TRIT_VALUE[right[column]] + carry
        carry = (column_sum + 1) // 3  # rounds to the nearest multiple of 3
        result.append(TRIT_SYMBOL[column_sum - 3 * carry])
    if carry:
        result.append(TRIT_SYMBOL[carry])
    return "".join(reversed(result)).lstrip("0") or "0"


def negate_balanced(trits: str) -> str:
    return trits.translate(str.maketrans("+-", "-+"))


samples = ["+", "+-", "+0-", "-0+", "++++", "+--+", "0"]
for left in samples:
    for right in samples:

print("all pairwise sums correct")
print("+0- (8) + +-- (5) =", add_balanced("+0-", "+--"), "=", balanced_to_int(add_balanced("+0-", "+--")))

hardH4 · Fast conversion of huge numbers. Repeated division costs \(\Theta(k)\) divisions of a \(k\)-digit number by a small base, and each division is \(\Theta(k)\) work, so \(\Theta(k^2)\) in total. Write a divide-and-conquer converter that splits the number around \(b^{2^\ell}\) and converts the halves recursively. Measure both on a 200 000-bit number. (Since Python 3.11, str() of huge ints is capped by sys.set_int_max_str_digits, a guard against denial-of-service attacks that exploit this quadratic cost.)

Hint

Precompute \(b, b^2, b^4, b^8, \dots\) up to the number's size. Splitting on \(b^{2^\ell}\) gives a low half with exactly \(2^\ell\) digits, if you pad with leading zeros, and a high half you recurse on with the next smaller power.

Solution
hw_fastconv.py
import random
import sys
import time

DIGIT_SYMBOLS = "0123456789abcdefghijklmnopqrstuvwxyz"


def to_base_simple(number: int, base: int) -> str:
    digits: list[str] = []
    while number > 0:
        number, digit = divmod(number, base)
        digits.append(DIGIT_SYMBOLS[digit])
    return "".join(reversed(digits)) or "0"


def to_base_fast(number: int, base: int) -> str:
    """Divide and conquer: split on base**(2**level), so each half is converted independently."""
    powers = [base]  # powers[level] = base ** (2 ** level)
    while powers[-1] ** 2 <= number:
        powers.append(powers[-1] ** 2)

    def convert(value: int, level: int, pad: bool) -> str:
        if level < 0:
            return DIGIT_SYMBOLS[value]  # a single digit
        high, low = divmod(value, powers[level])  # low has exactly 2**level digits (with padding)
        if high == 0 and not pad:
            return convert(low, level - 1, False)
        return convert(high, level - 1, pad) + convert(low, level - 1, True)

    return convert(number, len(powers) - 1, False) if number else "0"


sys.set_int_max_str_digits(0)
random.seed(3)
for _ in range(300):
    base, number = random.randint(2, 36), random.getrandbits(random.randint(1, 3000))
    assert to_base_fast(number, base) == to_base_simple(number, base)
print("300 random checks passed")

big = random.getrandbits(200_000)
for name, function in [("simple", to_base_simple), ("fast", to_base_fast)]:
    start = time.perf_counter()
    text = function(big, 10)
    print(f"{name:>6}: {len(text)} digits in {time.perf_counter() - start:.2f} s")

The recursion does a few big divisions instead of very many small ones. Python's big-int division is subquadratic for large operands, so the total drops well below the \(\Theta(k^2)\) of digit-at-a-time division (exact timings vary by machine). The padding flag is the subtle part: an inner low half like 0042 must keep its leading zeros, while the very first digits printed must not.

mediumH5 · Shortest round-trip printing. Python prints 0.1 for a double whose exact value is 0.1000000000000000055…. Write shortest_repr(x) that finds the fewest significant decimal digits that parse back to exactly x, and test it on random doubles.

Solution
hw_shortest.py
import random


def shortest_repr(number: float) -> str:
    """Fewest significant digits that still parse back to exactly the same double."""
    for precision in range(1, 18):  # 17 significant digits always suffice for a double
        candidate = f"{number:.{precision}g}"
        if float(candidate) == number:
            return candidate
    raise AssertionError("unreachable for finite doubles")


for number in (0.1, 0.1 + 0.2, 1 / 3, 2.0**-1074, 1e23, 123456789.125):
    print(f"{shortest_repr(number):>24}   repr: {number!r}")

random.seed(5)
for _ in range(100_000):
    number = random.uniform(-1e6, 1e6) * 10.0 ** random.randint(-30, 30)
    assert float(shortest_repr(number)) == number

Why 17 always suffices: a theorem of D. W. Matula (1968) says that \(\lceil 53\log_{10}2\rceil + 1 = 17\) significant decimal digits are always enough to identify a 53-bit binary significand. Intuitively, 17-digit decimals are spaced more finely than neighbouring doubles everywhere in the range (\(10^{16} > 2^{53}\)), so the nearest 17-digit decimal is closer to x than to any other double. hardH6 · Which base is cheapest? Suppose hardware cost is proportional to (number of states per digit) × (number of digits), the so-called radix economy. To cover numbers up to \(N\) in base \(b\) you need about \(\log_b N\) digits. Show that cost ≈ \(\frac{b}{\ln b}\ln N\), find the real \(b\) that minimises it, and compare bases 2, 3, 4 and 10.

Hint

\(\log_b N = \ln N / \ln b\) (§2.2). You need to minimise \(f(b) = b/\ln b\). The derivative of a quotient \(u/v\) is \((u'v - uv')/v^2\), and the derivative of \(\ln b\) is \(1/b\).

Solution

Cost \(= b\cdot \log_b N = b\cdot\frac{\ln N}{\ln b} = \frac{b}{\ln b}\cdot\ln N\). Since \(\ln N\) doesn't depend on the base, minimise \(f(b) = b/\ln b\).

A quick derivative refresher: \(f'(b)\) is the slope of \(f\) at \(b\). A smooth function's minimum sits where the slope changes from negative to positive, i.e. where \(f'(b) = 0\). By the quotient rule with \(u = b\) (\(u' = 1\)) and \(v = \ln b\) (\(v' = 1/b\)):

\[ f'(b) = \frac{1\cdot \ln b - b\cdot\frac1b}{(\ln b)^2} = \frac{\ln b - 1}{(\ln b)^2}. \]

The denominator is positive (for \(b \ne 1\)), so the sign of \(f'\) is the sign of \(\ln b - 1\): negative for \(b < e\) and positive for \(b > e\). So \(f\) decreases until \(b = e \approx 2.718\) and increases afterwards. The minimum is at \(b = e\).

Among integers: \(f(2) = 2/\ln 2 \approx 2.885\), \(f(3) \approx 2.731\), \(f(4) = 4/\ln 4 = 4/(2\ln 2) = f(2) \approx 2.885\) (exactly tied with binary!), and \(f(10) \approx 4.343\). Base 3 is the most economical integer base, about 5% cheaper than binary. That's the usual argument for ternary hardware, and it was part of Setun's motivation. Binary won anyway, because a two-state device (on/off, charged/discharged) is far simpler and more robust than a three-state one, and that real-world cost isn't captured by “states × digits”.

19History

Positional notation took thousands of years to assemble. The hard part was never the multiplication by the base; it was the zero.

  • c. 2000 BCEBabylonian base 60. Mesopotamian scribes wrote numbers positionally in base 60, each digit itself a cluster of wedges for tens and ones. For over a millennium there was no zero sign: an empty place was a gap, or inferred from context. A placeholder sign (two slanted wedges) appears in the last centuries BCE, but almost only between digits, not at the end, so 1 and 60 could still look alike. Their base 60 survives in our hours, minutes, seconds and degrees, helped by the fact that thirds terminate in base 60 (§11.3).
  • 1st millennium CEThe Maya used a base-20 positional system with a true zero glyph (with a quirk in the calendar: the third place counted 18 × 20 days instead of 20 × 20).
  • 628 CEBrahmagupta, in the Brāhmasphuṭasiddhānta, treated zero as a number in its own right and gave rules for computing with it. Indian mathematicians had by then combined decimal place value, a zero digit, and nine digit shapes that are the ancestors of ours.
  • c. 825Al-Khwārizmī wrote a treatise on calculating with the Hindu numerals in Baghdad. Latin translations of it brought the system to Europe, and his name gives us the word algorithm.
  • 1202Fibonacci's Liber Abaci taught the Hindu–Arabic numerals and their column algorithms to European merchants, against the abacus-and-Roman-numeral establishment. It took a few more centuries to win.
  • 1703Leibniz published Explication de l'Arithmétique Binaire in the Paris Academy's Mémoires (printed 1705), working out binary arithmetic and relating it to the hexagrams of the I Ching, which he'd learned about from the Jesuit Joachim Bouvet.
  • 1819W. G. Horner published the evaluation scheme now named after him. It had been known much earlier, to Qin Jiushao in 13th-century China and to Newton.
  • 1885Vittorio Grünwald described negative bases, with algorithms for arithmetic in them.
  • 1945Von Neumann's First Draft of a Report on the EDVAC proposed binary with two's-complement representation for an electronic stored-program computer.
  • 1957–59Pawlak and Wakulicz studied base −2, and Polish machines (BINEG, UMC) computed in negabinary.
  • 1958Setun, the balanced-ternary computer of Nikolay Brusentsov's group at Moscow State University. About 50 were built before production stopped in 1965.
  • 1985IEEE 754 standardised binary floating point after years of incompatible vendor formats, driven largely by William Kahan (Turing Award 1989). Revised in 2008 (adding decimal floating point and fused multiply-add) and 2019.
